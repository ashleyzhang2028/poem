报告里只有结论与「HTTP 状态 + 上游原话」，没有任何密钥。 贴到 Issue 里，CodeBuddy 就能定死是哪一环。

把 <你的域名> 换掉，逐条跑。每条只有一个结论，不必猜：

① API 挂上了没 —— 期望 200
curl -sS -o /dev/null -w '%{http_code}\n' https://<你的域名>/api/config
回 404 且正文是 The page could not be found，那是平台层报的 （本站的 404 是 JSON：{"code":"E_404","message":"没有这个接口。"}）， 意思是 /api/* 压根没接到函数上 —— 重新部署一次。

①之二 函数认不认转进来的地址 —— 期望 401
curl -sS 'https://<你的域名>/api/handler?__path=me'
平台层把 /api/* 转成这个形状再交给函数，所以它也必须是 401。 若它回的是本站的 E_404（JSON），说明函数在、但转进来的地址没人认 —— 那是 vercel.json 里那条 rewrite 的落点与路由表的前缀对不上， 两处必须同名（见仓库 docs/architecture.md §2.2.1.1）。

② 会话签得出来没 —— 期望 401
curl -sS https://<你的域名>/api/me
回 503 就是会话密钥没生效（改完要重新部署才生效 —— 环境变量的改动只在新部署里生效，这是「我明明配了」里最常见的一种）。

③ 库读得动没 —— 期望 200
把下面两条 $库地址 / $服务端密钥 换成你自己的两个值 （变量名在托管平台的环境变量那一页，本页不写它们的名字，免得把密钥名刻进浏览器）：
curl -sS -o /dev/null -w '%{http_code}\n' "$库地址/rest/v1/accounts?select=uid&limit=1" -H "apikey: $服务端密钥" -H "Authorization: Bearer $服务端密钥"

④ 库写得动没 —— 期望 201
把 ③ 的 accounts 换成 codes，加上 -X POST 与 -H 'Content-Type: application/json' -H 'Prefer: return=minimal' 和 -d '{"code_id":"diag-tmp","uid":"u_diag","purpose":"diag","code_hash":"x","salt":"x","created_at":0,"expires_at":0,"consumed_at":null,"attempts":0}'。

⑤ 注册真跑一遍
curl -sS -i -X POST https://<你的域名>/api/register -H 'Content-Type: application/json' -d '{"email":"you+diag@example.com","password":"diagtest12345","deviceId":"diag"}'

⑥ 服务端日志里搜
Vercel → 项目 → Logs，搜 api.error，把那一行的 error 字段贴回来。 四种串互斥：fetch failed（连不上）、supabase 404 PGRST205（表没建）、 supabase 401 Invalid API key（key 不对）、supabase 400 42703 column ... does not exist（表是旧形状）。

自检页会把服务端那一环的结论摊开（含 /api/diag 的服务端自报与 「写入实跑」）。所以它只对已登录的管理员开放 —— 其余情况一律看不到入口，直接打这个地址也不会加载自检脚本。

判断依据是服务端下发的角色（accounts.role 是 owner / admin）。没登录就先去登录， 角色不够就找管理员。
