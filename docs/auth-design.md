> 关联：Issue #132 / #163。当前 SW 缓存版本：`poem-app-v142`。
> **「现在不做、以后做」的条目另有一份**：[`docs/todo.md`](todo.md) ——
> 本文写的是**设计与已落地**的口径，两者别混。
>
> **「我的」页与设置整页分开**（2026-09-17，Issue #205）：
> 用户先要求把右下角那个页签改成「我的」，接着要求
> 「**在我的页面放个小齿轮作为设置的入口，其他还是应该放个人的全部内容**」。
> 于是分成两张页：
>
> - **`/mine/`（「我的」）只回答「我是谁」**：头像（上传 / 删除就地做）、昵称、
>   登录状态与层级徽章、本机数据、子用户、危险区（注销）。
>   那颗账号入口（未登录「登录」/ 已登录「管理登录状态」）也在这里。
> - **`/settings/`（设置整页）只回答「怎么调机器」**：四张二级页的入口一行不减，
>   外加「关于」。入口是「我的」页右上角那颗**齿轮**
>   （`<body data-top-action="settings">`）。
>
> 设置项本身一个没动：`/settings/general/`（通用：用户名 / 子用户 / **账号** /
> 数据管理）、`/settings/recite/`、`/settings/lists/`、`/settings/reader/` 照旧。
> **头像**从「通用」搬到了「我的」（它答的是「我是谁」，不是「怎么调机器」）。
> 本设计里凡是「设置页」字样，现在指的都是**对应的那张二级页**；
> 「账号」那一项仍在 `/settings/general/`（§3.5 的层级徽章与权限清单已经从 API
> 变成界面上真实可见的一行），`/privacy/` 那句「不上传、不云同步」在那里如实复述。
> 拆分不改变任何分组口径（四张页合起来把原来的组摊开；后来「阅读辅助」
> 与「朗读播放」两条各只有一条设置的组并成了一组「朗读」），
> 四张二级页的返回键仍是 `data-back="/settings/"`，而设置整页自己换成
> `data-back="/mine/"`（「我的」页顶上没有返回键，右端让给齿轮）。

## 0. 一句话结论

**主键选邮箱，登录凭证一律走邮箱随机码（无密码）；本期全部落在浏览器本机，
不发送任何网络请求；服务端只是「同一份协议换一个实现」，届时客户端零改造。**
短信登录不是「另一套流程」，只是 `channel: "email" | "sms"` 的一个取值 —— 见 §8。
条款口径已按「**条款永远跟随代码**」裁决并落地：代码实现到哪，条款就如实写到哪，见 §12。

## 1. 三条不可退让的边界（先立规矩，再谈流程）

1. **不花钱、不备案也能跑**
   本期不买短信、不买域名、不买服务器。邮箱通道由用户自己的邮箱服务商提供。

2. **不破坏「打开即用、可离线」**
   没登录的人，功能与今天**完全一致**。账号只增加「数据不丢」与「跨设备同步」两件事，
   不拿任何现有功能当人质。

3. **不假装安全**
   本期没有服务端，所有校验都在用户自己的浏览器里，**任何人都能绕过**。
   因此本期定位是「身份与数据的归属登记」，不是「防篡改的鉴权」。
   凡是用它当收费/权益凭据的用途，**本期一律不做**（详 §3.4、§12）。

## 2. 术语与账户形态

| 术语 | 含义 |
|---|---|
| **账号** | 一行账号记录，主键是 `uid`（不可变），登录标识是邮箱 |
| **身份标识 identity** | `{channel, value}`，如 `{email, a@b.com}`、`{sms, 138…}` |
| **会话 session** | 一次登录的凭据，本期为 30 天有效 + 可续期 |
| **随机码 code** | 短时效、单次使用的登录码，取代密码 |
| **档案 profile** | 账号下的展示信息（昵称），**不是儿童实名** |

### 2.1 账户形态：一人一账号，儿童不做独立账号

跬步面向家庭。**只允许成年人建号**，孩子的昵称是账号下的一个「展示名」，
不是独立账号（理由：未成年人实名/同意合规成本高，且无任何产品收益）。

- `profile.nickname` 就是今天设置页的那个「用户名」，`maxlength=12`，纯展示
- 账号可以登记多个昵称（`profiles[]`），将来做「家庭子用户」时不用改表结构
  > ✅ **已落地（2026-09-17，Issue #159）**：`profiles[]` 的形状真的没改
  > （`poem_profiles_v1 = {v:2, profiles:[{id,nickname,avatar,born}], current}`），
  > 表结构一行未动（`accounts` 至今没有 child / parent / family_id 任何一列）。
  > 「多个孩子各背各的」不是靠给孩子建账号，而是靠**本机的键分家**：
  > 进度 / 设置 / 已读跟着子用户走，设备域不跟（`docs/architecture.md` §5.2 ④）。
- **头像**：⚠️ **口径 2026-09-19 被用户改过**（Issue #163）——
  现在**做图片头像**，见 §2.3 与 `docs/architecture.md` §4.21
- **本期不做生日/学校/年级实名**：一律不收集

### 2.3 头像口径：**用户名首字 + 可上传图片**（2026-09-19 重裁）

> ⚠️ **本节 2026-09-19 整节重写**（Issue #163）。上一版写的是

> 完整设计（两档回落、域划分、本地压缩与方形裁切、裸字节上传、
> 路径由服务端拼）在 `docs/architecture.md` **§4.21**，此处不复述。

一句话现状：

| 档 | 什么时候 | 画什么 | 存哪 |
|---|---|---|---|
| **首字印**（默认） | 没传过图 | 用户名的第一个字母 / 汉字（英文大写）；昵称为空才回落到「诗」 | 只有昵称，账号域 |
| **图片** | 传过图 | 那张图（本地压成 256×256） | 地址进账号域；**字节进设备域** |

三条与账号设计直接相关的口径：

- **不传图 = 一个字节都不上传**。上一版那条「不收集」的承诺不是被推翻了，
  而是被**收窄到它本来的边界**：只有你主动传的那一刻，那张图才上云。
- **图片是公开可读的地址**（Supabase Storage 的 public bucket）——
  所以 `/privacy/` 里明确写了「谁拿到地址都能看到这张图，别用真人照片」。
- **儿童照片这件事由界面文案挡**，不由功能挡：`/privacy/` 的
  「昵称请只填小名」那一条旁边现在多了「头像别用真人照片」。
  挡不住的部分如实说明，比藏起功能诚实（用户要的是能传图）。

#### 2.3.1 上一版（字符印）为什么被删 —— 留作教训

那一版不是「做得不好」，是**方向错了**：它做了一个用户到处没见过的流程
（先从 12 个字里挑一个，再从 4 个颜色里挑一个）。理由写得很足
（不收集、不存图、儿童照片不上云），但**把「不收集」当成了不做的理由** ——
而那条承诺属于 `/privacy/`，不属于头像这个功能。用户原话：

> 「头像印记设置和传统用户头像流程不符，让人困惑，直接删除这个功能，
>  四个颜色背景选择全部删除。」

→ 教训：**自造的流程就是「困惑」本身**。要改的是条款，不是功能。

### 2.2 账号记录（与存储实现无关的字段定义）

```jsonc
{
  "uid": "u_8f3k2m9q",          // 不可变主键，永不复用
  "identities": [                // 登录标识，可多枚，每枚唯一
    { "channel": "email", "value": "a@b.com", "verifiedAt": "2026-09-15T02:00:00Z" },
    { "channel": "sms",   "value": "13800138000", "verifiedAt": "—" }   // 未来
  ],
  "profile": { "nickname": "小明" },
  "createdAt": "2026-09-15T02:00:00Z",
  "updatedAt": "2026-09-15T02:00:00Z",
  "lastLoginAt": "2026-09-15T02:00:00Z",
  "status": "active",            // active | suspended | deleting | deleted
  "plan": { "tier": "free", "until": null },   // 本期恒为 free，预留 pro/max
  "security": {
    "pwVersion": null,           // 无密码方案，留字段以便将来"改密"兼容
    "codesToday": 3,             // 当日发码次数（频控用）
    "codesDay": "2026-09-15",
    "failCount": 0,              // 连续失败次数
    "lockedUntil": null
  }
}
```

**五个硬约束**（写在测试里，见 §10）：
- `uid` 一旦分配，**永久不复用**（注销后也不回收，避免「新用户接管旧数据」）
- `identities[].value` 在**同一 channel 内唯一**；邮箱一律 `trim + 小写` 后比对
- 真实邮箱**以明文落盘**（Issue #197 用户裁决「邮箱必须记录到数据库」，
  见 §4.4.2）—— `accounts.email` 是明文，`email_hash` 仍用于登录查找
- `plan` / `security` / `status` **不属于用户可编辑数据**，导入备份时忽略
- 只有 `channel: "email" | "sms"` 两种，其余 channel 直接拒绝

## 3. 认证的三种模式（本期只开前两种）

| 模式 | 触发 | 适用 | 本期 |
|---|---|---|---|
| **本机模式**（local） | 默认 | 只想用、不想给邮箱 | ✅ |
| **邮箱码模式**（code） | 用户主动「用邮箱登录」 | 换设备、防数据丢失 | ✅ |
| 服务端鉴权模式（server） | 将来接后端 | 权益校验、支付 | ⛔ 预留 |

三者**共用同一套界面与同一个账号对象**，区别只在「谁签发会话」：

```
local  : 会话由 AuthCore.issueSession() 本机签发，scope = "local"
code   : 会话由服务端在 verify 成功时签发，scope = "account"
```

### 3.1 为什么用「随机码」而不是「密码」

- 家长群体记不住密码，**忘记密码是最高频的求助**
- 无密码就没有「密码泄漏 / 撞库 / 加盐存储」这一整类问题
- 与将来的短信登录**语义完全一致**：都是「一次性短码换会话」
- 代价：每次登录都要收信 —— 用 §6.3 的「设备信任期」抵消

### 3.2 为什么不是「邮箱 + 密码」「用户名 + 密码」

- 用户名登录要做昵称查重 + 找回 + 防枚举，成本高于收益，且与现有 `username` 展示语义冲突
- 自建密码存储要么自研（风险高）要么依赖后端（本期没有）

### 3.3 为什么不是第三方 OAuth（Google/GitHub/微信）

- 面向国内家长，Google/GitHub 无意义
- 微信网页授权需要 **已认证服务号 + 企业主体 + 备案域名**（详见 issue 前序讨论），与「不花钱」冲突
- 但**接口留了口子**：`identities[].channel` 可以扩到 `wechat`，`linkIdentity` 流程不变
- ⚠️ 微信登录（以及**微信小程序版**）已进「现在不做、以后做」的清单：
  [`docs/todo.md`](todo.md) 第 2、3 条

### 3.5 权益总闸：free / pro / max 三层（已落地，2026-09-15 裁）

> 「我还是想设置 free、pro、max 类似的用户分级，顶多不用支付，
> 我是管理员，我可以给他们分配不同的权限用不同的功能。」
> 「后面还会添加飞花令、古诗文大会、考试及题库等功能，这些功能至少 pro 用户才能使用。」
>
> ⚠️ **2026-09-17 的裁决把它分得更细**（Issue #159）：
> 「**现场考试和飞花令归 max 所有，题库归 pro.**」
> 所以上面那张表里的「飞花令 / 现场考试（今名「试题模拟」· 2026-09-19 另拆出
> 「古诗词大会集子」`exam.gathering`）」是 **Max** 起，题库复习是 **Pro** 起 ——

> 「我建议未登录用户不能使用全部语音播放功能，登录的 free 用户可以使用。」

### 3.6.2 账号入口动线（D 步，已落地）

三张账号页建好之后，剩下**最后一块**：从一个「未登录的人」到 `/login/` 的路。
这一块不写清楚，页面就只是「存在」，用户找不到 —— 那比不建更浪费。

**四页签里没有账号的位置**（背诵 / 课外 / 搜索 / 我的，每格才两三个字，
再加一格手机上一行就挤变形，`test/ui-consistency.test.js` 守的就是这件事）。
所以入口只能从「已有结构」里长出来，一共两个落点：

| 落点 | 谁渲染 | 指向 | 什么时候出现 |
|---|---|---|---|
| 「我的」页账号卡里的**账号入口** | `js/mine.js` | `/login/` | 总是（未登录「登录」/ 已登录「管理登录状态」，同一个落点） |

> ⚠️ **2026-09-20（Issue #244）：原 `/profile/`「个人中心」那一页已删除。**
> 用户原话：「现在有了 mine 页面，这个 profile 页面是不是可以删除了？」
> 两个页连卡片都长得一样（身份 / 本机数据 / 关于 / 注销），「我的」页还多了
> 子用户与头像上传 —— 于是个人中心**独有**的那几件（法务两条入口、
> 层级对比、跨设备同步开关 + 冲突裁决、管理后台）整体搬到「我的」页的
> 「关于」卡里，页面、脚本、预缓存、路由一起删干净，全站不再有 `/profile/`。
> 守卫在 `test/profile-removed.test.js`（含「搬过去的那四件还在」的正面断言）。

**两条独立的路**：动线是
① 底部「我的」页签 → `/mine/` → 账号入口 → `/login/`，
或 ② `/mine/` → 齿轮 → `/settings/` → 「通用」→ 账号那一项 → 去「我的」页。

**返回落点**（`data-back`，由 `js/chrome.js` 的 `pageBackHref()` 统一出）：

```
/login/     → /mine/       （登录是身份的事；落回设置页等于又多绕一层）
/admin/     → /mine/       （管理后台是从「我的」页进去的）
/mine/      → （没有）     （它是页签落点，顶上没有上一层；右端让给齿轮）
/settings/  → /mine/       （齿轮点进来，返回键点回去）
/settings/general/ → /settings/  （四张二级页同一条）
```

登录**成功之后**也回 `/mine/` —— 与顶栏返回键同一条动线，不出现两条。

**两条刻意收着的口径**：

1. **已登录时不再摆「去登录」**（自相矛盾）。「我的」页那一行此时换成
   「管理登录状态」，身份行上写着「昵称 + 层级徽章」；想退出 / 注销的人也在这一页，
   与那两件事放在一起。
2. **不做「到了 `/login/` 就把已登录的人弹回来」那种聪明** ——
   点一下就被弹回去，用户只会以为按钮坏了。`/login/` 自己认会话与信任期：
   信任期内顶部给「继续以 `a***@b.com` 进入」，会话还在时同样能继续。

**「我的」页那颗键是「自己会收敛的」**：拿不到内核（老缓存、脚本顺序不对）时
整个身份卡按默认值画（Free / 本机游客），账号入口照旧在 —— 它是这一页的主语，
不画的话这一页就没有意义。
（Issue #163 第四轮起，它与四组入口**共用 `#settings-index` 这一张清单**：
`renderAccountEntry()` 追加在 `renderIndex()` 之后，所以两处的调用顺序不能反。）

### 3.6.1 `/login/` `/admin/` 两张页（已落地；「个人中心」已并入「我的」页）

「账号」在设计里活了很久、在界面上一直只是一行只读状态。这几张页落地之后，
它第一次成为**用户可以自己走完的流程**：

| 页 | 做什么 | 不做什么 |
|---|---|---|
| `/login/` | 输邮箱 → 收码 → 填码 →（可选）补昵称；信任期内一点即入 | 不假装有服务器（见 §7.1）；不发任何网络请求。「重设凭证」那块页面入口已撤（#163：一页只有一套「输邮箱 → 收码」表单），能力本身保留 |
| `/admin/` | 按邮箱掩码发放层级；名单增删；导出 / 导入；「以 Free 身份预览」；清空（二次确认） | 非 `owner` 时**整页如实拒绝**且不渲染任何发放信息 |
| `/plans/` | 四列（未登录 / Free / Pro / Max）逐条对照；「你现在在这」那一列高亮；表尾每列可用项数（见 §3.6.2） | 不做收款、不做促销话术；不写任何存储 |

**四条硬规矩（已钉进 `test/account-pages.test.js` 与 `test/mine-page.test.js`）：**

1. **页面不许自己拼 `plan` / `tier`** —— 徽章与清单一律走
   `Entitlement.tierLabel()` / `matrix()` / `isOwner()`；页面里不出现
   `poem_plan_v1` / `poem_plan_grant_v1` / `poem_owner_v1` 任何一个键名
2. **本地体验版必须如实标注** —— `/login/` 上写着「本应用没有服务器，
   随机码由你这台设备生成」；文案用的是「已**生成**随机码」而不是
   「已发送」；有反向断言拦着「邮件已发送」这类说法
3. **退出与注销都不碰进度** —— 界面上如实写出来。实测：注销后
   `poem_recite_progress_v1` 与 `poem_profile_v1` 原封不动
4. **账号这几页一个字节都不写进度键** —— 有源码扫描守着（六把进度/设置键名一律不许出现）

**`role` 与 `tier` 是两条正交的轴。** `Entitlement.isOwner()` 是全站唯一
回答「谁能进管理后台」的函数，落在 `poem_owner_v1` 上：

> ⚠️ **2.2 起要分清两件事**：`isOwner()` 管的是「这一页画不画给你」，
> 而**真正拦人的是服务端**（`accounts.role`）—— `POST /api/admin/grant`
> 对有会话但不是 owner / admin 的请求如实回 **403**。
> 「入口藏起来」**不是**安全边界，这条从 1A 起就写着，2.2 让它第一次**真的成立**
> （在那之前，服务端根本没有能改别人数据的接口，所谓安全边界无从谈起）。

- **首次打开的这个浏览器自动成为本机主人**（幂等）。没有这个兜底，
  `/admin/` 会永远对所有人关着，那一页等于不存在
- 「我的」页的管理后台入口与 `/admin/` 的准入**走同一个出口** ——
  不会出现「入口看得见、点进去被拒」这种自相矛盾的组合
- 层级仍是 `free`：**管理员不是「买了 Max 的人」**
- 1 期接服务端后 `isOwner` 改读 `/api/me` 下发的 `role`，页面一行不动

**`js/admin-page.js` 这个名字有来历。** 管理页的逻辑**不叫** `js/admin.js`：
早年「访问统计」被整体删除时，`js/admin.js` 正是那个统计脚本的名字，
而 `test/legal.test.js` 立了一条反向断言「这个文件必须不存在」。
复用同名会让那条**正确**的防线变红 —— 改名比改断言好（断言守的是事实）。

**顶栏头像这一轮也改了规格**（用户 2026-09-15 要求）：
「右上角方形圆角还是替换成和 logo 一模一样大小的圆形」。
于是顶栏那一枚与 `.brand-mark` **同径 42px、整圆、印色铺满**，
`js/chrome.js` 不再自己传 `size`（尺寸只剩 CSS 一处来源）。
> ⚠️ **后记（2026-09-18 / 2026-09-20）**：顶栏那一枚头像后来**整块撤掉**了，
> 头像现在只长在「我的」页的身份卡里一处（见 §4.18）；
> 它当年的落点 `/profile/` 也随个人中心一起删了（Issue #244，见 §3.6.2）。

### 3.6.2 `/plans/` 层级对比页（已落地，2026-09-15 用户提）

用户的原始问题（Issue #132）：

> 「我看到了个人中心有个权限部分，这部分内容是不是应该有个专门的像其他网站
> 不同角色进行 4 列或者 5 列对比页面？最左侧是对比项目，右侧四列分别是匿名用户、
> 登录 free 用户、登录 pro 用户、登录 max 用户，下面用好看的打钩或者打叉。」

落地为 `/plans/`：**四列 × 逐条对照**，从「我的」页「关于」卡里那一行
「层级对比」进去（原先是 `/profile/` 的「权限」），看完就走。

| 列 | 是什么 | `can()` 收到的 ctx |
|---|---|---|
| 未登录 | 游客（匿名） | `{ tier: "free", signedIn: false }` |
| Free | 登录后的免费层 | `{ tier: "free", signedIn: true }` |
| Pro | 登录后的 Pro | `{ tier: "pro", signedIn: true }` |
| Max | 登录后的 Max | `{ tier: "max", signedIn: true }` |

**为什么是四列而不是把「游客」并进 free：** 游客与 free 之间差的是
`signedIn` 这个布尔，不是层级。今天全表只差一条（`read.aloud` ——
语音朗读要登录），但它恰恰是最容易被误解的一条（用户会把
「游客不能听」读成「免费版不能听」）。**单独一列，是把这件事说清楚的唯一办法。**

**这张表不许手抄。** 每一格都由 `Entitlement.compare()` 当场问 `can()` 算出来
（比原先 `/profile/` 那一节的 `matrix()` 更进一步：那边只画一档，
这边四档并排）。
手抄一份的下场是内核改了门槛、这张表还是老话 —— 而这张表恰恰是
**用户唯一会逐条对着看的页面**。`test/plans-page.test.js` 里有一条断言
把「每一格 === `can()` 的答案」逐格比一遍，不一致就红。

**三条已经钉进测试的口径：**

1. **未登录 ≠ free，且只差一条** —— 断言直接数「两列不一致的能力条数 === 1」，
   将来多锁一条免费功能会立刻红（那正是要人来确认的事）
2. **单调不回退** —— Free 有的 Pro 一定有、Pro 有的 Max 一定有。
   这条防的是「顺手把某项标成 pro-only 就把它从 free 收走了」这类误伤
3. **表尾必须与表身相符** —— 「能用 12/15」这种数字由同一份 `cells` 算出来，
   不许另算一遍（两个数字对不上是最难解释的 bug）

**诚实口径（本期特有）：** 表尾写明层级是**本机登记**、**不是付费凭据**、
没有收款也没有支付入口；页面里不出现「立即购买」「限时优惠」这类话
（本期确实收不了钱，写上就是假的）。`/plans/` 一个字节都不写存储 ——
看表不该留下痕迹。

## 3.6 「账号」在界面上长什么样（已落地在 /mine/ 与 /settings/general/）

设计走到这一步，账号一直只活在 `js/auth-core.js` 里 —— 用户看不到它。
现在它有两个展示位，**各说各的那一半**：

- **`/mine/`（「我的」页）**：身份行（印 + 昵称 + 掩码 + 层级徽章）+ 那颗账号入口
  （未登录「登录」/ 已登录「管理登录状态」）。这一页回答的是「**我是谁**」，
  所以头像、昵称、子用户、本机数据、注销全在这。
- **`/settings/general/`（「通用」）**：账号那一项说「**怎么调**」——
  登录状态一行 + 去 `/login/` 的键 + 层级来源那一行。

**只读展示 + 退出，不做别的**（理由：`/login/` 还没建，
做半截的登录流程比不做更糟）：

| 状态 | 界面写什么 |
|---|---|

## 4. 完整流程：注册 / 登录 合一

**注册与登录是同一个动作**（邮箱码方案的天然优势）：输邮箱 → 收码 → 填码 →
若该邮箱没有账号则建号，有则登录。用户不需要理解「我在注册还是登录」。

```
[入口] /login/
  │
  ├─ ① 输邮箱 ─────────────────────────────────────────────┐
  │    · 前端校验格式（宽松：本地部分不校验字符集大小写）      │
  │    · 归一化：trim → 小写 → 去掉零宽字符                  │
  │    · 命中「一次性邮箱前缀表」→ 提示但**不阻断**（§6.5）    │
  │    · 频控检查（§6.2）：邮箱 / 设备 / 全局三层            │
  │                                                          │
  ├─ ② 点「发送随机码」 → requestCode(identity, purpose)      │
  │    · 生成 6 位数字码（§5.1）                             │
  │    · 本机存 code 记录（§5.3），**不存明文码**（§5.4）      │
  │    · 本期：唤起 mailto: 预填主题与正文（§7）              │
  │    · 服务端版：调 POST /auth/code → 邮件由服务端发         │
  │                                                          │
  ├─ ③ 用户去邮箱取码，回来填 6 位 ─────────────────────────┤
  │    · 6 格数字输入框，自动跳格、支持整段粘贴                │
  │    · 每隔 1 秒检查一次过期，剩余时间倒计时显示             │
  │                                                          │
  ├─ ④ verifyCode(uid, code, purpose)                       │
  │    · 命中 → 建号/取号 → 签发会话 → 进 ⑤                 │
  │    · 不中 → failCount++，按 §5.5 的阶梯锁定              │
  │                                                          │
  └─ ⑤ 登录成功
       · mergePolicy：把本机未登录的进度「认领」进账号（§9）
       · 若 profile.nickname 为空 → 提示补昵称（沿用今天那 12 字输入框）
       · 跳回来源页；PWA 下不整页刷新
```

### 4.1 状态机（不可跳步；每条转移都有测试）

```
idle ──enterEmail──▶ emailEntered ──requestCode──▶ codeSent
                          ▲                            │
                          │                            ├──verify ok──▶ signedIn
                          │                            ├──verify bad─▶ codeSent (failCount+1)
                          └────resend / editEmail──────┤
                                                       ├──expired────▶ codeExpired ──resend──▶ codeSent
                                                       └──locked─────▶ locked ──wait/换设备──▶ idle
signedIn ──signOut──▶ idle
signedIn ──deletingAccount(二次确认)──▶ signedOut+erased
```

规则：
- `codeSent` 下**可以改邮箱重发**，但会清掉旧码（不允许两个邮箱的码并存）
- 任何一步刷新页面，状态从本机 `pending` 记录恢复（`codeSent` 可续）
- `locked` 是终态之一，**不因为重试自动解锁**，只能等 `lockedUntil`

## 4.4 【Issue #197】完整登录流程（已落地，2026-09-16 用户裁）

用户原话：

> 「我要求重新设计用户的整个登录流程。使用邮箱注册，注册邮件确认，登录，

这一节的每一件事都是**已落地**的（不是路线图），落地位置写在每条下面。

### 4.4.1 流程全图（六条路，两条主路 + 四条支路）

```
                     /login/（一页四屏，页签切动作不跳页）
                     │
   ┌─────────────────┴─────────────────┐
   │                                   │
【主路 A】密码登录                   【主路 B】快捷登录（随机码）
   邮箱 + 密码                         邮箱 → 收 6 位码 → 填码
   → session.issue                     → session.issue
   │                                   │
   └──────────┬────────────────────────┘
              │  （两条路签发的是**同一枚会话**，下游不必知道从哪条路进来）
              ▼
        登录成功 → 补昵称 → /mine/

【支路 ①】注册    ：「还没有账号？注册」→ 邮箱 + 密码 ×2
                      → 立刻建号（status='pending'）+ 发确认邮件 → 支路 ②
                      ⚠️ **确认之前登不进去**（两条主路都拦，见 §4.4.9）
【支路 ②】等确认    ：/verify/?vid=..&token=..  ← 邮件里那条链接（独立一页）
                      没收到 → 登录页那一屏的「重新发一封」（**匿名**可用）
【支路 ③】忘记密码 ：「忘记密码」→ 输邮箱 → 服务端发重设邮件
【支路 ④】重设密码  ：/reset/?rid=..&token=..   ← 邮件里那条链接（独立一页）
                      → 新密码 → **吊销全部会话** → 回登录页
```

**注册与快捷登录不是同一件事**（这一条与上面的 §4「注册 / 登录 合一」口径**并存**，
两者说的是两件事，别混）：

| | 快捷登录（随机码） | 注册（邮箱 + 密码） |
|---|---|---|
| 触发 | 主动作页签「快捷登录」 | 藏在「还没有账号？注册」文字链后面 |
| 何时建号 | **收到码才建号**（`findOrCreateAccount`） | **填完就建号**（口令要有地方放） |
| 邮箱确认 | 需要（**两条登录路都拦** —— 只拦一条等于没拦） | 需要（发确认邮件） |
| 口令 | 没有 | 有（scrypt 摘要） |

两条路都保留，**不是过渡期的临时状态**：家长群体记不住口令
（§3.1 写着「忘记密码是最高频的求助」），所以「不想记口令的人」
必须还有得走。反过来，只有随机码不够 —— 找回凭证、跨设备、将来的
第三方绑定都要一个稳定的账号锚点。

### 4.4.2 邮箱明文**落库**（推翻 §6.1 与 §2.2 的旧口径）

> ⚠️ **这是一次口径推翻，不是补充。** Issue #132 那一版写的是
> 「邮箱不以明文落盘，只存 `email_hash` + `email_mask`」；
> Issue #197 用户裁的是「**要求用户邮箱必须记录到数据库**」。
> 以本文为准：**明文落库**。

| 列 | 是什么 | 谁用它 |
|---|---|---|
| `accounts.email` | **明文**（`normalizeEmailForStore()`＝trim + 去零宽，**保留大小写**） | 显示（个人中心说「你的邮箱是 xxx」）、管理员名录、发信 |
| `accounts.email_hash` | `SHA-256(pepper \| 归一化邮箱)`，归一化**含小写折叠** | **登录查找**（`getAccountByHash`）、老数据平滑 |
| `accounts.email_mask` | `a***@b.com` | 界面回显、按掩码发放 |

**四条必须一起看的连带影响**：

1. **登录查找仍走 `email_hash`**，所以「大小写不同算同一个账号」这条历史行为
   **一个字都没变**。`email` 那一列只是**显示**用的，不参与查找 ——
   拿它去查的话，「A@b.com」与「a@b.com」会变成两个账号。
2. **明文只下发给「你自己」**（`/api/me`、登录 / 注册的响应）与**管理员**
   （`POST /api/admin/accounts`，且那条接口本身有角色闸）。
   别人的邮箱永远只以掩码出现。
3. **`email_hash` 留着**，不是历史包袱：老行不必回填明文就能继续登录；
   而且「按明文查账号」这条路永远不必开。
4. **老行可以是空明文**（`email` 默认空串）。界面遇到空值时**如实回落掩码**，
   绝不编一个 —— 编出来的明文比掩码更糟（掩码至少是真的）。

### 4.4.3 口令：怎么存、怎么判、怎么找回

| 项 | 值 | 落点 |
|---|---|---|
| 算法 | `scrypt(N=16384, r=8, p=1, len=32)`，Node 自带 `crypto` | `identity.hashPassword()` |
| 摘要串 | `scrypt$N$r$p$<saltHex>$<hashHex>` —— **参数写在串里** | 同上 |
| 盐 | 每个账号 16 字节随机 | `identity.newPasswordSalt()` |
| 最短 | 8 个**码点**（不是 UTF-16 长度） | `core.checkPassword()` / `PASSWORD_MIN` |
| 最长 | 72 个字符（防 DoS：scrypt 对超长输入一样要算） | `PASSWORD_MAX` |

**为什么参数写在摘要串里**：将来调 `N` 值，老用户必须还能登进来。
参数不写进串的下场是「换了参数之后所有老用户登不上」，
而那时**没有任何办法区分「口令错」与「参数变了」**。

**为什么最短按码点数**：`"😀😀😀😀😀😀😀".length === 14`（每个代理对算 2），
按 `.length` 判的话「七个 emoji」会被算成十四位而通过 —— 而它其实只有 7 个字符。

**明文口令出现在哪**：只在 ① 生成它的那一次函数调用内、② 用户的输入框里。
库里、日志里、响应体里、URL 里**都不出现**。
`test/api.test.js` 第廿二节逐条钉住，另有一条源码扫描断言守着
「`js/login.js` / `js/reset.js` 里没有一行同时出现口令与本地存储 / URL」。

**忘记密码 = 重设，不是找回**。本站拿不回原密码（只有单向摘要），
所以「忘记密码」这条路走到头是「设一个新密码」。这一点在
`/terms/` 里如实写出来了 —— 用户以为能找回原密码、结果发现只能重设，
那是体验事故。

### 4.4.4 两张一次性令牌表（**不并进 `codes`**）

| 表 | purpose | 谁发 | TTL | 形态 |
|---|---|---|---|---|
| `verifications` | `verify` | 注册时、个人中心点「重发确认邮件」 | **24 小时** | 邮件里那条链接 |
| `resets` | `reset` | 忘记密码第一步 | **1 小时** | 邮件里那条链接 |
| `codes`（既有） | `login` / `reset` | 快捷登录 | 10 分钟 | 6 位数字 |

**为什么不合成一张表**：两者是两种完全不同的凭据 ——
一个是 6 位数字（空间 1e6，靠失败上限与短 TTL 防猜），
一个是 64 位 hex（空间 2^256，靠 TTL 与「用过一次」防重放）。
合成一张表的下场是 **TTL、失败上限、作废规则互相污染**，
而症状是「确认链接十分钟就过期了」（被码的 TTL 带上）这种谁也查不出原因的怪事。

三条共用纪律（三张表都一样）：
- 落库的**只有摘要**（`tokenHash(uid, purpose, token, pepper)`），明文令牌只在邮件里
- **发新的即作废旧链接**（`voidVerifications` / `voidResets`）
- 形状不对（不是 64 位 hex）**不进库** —— 省一次查询，也少一条脏数据

### 4.4.5 四条「不假装」与三条「不泄露」

**不假装**（错了就说错了，成了就说成了）：

| 情形 | 如实说什么 |
|---|---|
| 发信商没配（console 通道） | `verifySent:false` → 界面写「这台服务器现在**没能**把确认邮件发出去」 |
| 服务端连不上 | 口令那四屏**整体不可用**（如实说），**绝不**回落本机 —— 本机版给不出「注册成功」这个真承诺 |
| 「邮箱还没确认」 | **拦**（403 `E_EMAIL_UNVERIFIED`），并给出一整屏「去点确认」+ 一颗「重新发一封」（**匿名**口，不需要登录）；应急闸门关掉时如实说「这台服务器现在**没有**拦」；**绝不**因为「信发不出去」就放行 |
| 注册时邮箱已存在 | 回**同一个响应**（`created:false` 但不报「已注册」），同时补口令 + 重发确认邮件 |

**不泄露**：

1. `login`：口令错与账号不存在回**同一个响应**，而且**耗时也一样**
   （账号不存在时照样算一次 scrypt；不然「这个邮箱注册过没有」
   就成了一件可以测出来的事）
2. `reset-request`：存在与不存在回**逐字相同**的响应
   （`test/api.test.js` 在生产形态那一档上直接比 JSON）
3. 两处的文案都**不出现**「没注册过 / 不存在」这类断言；
   允许的是**条件句**（「如果这个邮箱在本站注册过…」）——
   判断留给收件箱，界面不替服务端回答

### 4.4.5-A 邮箱确认闸：**不确认就不让登录**（2026-09-16 用户裁决）

用户在 Issue #197 里裁了：**不确认就不让登录**。这条推翻的是
本文上一版「不确认也能用」的口径 —— 下面是它落地后的**全部**口径。

| 项 | 口径 | 落点 |
|---|---|---|
| 拦谁 | `status === "pending"` 且 `email_verified_at == null` | `core.verifyGate()`，**只写一处** |
| 拦几条路 | **两条都拦**（口令 / 随机码） | `loginWithPassword` 与 `verifyCode` 各读它一次 |
| 判据落在哪 | **口令 / 码校验成功之后** | 见下 |
| 回什么 | **403 `E_EMAIL_UNVERIFIED`** | 不是 401（会被读成「没会话」），也不是 423（那是「等一会儿再来」） |
| 他唯一的出路 | **匿名重发确认邮件** | `POST /api/resend-verification` 不再要求登录，见 §4.4.5-B |
| 应急闸门 | `REQUIRE_EMAIL_VERIFIED`（默认 `1` = 拦） | 见下 |

**为什么判据必须落在校验之后**：落在之前，回话就会区分
「这个邮箱注册过但没确认」与「这个邮箱压根不存在」—— 那就成了
「谁是本站用户」的查询口（本文里三条反枚举纪律同源）。
落在之后，攻击者得**先猜中口令或拿到码**才撞得到这道闸，
而那时他本来就已经是账号主人，「这个邮箱确认了没有」对他不是新信息。
`test/api.test.js` 第廿六节 ① 逐条钉住这一点（未确认 + 错口令 → 401，不是 403）。

**老账号不会被倒扣**：闸只认 `status === "pending"`。
Issue #197 之前建的账号没有那个状态，它们**照旧能进** ——
否则一次升级就把全部老用户锁死，而他们连「重发确认邮件」那颗键在哪里都不知道。
这不是网开一面，是「口径变更不倒扣到已经存在的账号上」。

**应急闸门 `REQUIRE_EMAIL_VERIFIED=0`**：默认是拦。可以关掉的**唯一**理由是 ——
发信商没配（`MAIL_TRANSPORT=console`）时确认邮件送不到真人的收件箱，
那种实例上开着这道闸等于**谁也别想注册**。所以：

- 判据是「拦」；只有 console 通道的实例才由运维关掉
- **关掉时界面必须看得出来**：服务端把它自报在 `/api/me` 的
  `channel.requireVerified` 与注册响应里，界面据此不写「没确认就进不来」，
  并如实写「这台服务器现在没有拦」

### 4.4.5-B 重发确认邮件：**两条入口，一套闸**（未确认的人唯一的出路）

「不确认就不让登录」落地之后立刻暴露一个**死结**：
「注册完没点确认」的人登不进来 → 进不了个人中心 → **发不出确认邮件**。
屏幕上没有任何可点的东西，他唯一能做的是再注册一次（而那条路见 §4.4.5-C）。
所以这一条现在有**两条入口**，共用同一套闸与同一句文案：

| 入口 | 认谁 | 什么时候用 |
|---|---|---|
| 登录态（Cookie） | 会话里的 `uid` | 个人中心那颗「重发确认邮件」 |
| **匿名**（带 `email`） | 那个邮箱 | 登录被 403 拦下来之后，登录页那一屏 |

**匿名入口是全站唯一「不登录也能让本站往外发信」的接口**，所以四条闸都上了：

1. **频控四层 + 冷却**：邮箱 / 设备 / **出口 IP** / 全局，且全部走
   原子的 `take()`（判完当场落账）。原先只按设备档记，而且用的是 `check()`
   —— 两个都错：`deviceId` 是客户端给的、换一个就绕过，
   而 `check` 不落账意味着并发下全过。
2. **邮箱存在与否 + 已确认与否，回话逐字相同**。
   匿名口**连 `emailMask` 与 `verifyAttempts` 都不回**
   （它们都是从「这个邮箱存在」推出来的）——
   这一条是**实测顶出来的**：第一版把掩码写进了公共分支，
   于是「存在」与「不存在」两个响应不再逐字相同。
3. 已确认的**不发信**（发一封「你的邮箱已确认」没有意义，还会让这颗键看起来永远有用）。
4. 冒烟口 `devVerifyToken` **只在登录态那条路**给 ——
   匿名口给的话它就成了「凭邮箱取确认令牌」的接口。

### 4.4.5-C 注册**不许**改掉已有账号的口令（账号接管洞）

原先 `register` 无条件把自己这次请求里的口令写进账号，理由写的是
「老账号（发码那条路建的）没有口令，要给它补上」。**那个理由只对没有口令的账号成立** ——
对有口令的账号，那一行就是一个**不需要任何凭据的账号接管洞**：

```
register("victim@example.com", "attacker-pw")
  → 库里那个账号的 password_hash 被换成攻击者的
  → 攻击者用自己那个口令登录成功，拿到受害者账号的会话与全部进度
```

实测现场（第廿六节 ②）：注册两次，第二次换个口令之后，
**新口令能登、原主人口令登不进去**。

现在的判据是两条：

| 账号形态 | 再注册时做什么 | 为什么 |
|---|---|---|
| **没有口令**（老行 / 只走随机码的人） | **补上口令** + 发确认邮件 | 那是「发码那条路建的账号」的迁移路径；回「已注册」等于邮箱枚举 |
| **已经有口令** | **一个字都不写**，回 `created:false` + `existing:true` | 口令不覆盖、**确认邮件也不重发**（否则它是个刷别人收件箱的口子） |

两情形回**同一个 HTTP 状态**（`200` / `202`），只在 `created` / `existing`
两个**给界面看**的字段上不同 —— 存在性仍然不泄露。

### 4.4.5-D 一次性的「只给令牌」入口：不猜、不扫表

`verifyEmail` 原先有一段「只给了 `token` 没给 `vid`」的兜底：
把**全表**拉出来、挑**第一条还没消费的**记录、拿它去过校验。那一段是错的：

- 令牌摘要里带 `uid`（`tokenHash(uid, purpose, token)`），而挑出来的记录是**任意一条**
  —— 「拿别人的记录、比自己的令牌」，**合法的确认链接会被判成无效**；
- 邮件里那条链接是**我们自己拼的**（`mail.link()` 两个参数都带），缺 `vid`
  只可能来自「手工拷贝漏了一段」或「有人在乱试」；
- 更要紧的是它是一次**全表扫描**，而入口是匿名的 —— 每个请求都能让别人付那份代价。

现在这两条都走 `E_NO_TOKEN`，与 `resetConfirm` 里那条 `if (!rid)` 逐字同源。

### 4.4.5-E 发信重试：**这一次请求内尽力，且如实回报**

用户问「如果用户收不到邮件，重试的机制如何设计？」。答案落在
`api/_lib/mail/index.js` 的 `withRetry`，四条一次说清：

| 项 | 口径 |
|---|---|
| 重试几次 | `MAIL_RETRY_MAX`（默认 2，**不含第一次** → 最多共 3 次尝试） |
| 隔多久 | 指数退避 + 抖动：第 1 次失败后 ~400ms，第 2 次 ~1200ms（±30%） |
| 总预算 | `MAIL_RETRY_BUDGET_MS`（默认 6000）—— 压在 Serverless 函数超时之前收手，免得「为了重试把注册请求拖成 504」 |
| **哪些错值得重试** | 只重试**可能自愈**的：网络层错误、`429`、`5xx` |
| **哪些绝不重试** | 其余 `4xx`：`401`/`403` 密钥不对、`400` 收件人被拒、`422` 域名未验证 —— 重试一万次也一样，只会烧光额度、把错因埋掉 |

**放弃了必须抛出去，不许改成「成功但 `delivered:false`」**——
这一条是想清楚了才写的：调用方判的正是这个异常
（`sendCode` 靠它回 502 `E_MAIL_FAIL` / `E_SMS_FAIL`；
`issueVerification` / `issueReset` 靠它把 `verifySent` 标成 false）。
改成「成功」的返回值，症状就是**发信彻底失败而接口回 2xx、界面写「已发出」** ——
比不做重试更糟。

**这不是一个后台补发队列。** Serverless 里没有常驻进程，
「过五分钟再试一次」需要一个真队列（Redis / 云任务），那是另一件事 ——
在它落地之前**不许假装有**。现在的承诺只有一句：
**这一次请求内尽力重试，且如实回报**。回报的形状是三件事：

```
verifySent:    false          ← 事实（不是「尽力了」）
verifyAttempts: 3             ← 试了几次
verifyReason:  "network"      ← 为什么没成（网络层 / http_5xx / …）
```

界面据此写「这台服务器试了 3 次都没发出去」，而不是含糊的一句「没能发出」——
后者让用户不知道该等一下还是该找运维。

**凭据的处置**：发信失败之后，确认 / 重设令牌**仍然在库里**（只有「送到」那一步没成）。
用户点「重新发一封」走的是一条**新凭据**的路（`issueVerification` / `issueReset`
会作废旧的那一条），而**不是**一个「补发上一条」的队列 ——
队列会让「哪一条还有效」变成谁也说不清的事，症状是「用户点开了三封里的旧那一封」。

### 4.4.6 重设口令必须吊销全部会话

这是**这一件事的一半含义**，不是可选的收尾：口令被换，说明原来那个
**可能已经泄露**，那么所有拿旧口令 / 旧会话进来的人都必须出去。
省掉它的下场是「用户改了密码，但偷到 Cookie 的人还在里面」——
而那恰恰是最需要改密码的那一种情形。

`resetConfirm` 一次做齐五件（少一件都是半截功能）：
① 令牌校验（形状 / 过期 / 重放 / 定长比较）→ ② 口令形状校验（与注册**同一处**
`checkPassword`，不是两套规则）→ ③ 写新摘要（新盐）→ ④ `revokeSessions(uid)`
→ ⑤ 从 `locked` 里解出来（能收到邮件、能点开、能填新口令，就是本人；
还锁着是自相矛盾）。

**两件刻意不做的事**：

- ❌ **不顺手确认邮箱** —— 收到重设邮件 ≠ 邮箱已确认。
  写成「收到了 ⇒ 一定确认过」在下一次「改主邮箱」时会出错，两件事各写各的。
- ❌ **不顺手解开 `suspended`** —— 只把 `pending` 提成 `active`**这一个方向**。
  顺手解开的后果是「封掉的账号点一下邮件就复活了」。

### 4.4.7 口令失败：计数落在**账号**上

| 项 | 值 | 为什么 |
|---|---|---|
| 判据 | **账号**（`uid`），不是设备 / IP | 撞库打的是**同一个账号**（一份泄露的口令表逐个试）；按 IP 计数拦不住分布式尝试 |
| 上限 | 连续 10 次 → `status='locked'` | 与 §5.5 的「锁 24 小时」同一形状 |
| 成功一次 | **把失败窗口清空** | 不清的下场是「错九次、对一次、再错一次 → 锁号」，而那个用户其实只错了一次 |
| 锁着的时候 | **对的口令也进不来**（423） | 锁是终态，不是「再试一次就好」 |
| 设备档 | `login` 桶另有 20 次/小时 的退避 | 两条一起：设备档是**退避**、锁号是**终态** |

**为什么失败窗口不能拿 `hits` 凑合**：`hits` 是单调累加的（只增不减），
拿它当失败计数就没有「清空」这件事。所以失败窗口有自己的一对表
（`fails` / `failWin` 语义），`limiter.fail()` / `limiter.fails()` / `limiter.clearFails()`。

### 4.4.8 客户端：一页四屏 + 两张独立页

| 落点 | 是什么 | 为什么在这儿 |
|---|---|---|
| `/login/` | **两个页签**（密码登录 / 快捷登录）+ 注册、忘记密码两屏支路 | 一页只有**一件主动作**（实心按钮），其余动作收成文字链 —— 上一轮被点名的「一页里三颗一样重的按钮」不许再出现 |
| `/verify/` | 确认邮箱（读 `?vid=&token=`） | 用户可能在**另一台设备**上点开邮件；挂在登录页上的话，点开链接只会落到一个空白登录页 |
| `/reset/` | 重设密码（读 `?rid=&token=`） | 同上 |

三张页都 `data-dock="off"`（做完就走），返回落点都指 `/login/`。

**一页四屏怎么保证「一次只有一件事」**：四个邮箱输入框分住在四个
互斥的 `[hidden]` pane 里（`display:none` 的那个不显示），
由 `LoginPage.setMode()` **一处**切换。`test/account-pages.test.js`
的第十一节从「数几个输入框」改成「**结构**上每个框都在自己的 pane 里」——
数字会随流程增减而变，结构不该变。

**URL 里的令牌**：`/verify/` 读出参数即 `history.replaceState` 抹掉
（进浏览器历史、被分享时带走、被截图带走，都是凭据泄露）；
`/reset/` 则**抹在提交成功之后** —— 那一页要等用户填完两次口令才发请求。
两处差异是刻意的。

### 4.4.9 【Issue #197 后半段】没确认就不让登录（推翻了本节的旧口径）

用户原话（2026-09-16，接在「重新设计整个登录流程」之后）：

> 「不确认就不让登录」

**这是一次口径推翻，不是补充。** 本节前一版（以及 `api/_routes/auth/register.js`
的文件头、`login/index.html` 的提示、`/terms/` 的条款）写的是
「**不确认也能用**，确认是为了将来能找回密码」。那一条现在**不成立**了。

#### 拦在哪两条路上，以及为什么必须是两条

| 路 | 拦点 | 不拦的下场 |
|---|---|---|
| 口令登录 `/api/login` | 口令校验**之后**、签发会话之前 | 注册时填了口令的人直接长驱直入 |
| 随机码登录 `/api/verify-code` | 码校验**之后**、签发会话之前 | 换成「快捷登录」那个页签就绕过去了 |

⚠️ **只拦其中一条 = 等于没拦，而界面上还写着「确认后才能登录」。**
这正是本项目反复出现的那个形状（限制写在 A 处、绕过在 B 处），
所以判据只写一处（`core.emailGate()`），两条路都读它，
`test/api.test.js` 第廿四节直接数「有几处读它」。

#### 判据为什么在**口令校验之后**

判在前面（一拿到账号就判）会把两种情形分成两种响应：

- 「这个邮箱注册过，但没确认」→ 403 `E_EMAIL_UNVERIFIED`
- 「这个邮箱压根不存在」→ 401 `E_LOGIN_FAIL`

两者一对比，**「谁是本站用户」就成了一件可以测出来的事**（邮箱枚举，
与 §4.4.5 那三条「不泄露」是同一条纪律）。判在后面就不一样了：
攻击者得**先猜中口令**才能撞到这道闸，而那时他本来就已经是账号主人了，
多说一句「去确认邮箱」不泄露任何他还不知道的东西。

#### 确认邮件成了**唯一的出路**，所以注册那条路必须发信

这条口径落下去之后，「注册完成但没点确认」这个中间态上的人
**什么也做不了**：登不进来，而「重发确认邮件」原来的入口在个人中心里
（个人中心要登录）。这是一个**用户自己造不出来的死结**。三条一起补：

1. **注册路径无条件发信** —— 只要邮箱还没确认就发（全新注册、老账号重新注册都发）；
   已确认的人不再发（他不是走不通，省一封垃圾邮件）。
2. **新增匿名重发口** `POST /api/resend-verification-by-email`。
   它是全站唯一一条「不登录也能让本站往外发信」的接口，因此带四条闸：
   频控四层 + 冷却（**冷却键独立命名空间**，见下）+ **存在与否回同一形状** +
   已确认的不发信。要登录那条 `resend-verification` **保留**（个人中心那颗键仍在）。
3. **登录页多一屏 `step-unverified`**：「口令对了/码也对了，但邮箱没确认」时
   整屏说清，并给一颗「重新发一封」。
   ⚠️ 它**不复用**注册完那一屏 —— 那边开头一句是「账号建好了」，
   对「回来登录但没确认」的人是一句错话。

#### 三处容易做错的细节（都实测过）

- **被拦时先把码消费掉，再判闸。** 反过来的话「没确认」的人每次都能拿
  同一枚码再试（码没消费），而且「确认完再回来填那枚码」也成了一条路 ——
  界面上就会写出「刚才那枚码还能用」这种不该有的承诺。
- **登录被拦时不顺手发确认信。** 发的话，任何人拿一个已知的未确认邮箱
  反复点「登录」就能给机主刷垃圾邮件。发信只允许由**用户自己的动作**触发。
- **匿名重发的冷却键不能与发码共用。** 共用（都是 `email|<邮箱>`）的后果：
  一个人刚用随机码发过码（完全正当），紧接着点「重新发一封」就被
  「发得太快了」挡回来 —— 而他在那一屏上**没有任何别的路**。
  频控的 device / ip / global 三档仍共用（防的是同一台设备狂刷，那是同一件事）。

#### 应急闸门 `REQUIRE_EMAIL_VERIFIED`（默认 **1**）

一个**针对发信商现状**的闸门，不是产品选项：

| 值 | 效果 | 什么时候用 |
|---|---|---|
| 缺省 / `1` | 拦 | **默认**。信发得出去，那封信就该有分量 |
| `0` | 不拦 | 只在 `MAIL_TRANSPORT=console`（信送不到真实收件箱）的实例上显式关掉 |

关掉时必须**看得见**：`/api/me` 的 `channel` 多两项（`emailGate` / `emailDeliverable`），
界面据它改口。四处跟着改：

- 注册完那一屏：说「这台服务器现在**没有**拦「邮箱没确认」」（而不是「去收件箱」）
- 口令登录：不再回 403
- 个人中心那一行：说「这台服务器没有拦确认，确认只影响找回密码」
- `/verify/` 确认成功那一屏：不说「现在可以去登录了」（他本来就能登）

⚠️ 这两项**不参与判权**（真闸在服务端），只是如实自报 ——
与 `channel.mail` / `channel.db` 完全同一条纪律。

#### 与「忘记密码」的交界：一条必须说出来的死角

「重设口令」**不动** `email_verified_at`（§4.4.6 那条「两件事各写各的」），
所以一个**没确认过**的人可以走完整套「忘记密码」流程
（收信 → 点链接 → 填新口令 → 看到「请用新密码重新登录」），
然后回去一登 —— **403**。他会以为新口令没生效，于是再来一遍。

处理方式是**如实说出还有一步**，而不是顺手把确认状态改掉：

- `POST /api/reset-confirm` 的响应多一个 `emailVerified`，且 `note`
  在未确认时改写成「**但这个邮箱还没确认，暂时登录不了** ——
  请到登录页点「重新发一封确认邮件」…」
- `/reset/` 成功那一屏按它显示一条 warn 提示（`#reset-ok-hint`）

⚠️ 为什么不「反正他能收到重设邮件，就顺手算他确认了」：
那样一来「确认」这件事就不再是「点过那封确认邮件」的凭据，
而是「能收到本站任意一封信」的同义词 —— 下一次改主邮箱时就会出错
（那正是 §4.4.6 里注的那一处）。

#### 老账号（这条口径之前建的）怎么办

它们 `email_verified_at` 为空 → 按同一口径**拦**。出路与新账号完全一样
（匿名重发 → 点链接 → 进来），不需要「迁移脚本」也不需要「宽限期」：
宽限期正是那种「写着会过期、实际上没人去改」的临时措施。

### 4.4.10 管理后台：两张名单**不是一张表**

| | 「服务端名单」（§3.5 · 2.2） | 「全部账号」（Issue #197） |
|---|---|---|
| 接口 | `POST /api/admin/grants` | `POST /api/admin/accounts` |
| 是什么 | **台账**：发过什么 | **名录**：都有谁 |
| 列出 | `plan !== free` | **全部**（除 deleted） |
| 邮箱 | **只回掩码** | **回明文** —— 那是它存在的理由 |
| 给的操作 | 改层级 | **只读**（发放仍按掩码在上面那张表上做） |

用户原话「我还是要看到这些用户」—— 而掩码 `a***@qq.com` **认不出是谁**。
所以那张需要「认人」的表必须回明文（这也正是 `accounts.email` 落库的第二个理由）。

四条边界（`core.adminAccounts` 里逐条写着）：
① 角色闸在服务端（不是 owner / admin 一律 403，界面上藏入口不是安全边界）
② **绝不回** `password_hash` / `password_salt`
③ **绝不回** `email_hash`（泄出去等于把「这个人是不是本站用户」变成可查询的事实）
④ 不回进度 / 会话 / 确认令牌

**登记的能力**：`Issue #197` 没有引入任何新的权益能力 ——
注册、确认、登录、忘记密码、重设都是**所有人**都有的基本功能。
口令与随机码也不是「两条能力」：它们只是同一件事（拿到会话）的两条路。

### 4.4.12 【Issue #197 后续】人机校验：Cloudflare Turnstile

用户原话（2026-09-17）：

> 「用户登录，注册，密码找回，密码，发送随机码重置等页面添加 Cloudflare
> Turnstile 支持，并且说明在文档中 Cloudflare Turnstile 的配置步骤」

#### 为什么是 Turnstile，而不是图形验证码 / 滑块

三件与本站既有口径对得上的事：

1. **不花钱、不备案也能跑**（§1 第 1 条）。Turnstile 免费档
   **每月 100 万次**校验，对本站来说是「用不完」。
2. **不打断真用户**。它默认**不弹**任何需要点的东西（无感校验），
   只有判不准时才出一小块勾选框 —— 图形验证码那种「看图选字」
   对一个面向小朋友的背诗应用是明确的伤害。
3. **不需要自己实现服务端**。一根 siteverify 的往返（§4.4.12 下详），
   而不是自己维护一套「难 / 中 / 易」的题库 + 图片服务。

#### 它挡在哪儿：四条匿名可写的口子（**清单只写一处**）

| 挂闸 | 为什么 |
|---|---|
| `POST /api/send-code` | 匿名可调、**会发信**。刷子拿它当免费的邮件炮台 |
| `POST /api/register` | 匿名可调、**会建号 + 会发信** |
| `POST /api/reset-request` | 匿名可调、**会往任意邮箱发信** |
| `POST /api/resend-verification`（含匿名那条） | 全站唯一「不登录也能让本站往外发信」的接口 |

**不挂**的几条，理由是「它们本来就有凭据」：

| 不挂 | 为什么 |
|---|---|
| `POST /api/login` | 口令得**猜中**才能过；加人机校验只是多打扰真用户 |
| `POST /api/verify-code` | 同上，随机码得猜中 |
| `POST /api/reset-confirm` | 用户是**点邮件里那条链接**进来的，那一步已证明邮箱可达 |
| `POST /api/verify-email` | 同上 |

⚠️ **加在哪几条、用什么顺序，只写在 `core.humanGuard()` 一个函数里**。
把 `turnstile.guard(...)` 抄进四个函数开头也能跑，但那样就有四处
「要不要校验」的判断 —— 将来改一处（比如加「登录态的人免校验」），
就会出现「三条接口改了、第一条没改」，而**没改的那一条会静默地不校验**。

#### 顺序：**先人机校验、后频控**

两个都要，而且顺序是刻意的：**被 Turnstile 挡掉的那一次不占频控额度**。
反过来（先频控）的下场是刷子可以用无效 token 把「一小时 5 封」那本账刷满，
于是**真正的用户被挤掉** —— 一种不需要猜口令就能做的 DoS。

#### 三条口径

1. **默认关**（`TURNSTILE_ENABLED` 缺省 `0`）。理由与 `SMS_ENABLED` 逐字同源：
   没配好密钥时打开它 = **谁也别想登录**。开关是给运维的，不是给代码猜的。
2. **没配就如实降级，不假装拦着**。`turnstileReady(cfg)` 为 false 时服务端
   **跳过**校验，并把这件事自报在 `/api/me` 的 `channel.turnstile` 与
   `/api/config` 的 `turnstile.enabled` 里 —— 与 `mail: "console"`
   「真实用户收不到信」是同一种「如实说这台服务器的状态」。
3. **失败一律 400 + `E_TURNSTILE`**，且**不回 Cloudflare 的 `error-codes`**
   （那些码会把「密钥配错了」这类服务端配置问题暴露给调用方）。
   只进服务端日志（`api.turnstile_blocked`，经 `redact`）。

#### 两处判据必须只写一份

- `api/_lib/turnstile.js` 的 `turnstileReady(cfg)` —— 「开关 + 密钥 + 非旁路」
  三个条件。写成让调用方各自 `if (cfg.x && cfg.y)` 的形状，
  漏一处就是「那个接口不校验」而谁也不报错。
- `core.humanGuard(deps, input)` —— 挂载点与顺序。

#### fail-closed：连不上 Cloudflare 时**不放行**

这一条是刻意选的**难那一侧**：

| 选择 | 后果 |
|---|---|
| fail-open（连不上就放行） | **拔网线 = 绕过人机校验**，而且没有任何紧急开关能补救一个已经被刷穿的窗口 |
| **fail-closed（连不上就拒）** | Cloudflare 抖动时登录短暂不可用 —— 但这一层本来就是**可关的应急闸**（`TURNSTILE_ENABLED=0` 一行就绕开） |

⚠️ 但**没配密钥**那一档**不是**网络失败：那是运维明示的「这台没开」，
走 `skipped`（**不拦**）。两件事不许混为一谈 ——
把「没配」按 fail-closed 处理，等于在一个没人机校验的实例上用一句假话锁门。

#### hostname 校验

核过的 token 必须属于**本站**（防「拿别人站点的 token 来糊弄我们」）：
响应里的 `hostname` 与 `cfg.siteUrl` 的 host 比一次，对不上按拒绝处理。

#### 前端那半边（`js/turnstile.js`）：只在「省一次请求」，不判安全

| 前端做 | 前端**不**做 |
|---|---|
| 渲染 widget、把 token 交给 `js/auth-api.js` | 判「校验过没过」—— 那在服务端 |
| 提交前 `gate()` 拦一下（省一次必然失败的请求） | 自己拼 siteKey（由 `/api/config` 下发） |
| 提交后 `reset()`（token 一次性） | 在没配的实例上拦用户（那等于用假话锁门） |

⚠️ **没配时一个字节都不发给 Cloudflare**：不渲染 widget、连它的脚本都不加载，
页面上的挂载点一直是 `hidden` —— 绝不摆一个空壳让人以为「本站有人机校验」。

#### 配置步骤（与 `npm run doctor -- --steps` 第 F 步同一份数据）

⚠️ 这一节的文字与 `api/_lib/ops.js` 的 `STEPS`（第 F 步）是**同一件事的两种呈现**，
改一处要改两处；「哪几个变量、缺了会怎样」的**权威**在 `ENTRY` / `check()` 里。

1. **Cloudflare 控制台 → Turnstile → Add site** → 填本站域名（`kuibu.app` 那种，
   **不带** `https://`）→ Create
2. 建完那一页给你**两个 key**，它们是一对，**缺一个都跑不起来**：
   - **Site Key** —— 公开值，由 `/api/config` 下发给浏览器渲染 widget
   - **Secret Key** —— 保密，只在服务端核 token 时用
3. **托管平台**（Vercel / CNB / 自建 → 项目 → Settings → Environment Variables）
   建**三个**：

   ```
   TURNSTILE_ENABLED    = 1                                   # 开关（默认 0/关）
   TURNSTILE_SITE_KEY   = 0x4AAAAAAA...                        # 上面那一对里的 Site Key
   TURNSTILE_SECRET_KEY = 0x4AAAAAAA...                        # 上面那一对里的 Secret Key
   ```

   ⚠️ **填在托管平台的环境变量里，不是 Cloudflare、也不是 Supabase。**
   理由与「Resend 密钥填哪」逐字同源（README 那一节写得很细）：
   Cloudflare 那边只是「允许你用它的服务」，锁在**跑着本站服务端的那台机器**上。
4. **重新部署一次** —— 环境变量**只在新部署里生效**，光改不重新部署 = 没改
5. **回来验**（四条，每条一个明确结论）：
   - `curl -sS "$SITE_URL/api/config"` → `{"turnstile":{"enabled":true,"siteKey":"0x…"}}`
   - 打开 `/login/`，密码那一屏下方应当出现 Cloudflare 的方框
   - 故意不勾就点「注册」→ 前端就地提示「请先完成人机校验」，**不发请求**
   - 把 widget 删掉再点（模拟绕过前端）→ 服务端回 `400 E_TURNSTILE`
     —— **这一条才证明闸在服务端**

⚠️ 三条容易踩的：

- **两个 key 是一对**：只填 Site Key（前端渲染了）而缺 Secret Key，
  服务端 `turnstileReady()` 为 false → **跳过校验**（看着像开着，实际没拦）；
  只填 Secret Key 而缺 Site Key，前端不渲染 → **每次登录都被服务端拒**。
  `npm run doctor` 的 notes 会把这两档分别点破。
- **本地开发 / CI** 不想真接 Cloudflare，用 `TURNSTILE_BYPASS=1`。
  它**只在服务端读**、**绝不随任何响应下发**，所以生产开着它时客户端无从察觉
  —— 也正因如此，`npm run doctor` 会为它单独喊一条警告。
- **widget 要允许本站域名**：Cloudflare 那边 Add site 时填的域名与
  实际访问的域名不一致时，widget 会渲染失败（浏览器控制台看得见）。

## 5. 随机码规则（安全核心）

### 5.1 码的形态

| 项 | 值 | 理由 |
|---|---|---|
| 字符集 | `0-9`（纯数字） | 邮箱里好认好输，无 O/0 混淆 |
| 长度 | **6 位** | 10^6；配合 §6.2 频控足够 |
| 有效期 | **10 分钟** | 够慢手用户；比常见的 5 分钟宽松一点 |
| 使用次数 | **1 次**（成功即失效） | 防重放 |
| 校验失败上限 | **5 次** | 之后该码作废，必须重发 |
| 比较方式 | 定长比较 + 失败也走完循环 | 防时序侧信道（服务端实现要求） |

### 5.2 用途绑定 purpose（同码不同用，互不通用）

```js
PURPOSE = {
  login:  "登录 / 注册",     // 双方共用一个 purpose
  reset:  "重设凭证"         // 本期无密码，等价于"吊销全部会话 + 清设备信任"
}
```

**`login` 的码不能用于 `reset`，反之亦然**。将来加 `bind`（绑定新邮箱/手机号）时同样独立。

### 5.3 码记录（落盘形态）

```jsonc
// poem_auth_v1.codes[<codeId>]
{
  "codeId": "c_7f2a…",           // 随机，不是码本身
  "uid": "u_8f3k2m9q",
  "purpose": "login",
  "channel": "email",
  "sentTo": "a***@b.com",        // 掩码，用于界面回显"已发往"
  "codeHash": "…",               // 见 5.4
  "salt": "…",
  "issuedAt": 1757900000000,
  "expiresAt": 1757900600000,
  "attempts": 0,
  "consumedAt": null
}
```

同一 `uid + purpose` 同时**只保留最新一枚**（发新的即作废旧记录）。

### 5.4 不允许存明文码

- 存储层只留 `codeHash = SHA-256(uid + purpose + code + salt)`（`salt` 每码随机 16 字节）
- 用户输入时同样按此公式现算比对
- **服务端版强制要求**：任何日志、错误上报、监控里**禁止出现明文码**（写进 review checklist）
- 明文码只在两处短暂存在：① 生成它的那一次函数调用内；② 用户的邮箱里
- **`ALLOW_CODE_ECHO` 那条冒烟口子必须跟着「真送出去了」才作数。**
  它唯一的用途是本地联调与 CI 里取码，而这两个环境恰恰是「发信商时通时不通」
  的地方。原先 `sendCode` 的 `catch` 把中转那一条响应原样回了出去 ——
  于是**发信一失败，明文码就跟着 5xx 回给了调用方**。
  现在的判据是一个只在 `sendVia` 真回来之后才置真的 `echoAllowed`：
  异常路径、发信失败路径都不带 `devCode`。
  这条钉进了 `test/api.test.js` 第二十三节（④）。
- **id 生成不许写成「撞了就重摇」**。`codeId` / `uid` / `sid` 一律走
  「随机取一次 + 确定性线性探测」，步数上限明确。写成
  `do { x = rand() } while (撞了)` 的版本在随机源退化时是**死循环** ——
  实测的现场表现是：第一次发码正常，第二次调用整个线程卡死、不报任何错。
  这条已钉进测试（`test/auth.test.js` 第十二节）。

### 5.5 阶梯锁定（防暴力猜 6 位）

| 连续失败 | 处理 |
|---|---|
| 1~4 次 | 提示剩余次数 |
| 第 5 次（该码） | **该码立即作废**，必须重发，同时记「1 轮失败」 |
| 单账号当日发码 > 10 次 | **锁 1 小时**（`lockedUntil`） |
| 单账号连续 3 轮「发码后一次都没对」 | **锁 24 小时** |
| 全局异常（服务端版） | 单 IP / 单设备阈值触发人机校验（§11 三期） |

> ⚠️ 这条是**实测修正过的**。最初写的是「累计错 3 次就锁 24 小时」，
> 写进测试才发现它同时满足两个条件、结果反了：单枚码本身就能错 5 次，
> 正常用户手抖三次就被锁一天；而手改 localStorage 清掉计数又能立刻重来。
> 现在的判定对象是**「整轮失败」**（发一枚码 → 一次都没对 → 才算一轮），
> 既不会误伤正常用户，也不会被单枚码的 5 次重试放大成 5 倍机会。

锁定与失败计数**只认 uid，不认邮箱字符串**（防止大小写/别名绕过）。

**服务端这一半直到 Issue #197 才真的落地。** 上面这张表从 1A 期起就写着
「单账号连续 3 轮 → 锁 24 小时」，而 `api/_lib/core.js` 里**从来没有实现它** ——
`verifyCode` 只判「**这一枚码**错了几次」（`codeMaxAttempts`），
换一枚码就重新从 5 次数起。实测（`test/api.test.js` 第二十三节）：
一个坏客户端对同一个邮箱连着发码、每枚码错 5 次，可以**无限**进行下去。
所以这句话以前是**文档跑在代码前面**，现在两端对齐了：

| 项 | 服务端落点 |
|---|---|
| 「1 轮」的判据 | 一枚码**刚好被第 5 次错误作废**那一刻记一轮（语义判据，不看时钟） |
| 轮数 | `limiter._hits["wrong\|<uid>"]` 的长度 |
| 上限 / 锁多久 | `WRONG_ROUNDS_LIMIT`（默认 3）/ `ACCOUNT_LOCK_MS`（默认 24h） |
| 「锁」写在哪 | `accounts.status = "locked"` + `accounts.locked_until` |
| 谁读它 | `sendCode` 开头那一条（还在锁里 → 423 带 `retryAfter`；**已过期 → 当场解锁**） |
| 出口 IP | `WRONG.ip` 那一档，判据是 `轮数上限 × 单码上限` 次错误（挡住「换小号猜」） |

> ⚠️ **锁必须会到期**。原先代码里那条 `if (acc.status === "locked") → 423`
> 是**只读不写**的：没有任何一处会把 `status` 写成 `"locked"`，
> 于是它既是死代码，又给后来的人一个错觉「锁定已经做好了」。
> 现在写进去了，就必须同时写**解锁**（`locked_until` 到期即改回 `active`
> 并清掉轮数账）—— 否则「锁 24 小时」会变成「锁一辈子」，
> 而界面上写的还是「1 小时后再试」。

**频控的账本只有一个，而且必须是原子的。** 服务端的频控器是**进程内**的
（`makeRateLimiter`），它的正确用法是 `take()`（判完当场落账），
**不是** `check()` 之后再找地方 `hit()` —— 后者中间隔着发信商那次真实的
网络往返，并发打进来时每一条请求都在空窗口上通过（实测：连点两次重发，
第二次也放行）。同一条纪律也覆盖**所有被拒的走法**：码长不对、
码过期、码已用这些早退路径**都要落账**，否则那道闸只是个建议。

> ⚠️ 多实例下这本账是**尽力而为**的，接口如实自报：
> `/api/me` 的 `channel.rate === "instance"`。要跨实例必须把窗口搬到
> 共享存储，那是另一件事；在它落地之前，界面不许把「次数有限」说得比事实更硬。

## 6. 频控、防滥用与隐私

### 6.1 邮箱不在**本机**落明文（服务端口径见 §4.4.2）

> ⚠️ **口径已被 §4.4.2 部分推翻**：Issue #197 起，**服务端**的 `accounts.email`
> 确实是明文（用户裁决「要求用户邮箱必须记录到数据库」）。
> 本节剩下的是**本机那一半**（`js/auth-core.js` 的 `poem_auth_v1`）——
> 本机存储仍然只存摘要 + 掩码，那一条没变。



本机模式下数据不出设备，但浏览器数据可能被导出备份、被同机他人看到。
因此账号记录里只存：

```
emailHash = SHA-256(normalized(email) + PEPPER)   // 用于查重与登录比对
emailMask = "a***@b.com"                          // 用于界面回显
```

- `PEPPER` 本机随机生成一次，存 `poem_auth_v1.pepper`，**不导出**（导出备份里剔除）
- 换句话说：拿到备份文件也**还原不出完整邮箱**，但换个设备无法用同一份账号数据登录 ——
  这是刻意的取舍：本机模式不追求跨设备，跨设备要等三期有服务端

### 6.2 三层频控（每层独立计时，**取最严**）

| 层 | 键（哈希后） | 限制 |
|---|---|---|
| 邮箱 | `identityHash` | **重发冷却 60 秒**；1 小时 5 次；24 小时 10 次 |
| 设备 | `deviceId`（随机 UUID，存本机，**非指纹**） | 1 小时 10 次；24 小时 30 次 |
| 出口 IP（**服务端版**） | `x-forwarded-for` 第一段 | 1 小时 30 次；24 小时 100 次 |
| 全局 | 常量 | 1 小时 20 次；24 小时 60 次（本机模式兜底） |

> ⚠️ **服务端版的四层里有三层要看「调用方是谁」，而这件事只有 IP 改不动**。
> `deviceId` 是**客户端自己给的**（`x-kb-device` 头或请求体），
> 每天换一个就绕过了设备档；邮箱更是攻击者自己挑的。
> 所以 `/api/verify-code` 与 `/api/send-code` 都必须把 IP 传给内核
> （`api/_routes/verify-code.js` 里那一行 `ip: d.ip` 就是它）——
> 漏传的后果不是报错，而是**那一档永远落在 `"unknown"` 这一个桶里**：
> 桶被刷满时**所有用户一起被拒**（DoS），而真正的攻击者换个网络就走了。

**校验口（`/api/verify-code`）的闸与发码口不是同一组**，各管各的：

| 闸 | 挡的是什么 | 落点 |
|---|---|---|
| 设备档（`verify:<deviceId>`） | 一台机器猛试 | `E_RATE_DEVICE` 429 |
| IP 档（`verify:<ip>`） | 一个网络猛试 | `E_RATE_IP` 429 |
| 该码的 5 次（`codes.attempts`） | 单枚码被猜 | `E_CODE_WRONG` → `E_CODE_VOID` |
| 账号的连续失败轮数 | **换着码猜**（§5.5） | `E_LOCKED` 423 |
| 出口 IP 的猜错次数 | **换小号猜** | `E_RATE_IP` 429 |

> ⚠️ 判据分开的另一个原因：**正常用户的请求也会落进 IP 档**。
> 如果「猜错计数」与「限流」共用一本账，一个共享出口（学校机房、
> 运营商 CGNAT）里的几十个用户会互相把对方的额度吃满，
> 而真正的猜错计数看起来还很宽松。

倒计时期间按钮置灰并显示「还需等待 47 秒」。

> 注意「60 秒冷却」与「频控档位」是两件事：前者只管「同一枚码别连点」，
> 后者管「这段窗口里一共要了几枚」。把冷却也算进频控档位，
> 会让「正常的三次重发」被误判成刷量 —— 这也是实测改过来的。
**`deviceId` 是随机生成的本地值，不采集 UA/屏幕/字体等任何指纹特征** —— 与 `/privacy/` 的
「不采集设备标识」承诺保持一致（这句承诺本身要不要改，见 §12）。

### 6.3 设备信任期（减少重复收信）

- 登录成功后，本机记 `trustedUntil = now + 30 天`
- 信任期内打开 `/login/`，顶部直接给「继续以 a***@b.com 进入」，**一点即入，不发码**
- 但**每次登录都写 `lastLoginAt`**，且会话过期后必须重新收码（信任期不等于永久会话）
- 提供「退出并取消信任本设备」，以及设置页「退出全部设备」（本期等价于清本机会话）

### 6.4 会话规则

| 项 | 值 |
|---|---|
| 有效期 | 30 天 |
| 续期 | 剩余 < 15 天且用户有操作时静默续到 30 天 |
| **续期不许写成「每次登录都签新的」** | 见下 |

> ⚠️ **服务端这一条也翻过一次车（Issue #197）。**
> 设计里那句「剩余 < 15 天时静默续到 30 天」是**有条件的**，
> 而 `api/_routes/verify-code.js` 原先做的是「每一次登录都签一枚新 Cookie」——
> 那等于**无上限的滑动窗口**：用户只要别空过 30 天，
> 这一枚会话就能活 60 天、90 天、无限期，而库里那一行 `sessions`
> 的 `exp` 还停在最初那一刻（续期从不落库）。
> 判据现在收在 `session.shouldRenew()` 一处：
> **剩余不足一半**才续（`(exp - now) < sessionDays/2` ——
> 不写死 15 天，因为 `sessionDays` 改成 7 时「写死 15 天」会让每一次请求都续期，
> 又滑回去）；不该续时**不发 `Set-Cookie`**，浏览器手里那一枚原封不动，
> 响应里多一个 `sessionKept:true` 让界面与测试都看得出这一次是沿用。
| 存储位置 | `localStorage`（本期无服务端，HttpOnly Cookie 无意义） |
| 会话内容 | `{sid, uid, scope, iat, exp, nonce}`，**不含邮箱**；`sid` 唯一性同上 |
| 退出 | 清会话 + 清 `pending`；**不动任何进度数据** |
| 注销账号 | 二次确认 + 要求重输一次邮箱 → 清账号、会话、信任期；进度数据单独询问是否一并清空 |

> 服务端版必须改为 `HttpOnly + Secure + SameSite=Lax` 的加密 Cookie，
> **禁止用 localStorage 存长寿命 token**。本期是例外，因为它只能在用户自己机器上自我验证。

### 6.5 一次性邮箱（临时邮箱）

- 维护一份「常见一次性邮箱域名前缀表」（如 `mailinator`、`10minutemail`、`guerrillamail` 等）
- 命中时**只在发送前给一句提示**：「临时邮箱收不到后续邮件，可能丢失账号，确定继续？」
- **不阻断**：挡住的是真用户，挡不住有心人，而收益是负的
- 表本身放 `js/auth-core.js`，可由测试替换（不联网）

## 7. 【关键】本期没有后端，码怎么送到用户手里

这是这份设计里唯一"将就"的地方，必须说清楚，不能含糊。

### 7.1 本期的做法：本地发码 + 用户自送（明确标注为「本地体验版」）

1. 前端生成码，存哈希到本机
2. 点击「发送随机码」→ 界面弹出一个本地对话框，内含：
   - 复制按钮：把码复制到剪贴板
   - `mailto:` 按钮：打开用户自己的邮箱客户端，主题/正文预填「【跬步】登录码 XXXXXX」
   - **明文提示**：「当前为本地体验版：本应用没有服务器，码由你自己保管。
     真机上请勿把码发给他人。」
3. 用户回填即可登录

**它不比「输两次邮箱」更安全，也不比它更不安全** —— 因为它本来就是本机自证。
所以**绝不能把它宣传成"邮件认证已经做好了"**。

### 7.2 服务端版（**1A 期已落地**，接口见下）

> ✅ **已实现**（2026-09-15）。落地时路径从设计里的 `/auth/*` 改成 `/api/*` ——
> Vercel Serverless 的目录约定就是 `api/`，用 `/auth/*` 要多配一层 rewrite，
> 而 rewrite 会让「哪个文件对应哪个接口」变得不可见。六个接口的实现在
> `api/_routes/{send-code,verify-code,me,account}.js` 与 `api/_routes/sync/{pull,push}.js`
> （Issue #205 之后实现都在 `_routes/` 下，线上由 `api/handler.js` 一个固定函数收口 ——
> `vercel.json` 用 `__path` 传原路径；目录兜底与动态 catch-all 都曾在线上全站 404，
> 见 `docs/architecture.md` §2.2.1.1），
> 业务内核全在 `api/_lib/core.js`（这样才写得了测试），
> 客户端的 `transport` 是 `js/auth-api.js`。
> 上面「本期的做法」（本地发码 + 用户自送）**保留为降级路径**：
> 服务端没配好 / 连不上 / 断网时自动回落，界面如实标注「本机体验版」。

```
POST   /api/send-code   {email, purpose, deviceId}   → 202 {codeId, expiresAt, cooldown, transport, delivered, store}
POST   /api/verify-code {codeId, code, deviceId}     → 200 {account} + Set-Cookie: kbsid=...
                                                       400/423 {code, message, remaining?, retryAfter?}
GET    /api/me                                        → 200 {uid, nickname, plan:{tier,until}, features[], mask,
                                                            channel:{mail,delivered,db,sms}}   ← 2C 补的开通状态
                                                       401 {code:"E_NO_SESSION"}
POST   /api/sync/pull   {since, deviceId}            → 200 {recs[], serverTime}
POST   /api/sync/push   {recs[], deviceId}           → 200 {applied, conflicts[], serverTime}
DELETE /api/account     {confirm:true, deviceId}     → 200 {deleted, export, note} + 清 Cookie
```

**与设计原稿的三处差异**（都是实测顶出来的）：

1. **`/auth/*` → `/api/*`**，理由见上（Vercel 目录约定；少一层 rewrite 就少一层不可见映射）
2. **注销不返回 `exportUrl`** —— 本期没有对象存储放导出文件。
   数据**直接随响应回**，用户自己存。假装有个下载链接比不做更糟。
3. **退出登录没有单独接口** —— 会话是签名 Cookie，前端清 Cookie 即可；
   服务端那条 `revokeSessions` 只在「注销」与「重设凭证」时用（那两件才需要真正吊销）。
   `/api/session` 那条设计里写了但 1A 没建：它会是一个「删了也不影响任何断言」
   的接口，而「无害的冗余接口」正是之后会被误用的那一类。

同一套状态机与错误码（§13），客户端只换 `transport` 实现。

> **2C 补：`/api/me` 如实自报开通状态。**
> 界面在说「由服务器判定」时，得让用户看得见**这台服务器是什么状态**：
> `channel: { mail:"sendgrid"|"console", delivered, db:"db"|"memory", sms }`。
> 三个字段全是事实，且全部取自既有判定（`cfg.mail()` / `cfg.hasDb()`），不另算一份。
> 客户端**收下但不落盘、不参与判权**（`AccountApi.channel()`）——
> 缓存一份必然与服务端真实状态漂移。
> 未登录时 `/api/me` 仍是 401，**不下发任何开通状态**。
> 开通到哪一步、缺哪个变量、怎么补：`npm run doctor`（§7.3）。

### 7.3 配置怎么核对：可执行的自检（2C）

「接服务端」这一步的配置项有 13 个，散在会话 / 数据库 / 发信 / 短信 / 冒烟五组里。
自检把「缺哪个、缺了会怎样、怎么补」一次说清，**且不部署就能问**：

```
npm run doctor                 # 人看的一段文字（可直接贴进 Issue）
npm run doctor -- --json       # 程序看的形状；退出码 = 体检结论
npm run env:example > .env.example   # 生成可直接粘贴的模板（唯一来源）
```

三档分得清：**必须**（`SESSION_SECRET`、Supabase 那一对）／
**这一件需要**（发信商密钥）／**可选**。
**一个都不配也照样能完全离线使用** —— 自检把这句话写在报告里，
免得「未配置」被读成「坏掉」。

清单定义在 `api/_lib/ops.js` 的 `ENTRY` 里，**自检与 `.env.example` 读的是同一份** ——
手抄的清单必然与代码分叉，而本项目里这种分叉已经出现过好几次。

### 8.2 「没开通」时会发生什么（这是 2B 的核心口径）

```
POST /api/send-code  { channel:"sms", value:"13800138000" }
  → 503  { code:"E_SMS_NOT_OPEN", message:"短信登录还没开通（需要先签短信商并完成模板报备）…" }
```

三条不能退让的：

1. **如实拒，不假装** —— 没有真短信商时**绝不走 console 兜底把它「成功」掉**。
   一条永远收不到的短信 + 一个「已发送」提示 = 骗人（§12 总原则）。
2. **不做副作用** —— 拒在归一化之后、落库之前：**不创建账号、不写一条码记录**。
   否则「试一下短信登录」会在库里留下一串孤儿账号。
3. **不偷偷降级** —— 界面收到 `E_SMS_NOT_OPEN` **不许**像 `E_OFFLINE` 那样切回
   「本机体验版」（本机版同样发不出短信，切过去只是换个说法）。
   `js/auth-api.js` 的 `TRANSPORT_ERR` 里它有一条**独立**文案，且不在回落名单里。

> ⚠️ `SMS_ENABLED=1` 只是「允许尝试」，**不等于能发**。
> 真正能发还要求 `SMS_TRANSPORT` 指向一个已实现的短信商；
> 只开开关不接商，请求**仍然**是 503。

## 9. 【关键】登录时本机已有进度怎么办

这是最容易出事故的地方。规则如下（`mergePolicy`）：

| 场景 | 处理 | 理由 |
|---|---|---|
| A. 本机进度为空，账号有数据 | 拉账号数据覆盖本机 | 新设备首次登录 |
| B. 本机有进度，账号为空（新注册） | **把本机进度"认领"进账号** | 否则用户一注册就丢光数据，最恶劣的体验 |
| C. 两边都有，且是同一账号同一设备 | 按 `id` 逐条取「复习次数多 / `nextReviewAt` 更晚」者 | 打卡要单调，不能因为同步回退 |
| D. 两边都有，但无法判断来源 | **不自动合并**，弹选择：「保留本机 / 保留账号 / 先导出再决定」（**已由用户裁决确认**，细则见 §12.3） | 宁可不合并，也不静默覆盖 |
| E. 用户在 A 设备登录了 B 的账号 | 提示「本机有另一份进度（3 首诗）」，需显式选择 | 家庭共用一台设备很常见 |

**只读页面绝不可触发任何合并或写盘**（现有测试已守这条，新增用例继续守）。

合并的粒度只到「进度记录 + 昵称 + 账号域设置」，**设备偏好一律不同步**
（字号、注音档、连读档、播放模式、iOS 引导条已关）。

**账号域 = `grade` / `term` / `scope` / `dailyCount` / `algo` + `username`**
（用户已于 2026-09-15 裁决，见 §12.2），
**设备域 = `helper` / 字号 / 对齐 / 连读档 / 播放模式 / iOS 引导条已关**。
这条口径沿用 Issue #132 阶段 0 的裁定，并且它决定了「阶段 0 必须把
`poem_recite_settings_v1` 按字段拆家」是硬需求而不是优化项。

## 10. 异常与边界（逐条可测）

| 场景 | 期望行为 |
|---|---|
| 邮箱格式错 | 就地提示，不进入 `emailEntered`，不计入失败次数 |
| 邮箱带空格/大写/零宽字符 | 归一化后视为同一邮箱 |
| 连续点「发送随机码」 | 第 2 次起按钮置灰 + 倒计时，**不发新码** |
| 收到两封码，用旧码 | 拒绝（旧码已作废），提示「请用最新一封」 |
| 码过期后再输 | 明确区分「已过期」与「码错误」，过期可直接重发 |
| 输错 5 次 | 该码作废，必须重发；界面不透露"还剩几次"以外的信息 |
| 关掉页面再回来 | 从 `pending` 恢复，倒计时继续走 |
| 系统时间被改早/改晚 | 以 `issuedAt` 单调时钟为准；检测到时间倒退则**直接作废全部码** |
| 存储被写脏（手改 localStorage） | 全部字段做运行时校验，非法值回落默认，不抛异常 |
| localStorage 不可用（隐私模式） | 降级为「内存会话」，本次可用、刷新即退；给出说明 |
| 存储写满（QuotaExceeded） | 捕获、提示、不丢当前输入；会话优先于日志 |
| 用户注销 | 二次确认 + 重输邮箱确认；进度数据单独确认 |
| 会话过期 | 静默降级为 local 模式，**绝不弹窗打断背诵** |
| 备份导入含账号字段 | 忽略 `plan` / `security` / `identities` 的可疑字段（§2.2 硬约束） |

## 12. 合规：用户已裁决的三件事（2026-09-15）

> **总原则（用户原话）**：「用户协议和隐私条款永远遵从于代码的实际情况，
> 代码改了相应内容当然要跟着改。」
> 因此条款的修订**不跟路线图走、也不跟"将来会不会接服务端"走，只跟当前代码走**：
> 代码里实现了什么，条款就写什么；代码没实现的事，条款一个字都不许提前透露。

### 12.1 裁决一：`/privacy/` 的「不上传、不云同步 / 无注册无登录」

**裁决：现在就改，不等接服务端。**

做法（已随本次一并落地）：

| 今天的写法 | 改成 | 依据 |
|---|---|---|
| 「不需要注册」 | 「**不需要注册也能用全部功能**；也可选填邮箱建一个**只存在本机的账号**」 | 代码里有 `AuthCore` 的 local/code 模式（本机落盘），但没有服务端 |
| 「不上传、不云同步」 | 「**不上传、不云同步**：目前没有任何服务器，全部数据（含账号记录）只在本机」 | 事实未变 —— 本期确实一个请求都不发 |
| 「不收集手机号、邮箱、姓名…」 | 「不收集手机号、姓名、学校、位置；**邮箱仅在你自己主动填写时收集，且只以摘要 + 掩码存在本机**，不发送给任何第三方」 | 邮箱算个人信息（见 12.3），"什么都不收集"已不准确 |

**为什么不是"等接服务端时统一改"**：如果页面上已经出现"用邮箱登录"，
而条款仍写"无注册、无登录"，那条款就是一句**当场被自己违反**的话；
反过来，若为了保住旧条款而把 `/login/` 藏起来不进导航，那条款就成了**代码的枷锁**，
违反用户刚立的原则。按"条款跟随代码"的口径，正确做法是：
**代码实现到哪一步，条款就如实写到哪一步**——本期如实写「本机账号、无服务器、不发请求」。

落实清单（本次已做）：
- `privacy/index.html`：§一「收集什么」、§二「数据存在哪」、§三「儿童隐私」三处改写
- `terms/index.html`：§2「使用方式」、§5「儿童信息」两处改写
- `test/legal.test.js`：断言从「无注册无登录」改为「**本地账号 + 不上传不云同步**」，
  并新增一条**反向断言**：条款里**不得出现**「云同步」「已接入服务器」等未实现的说法
  （防止文案跑在代码前面 —— 这是比"文案落后"更糟的错）

### 12.2 裁决二：`grade / term / scope / dailyCount / algo` = **账号域（跨设备一致）**

**裁决：算，保持跨设备同步。**

依据：这五个字段直接决定「排哪几首、每天几首、怎么复习」。若各自为政，
会出现「电脑上背三年级上册、手机上排二年级下册」——同一份进度、两套排程，
是比"字号不一致"严重得多的错误。因此：

| 字段 | 归属 | 同步 |
|---|---|---|
| `grade`（年级） | **账号域** | ✅ |
| `term`（学期） | **账号域** | ✅ |
| `scope`（背诵范围） | **账号域** | ✅ |
| `dailyCount`（每日数量） | **账号域** | ✅ |
| `algo`（复习算法） | **账号域** | ✅ |
| `username`（昵称） | **账号域** | ✅ |
| `helper`（注音开关） | 设备域 | ❌ |
| 字号 / 对齐 / 连读档 / 播放模式 / iOS 引导条 | 设备域 | ❌ |

**这条裁决有连带影响，必须写清（否则会做成"改名不生效"或"一同步就全变"）**：

1. 现在 `grade/term/scope/dailyCount/algo` 与 `username/helper` **同躺在
   `poem_recite_settings_v1` 一个对象里**（见 §9 与 Issue #132 的阶段 0 设计）。
   要让前五个"跨设备一致"、后一个"各设备不同"，
   **本阶段 0 的"设置域按字段拆家"就从"建议"变成"必须"**：
   - 账号域 → `poem_recite_settings_v1`（沿用旧键名，最小改动）+ `poem_profile_v1`
   - 设备域 → `poem_device_prefs_v1`

   > ✅ **已落地（2026-09-15）**：`js/progress-store.js` 是这三域的唯一一份定义，
   > `js/storage.js` 退化成薄转发层。拆家**本期只动了 `helper` 一件** ——
   > `grade/term/scope/dailyCount/algo` 本来就该留在老键里（账号域沿用旧键名），
   > 字号 / 对齐 / 连读档 / 播放模式仍然原地不动（设备域的老键）。
   > ⚠️ **一个实测顶出来的口径**：`helper` 写的时候必须**两把键一起写**
   > （新键是正主、老键里那份是镜像），因为集子页与设置页至今从老键读它；
   > 只写新键会出现「首页说已开启、集子页是纯文本」。
   > 导出备份时 `settings.helper` 也要带上（老版本导入时才不会把它变回默认）。
   > 落地细节与另外两处偏差见 `docs/architecture.md` §3.3 / §3.4。
2. **改了账号域设置要能触发重排**：`scope/grade/term` 一变，`poem_plan_*` 缓存必须失效
   （现有逻辑已有失效机制），跨设备同步到达时**同样要清缓存重算**，否则"同步了但今日任务没变"。
3. **`profile.nickname` 就是账号域里的 `username`**（§2.1），两者不是两回事。

### 12.3 裁决三：登录时「两边都有且无法判断来源」→ 弹选择

**裁决：认同。弹「保留本机 / 保留账号 / 先导出再决定」三项。**

即 §9 表格里的 **D 场景，正式定为"不自动合并"**，三个选项各自的语义：

| 选项 | 做什么 | 风险 |
|---|---|---|
| **保留本机** | 用本机进度覆盖账号，并把本机进度推到账号 | 账号侧旧进度被覆盖（但用户已看到两边篇数） |
| **保留账号** | 用账号进度覆盖本机 | 本机进度被覆盖（**先自动存一份本机快照**，可回退） |
| **先导出再决定** | 把本机进度导出为 JSON 文件（复用 `Storage.exportJSON`），停在选择页不写盘 | 无 |

配套三条硬规则（写进测试）：
1. **弹选择之前，两个选项的"篇数 / 截至时间"必须都显示出来** —— 不让用户在不知道代价的情况下选
2. **"保留账号"前先静默落一份本机快照**（`poem_pre_merge_backup_v1`），给后悔药
3. **只读页面（首页浏览、集子页翻阅）绝不触发该弹窗**，也不写任何盘

#### 2.3.1 档案键 `poem_profile_v1`（账号域）

头像与昵称**住同一份档案**（`docs/architecture.md` §3.1 已裁决 `username` 属账号域）：

```jsonc
// localStorage: poem_profile_v1          ← 账号域（跟着同步与导出走）
{
  "v": 1,
  "nickname": "小明",                     // = 今天设置页那个「用户名」，maxlength 12
  "avatar": { "img": "https://…" }        // "" = 没传图，回到首字印
}

// localStorage: poem_avatar_local_v1     ← **设备域**（不上云、不进导出）
{ "img": "data:image/jpeg;base64,…" }     // 那张图的本机副本，离线时画的是它
```

- `img` 只认白名单里的地址（见上面第 3 条硬规矩）；
  非法 / 缺省值**归一化为空串**（不是写成默认）——
  「盘上没存过」与「传过又删了」必须能分开，界面才能如实写状态
- 上一版的 `char` / `ink` **不再读、不再写、不再校验**（用户点名删掉的那套）；
  老用户打开设置页看到的是自己名字的首字，不是一枚认不出的印
- **兼容读**：昵称取值 `poem_profile_v1` → 老 `poem_recite_settings_v1.username` → 空串
  （`Avatar.nickname()` 已按此实现）
- **本轮的写**：设置页/首页改昵称时**同时**写 `poem_profile_v1`（新增，镜像）
  与老 `settings.username`（**不动**，各页仍在读它）——
  两条键在此期间保持一致，老代码零改动。
  ⚠️ 「写新键 + 清老字段」那一步属于**阶段 0 的 `ProgressStore` 迁移**
  （`docs/architecture.md` §3.1 ④），本轮不做：清老字段会牵动
  `js/storage.js` 的 `getSettings()` 与三个写入点，超出头像这件事的范围
- **不碰设备域**：头像属身份不属设备偏好，进 `poem_profile_v1`
  而不是 `poem_device_prefs_v1` —— 手机与电脑上必须是同一枚印

- 只有 `channel: "email" | "sms"` 两种，其余 channel 直接拒绝

## 3. 认证的三种模式（本期只开前两种）

| 模式 | 触发 | 适用 | 本期 |
|---|---|---|---|
| **本机模式**（local） | 默认 | 只想用、不想给邮箱 | ✅ |
| **邮箱码模式**（code） | 用户主动「用邮箱登录」 | 换设备、防数据丢失 | ✅ |
| 服务端鉴权模式（server） | 将来接后端 | 权益校验、支付 | ⛔ 预留 |

三者**共用同一套界面与同一个账号对象**，区别只在「谁签发会话」：

```
local  : 会话由 AuthCore.issueSession() 本机签发，scope = "local"
code   : 会话由服务端在 verify 成功时签发，scope = "account"
```

### 3.1 为什么用「随机码」而不是「密码」

- 家长群体记不住密码，**忘记密码是最高频的求助**
- 无密码就没有「密码泄漏 / 撞库 / 加盐存储」这一整类问题
- 与将来的短信登录**语义完全一致**：都是「一次性短码换会话」
- 代价：每次登录都要收信 —— 用 §6.3 的「设备信任期」抵消

### 3.2 为什么不是「邮箱 + 密码」「用户名 + 密码」

- 用户名登录要做昵称查重 + 找回 + 防枚举，成本高于收益，且与现有 `username` 展示语义冲突
- 自建密码存储要么自研（风险高）要么依赖后端（本期没有）

### 3.3 为什么不是第三方 OAuth（Google/GitHub/微信）

- 面向国内家长，Google/GitHub 无意义
- 微信网页授权需要 **已认证服务号 + 企业主体 + 备案域名**（详见 issue 前序讨论），与「不花钱」冲突
- 但**接口留了口子**：`identities[].channel` 可以扩到 `wechat`，`linkIdentity` 流程不变
- ⚠️ 微信登录（以及**微信小程序版**）已进「现在不做、以后做」的清单：
  [`docs/todo.md`](todo.md) 第 2、3 条

### 3.6.2 账号入口动线（D 步，已落地）

三张账号页建好之后，剩下**最后一块**：从一个「未登录的人」到 `/login/` 的路。
这一块不写清楚，页面就只是「存在」，用户找不到 —— 那比不建更浪费。

**四页签里没有账号的位置**（背诵 / 课外 / 搜索 / 我的，每格才两三个字，
再加一格手机上一行就挤变形，`test/ui-consistency.test.js` 守的就是这件事）。
所以入口只能从「已有结构」里长出来，一共两个落点：

| 落点 | 谁渲染 | 指向 | 什么时候出现 |
|---|---|---|---|
| 「我的」页账号卡里的**账号入口** | `js/mine.js` | `/login/` | 总是（未登录「登录」/ 已登录「管理登录状态」，同一个落点） |

> ⚠️ **2026-09-20（Issue #244）：原 `/profile/`「个人中心」那一页已删除。**
> 用户原话：「现在有了 mine 页面，这个 profile 页面是不是可以删除了？」
> 两个页连卡片都长得一样（身份 / 本机数据 / 关于 / 注销），「我的」页还多了
> 子用户与头像上传 —— 于是个人中心**独有**的那几件（法务两条入口、
> 层级对比、跨设备同步开关 + 冲突裁决、管理后台）整体搬到「我的」页的
> 「关于」卡里，页面、脚本、预缓存、路由一起删干净，全站不再有 `/profile/`。
> 守卫在 `test/profile-removed.test.js`（含「搬过去的那四件还在」的正面断言）。

**两条独立的路**：动线是
① 底部「我的」页签 → `/mine/` → 账号入口 → `/login/`，
或 ② `/mine/` → 齿轮 → `/settings/` → 「通用」→ 账号那一项 → 去「我的」页。

**返回落点**（`data-back`，由 `js/chrome.js` 的 `pageBackHref()` 统一出）：

```
/login/     → /mine/       （登录是身份的事；落回设置页等于又多绕一层）
/admin/     → /mine/       （管理后台是从「我的」页进去的）
/mine/      → （没有）     （它是页签落点，顶上没有上一层；右端让给齿轮）
/settings/  → /mine/       （齿轮点进来，返回键点回去）
/settings/general/ → /settings/  （四张二级页同一条）
```

登录**成功之后**也回 `/mine/` —— 与顶栏返回键同一条动线，不出现两条。

**两条刻意收着的口径**：

1. **已登录时不再摆「去登录」**（自相矛盾）。「我的」页那一行此时换成
   「管理登录状态」，身份行上写着「昵称 + 层级徽章」；想退出 / 注销的人也在这一页，
   与那两件事放在一起。
2. **不做「到了 `/login/` 就把已登录的人弹回来」那种聪明** ——
   点一下就被弹回去，用户只会以为按钮坏了。`/login/` 自己认会话与信任期：
   信任期内顶部给「继续以 `a***@b.com` 进入」，会话还在时同样能继续。

**「我的」页那颗键是「自己会收敛的」**：拿不到内核（老缓存、脚本顺序不对）时
整个身份卡按默认值画（Free / 本机游客），账号入口照旧在 —— 它是这一页的主语，
不画的话这一页就没有意义。
（Issue #163 第四轮起，它与四组入口**共用 `#settings-index` 这一张清单**：
`renderAccountEntry()` 追加在 `renderIndex()` 之后，所以两处的调用顺序不能反。）

### 3.6.1 `/login/` `/admin/` 两张页（已落地；「个人中心」已并入「我的」页）

「账号」在设计里活了很久、在界面上一直只是一行只读状态。这几张页落地之后，
它第一次成为**用户可以自己走完的流程**：

| 页 | 做什么 | 不做什么 |
|---|---|---|
| `/login/` | 输邮箱 → 收码 → 填码 →（可选）补昵称；信任期内一点即入 | 不假装有服务器（见 §7.1）；不发任何网络请求。「重设凭证」那块页面入口已撤（#163：一页只有一套「输邮箱 → 收码」表单），能力本身保留 |

**四条硬规矩（已钉进 `test/account-pages.test.js` 与 `test/mine-page.test.js`）：**

1. **页面不许自己拼 `plan` / `tier`** —— 徽章与清单一律走
   `Entitlement.tierLabel()` / `matrix()` / `isOwner()`；页面里不出现
   `poem_plan_v1` / `poem_plan_grant_v1` / `poem_owner_v1` 任何一个键名
2. **本地体验版必须如实标注** —— `/login/` 上写着「本应用没有服务器，
   随机码由你这台设备生成」；文案用的是「已**生成**随机码」而不是
   「已发送」；有反向断言拦着「邮件已发送」这类说法
3. **退出与注销都不碰进度** —— 界面上如实写出来。实测：注销后
   `poem_recite_progress_v1` 与 `poem_profile_v1` 原封不动
4. **账号这几页一个字节都不写进度键** —— 有源码扫描守着（六把进度/设置键名一律不许出现）

**`role` 与 `tier` 是两条正交的轴。** `Entitlement.isOwner()` 是全站唯一
回答「谁能进管理后台」的函数，落在 `poem_owner_v1` 上：

> ⚠️ **2.2 起要分清两件事**：`isOwner()` 管的是「这一页画不画给你」，
> 而**真正拦人的是服务端**（`accounts.role`）—— `POST /api/admin/grant`
> 对有会话但不是 owner / admin 的请求如实回 **403**。
> 「入口藏起来」**不是**安全边界，这条从 1A 起就写着，2.2 让它第一次**真的成立**
> （在那之前，服务端根本没有能改别人数据的接口，所谓安全边界无从谈起）。

- **首次打开的这个浏览器自动成为本机主人**（幂等）。没有这个兜底，
  `/admin/` 会永远对所有人关着，那一页等于不存在
- 「我的」页的管理后台入口与 `/admin/` 的准入**走同一个出口** ——
  不会出现「入口看得见、点进去被拒」这种自相矛盾的组合
- 层级仍是 `free`：**管理员不是「买了 Max 的人」**
- 1 期接服务端后 `isOwner` 改读 `/api/me` 下发的 `role`，页面一行不动

**`js/admin-page.js` 这个名字有来历。** 管理页的逻辑**不叫** `js/admin.js`：

### 3.6.2 `/plans/` 层级对比页（已落地，2026-09-15 用户提）

用户的原始问题（Issue #132）：

> 「我看到了个人中心有个权限部分，这部分内容是不是应该有个专门的像其他网站
> 不同角色进行 4 列或者 5 列对比页面？最左侧是对比项目，右侧四列分别是匿名用户、
> 登录 free 用户、登录 pro 用户、登录 max 用户，下面用好看的打钩或者打叉。」

落地为 `/plans/`：**四列 × 逐条对照**，从「我的」页「关于」卡里那一行
「层级对比」进去（原先是 `/profile/` 的「权限」），看完就走。

| 列 | 是什么 | `can()` 收到的 ctx |
|---|---|---|
| 未登录 | 游客（匿名） | `{ tier: "free", signedIn: false }` |
| Free | 登录后的免费层 | `{ tier: "free", signedIn: true }` |
| Pro | 登录后的 Pro | `{ tier: "pro", signedIn: true }` |
| Max | 登录后的 Max | `{ tier: "max", signedIn: true }` |

**为什么是四列而不是把「游客」并进 free：** 游客与 free 之间差的是
`signedIn` 这个布尔，不是层级。今天全表只差一条（`read.aloud` ——
语音朗读要登录），但它恰恰是最容易被误解的一条（用户会把
「游客不能听」读成「免费版不能听」）。**单独一列，是把这件事说清楚的唯一办法。**

**这张表不许手抄。** 每一格都由 `Entitlement.compare()` 当场问 `can()` 算出来
（比原先 `/profile/` 那一节的 `matrix()` 更进一步：那边只画一档，
这边四档并排）。
手抄一份的下场是内核改了门槛、这张表还是老话 —— 而这张表恰恰是
**用户唯一会逐条对着看的页面**。`test/plans-page.test.js` 里有一条断言
把「每一格 === `can()` 的答案」逐格比一遍，不一致就红。

**三条已经钉进测试的口径：**

1. **未登录 ≠ free，且只差一条** —— 断言直接数「两列不一致的能力条数 === 1」，
   将来多锁一条免费功能会立刻红（那正是要人来确认的事）
2. **单调不回退** —— Free 有的 Pro 一定有、Pro 有的 Max 一定有。
   这条防的是「顺手把某项标成 pro-only 就把它从 free 收走了」这类误伤
3. **表尾必须与表身相符** —— 「能用 12/15」这种数字由同一份 `cells` 算出来，
   不许另算一遍（两个数字对不上是最难解释的 bug）

**诚实口径（本期特有）：** 表尾写明层级是**本机登记**、**不是付费凭据**、
没有收款也没有支付入口；页面里不出现「立即购买」「限时优惠」这类话
（本期确实收不了钱，写上就是假的）。`/plans/` 一个字节都不写存储 ——
看表不该留下痕迹。

## 4. 完整流程：注册 / 登录 合一

**注册与登录是同一个动作**（邮箱码方案的天然优势）：输邮箱 → 收码 → 填码 →
若该邮箱没有账号则建号，有则登录。用户不需要理解「我在注册还是登录」。

```
[入口] /login/
  │
  ├─ ① 输邮箱 ─────────────────────────────────────────────┐
  │    · 前端校验格式（宽松：本地部分不校验字符集大小写）      │
  │    · 归一化：trim → 小写 → 去掉零宽字符                  │
  │    · 命中「一次性邮箱前缀表」→ 提示但**不阻断**（§6.5）    │
  │    · 频控检查（§6.2）：邮箱 / 设备 / 全局三层            │
  │                                                          │
  ├─ ② 点「发送随机码」 → requestCode(identity, purpose)      │
  │    · 生成 6 位数字码（§5.1）                             │
  │    · 本机存 code 记录（§5.3），**不存明文码**（§5.4）      │
  │    · 本期：唤起 mailto: 预填主题与正文（§7）              │
  │    · 服务端版：调 POST /auth/code → 邮件由服务端发         │
  │                                                          │
  ├─ ③ 用户去邮箱取码，回来填 6 位 ─────────────────────────┤
  │    · 6 格数字输入框，自动跳格、支持整段粘贴                │
  │    · 每隔 1 秒检查一次过期，剩余时间倒计时显示             │
  │                                                          │
  ├─ ④ verifyCode(uid, code, purpose)                       │
  │    · 命中 → 建号/取号 → 签发会话 → 进 ⑤                 │
  │    · 不中 → failCount++，按 §5.5 的阶梯锁定              │
  │                                                          │
  └─ ⑤ 登录成功
       · mergePolicy：把本机未登录的进度「认领」进账号（§9）
       · 若 profile.nickname 为空 → 提示补昵称（沿用今天那 12 字输入框）
       · 跳回来源页；PWA 下不整页刷新
```

### 4.1 状态机（不可跳步；每条转移都有测试）

```
idle ──enterEmail──▶ emailEntered ──requestCode──▶ codeSent
                          ▲                            │
                          │                            ├──verify ok──▶ signedIn
                          │                            ├──verify bad─▶ codeSent (failCount+1)
                          └────resend / editEmail──────┤
                                                       ├──expired────▶ codeExpired ──resend──▶ codeSent
                                                       └──locked─────▶ locked ──wait/换设备──▶ idle
signedIn ──signOut──▶ idle
signedIn ──deletingAccount(二次确认)──▶ signedOut+erased
```

规则：
- `codeSent` 下**可以改邮箱重发**，但会清掉旧码（不允许两个邮箱的码并存）
- 任何一步刷新页面，状态从本机 `pending` 记录恢复（`codeSent` 可续）
- `locked` 是终态之一，**不因为重试自动解锁**，只能等 `lockedUntil`

## 4.4 【Issue #197】完整登录流程（已落地，2026-09-16 用户裁）

用户原话：

> 「我要求重新设计用户的整个登录流程。使用邮箱注册，注册邮件确认，登录，
> 忘记密码，重设密码，再加一个发送随机码快捷登录，要求用户邮箱必须记录到数据库，
> 用户名等也要。以及 profile 信息等等。」

这一节的每一件事都是**已落地**的（不是路线图），落地位置写在每条下面。

### 4.4.1 流程全图（六条路，两条主路 + 四条支路）

```
                     /login/（一页四屏，页签切动作不跳页）
                     │
   ┌─────────────────┴─────────────────┐
   │                                   │
【主路 A】密码登录                   【主路 B】快捷登录（随机码）
   邮箱 + 密码                         邮箱 → 收 6 位码 → 填码
   → session.issue                     → session.issue
   │                                   │
   └──────────┬────────────────────────┘
              │  （两条路签发的是**同一枚会话**，下游不必知道从哪条路进来）
              ▼
        登录成功 → 补昵称 → /mine/

【支路 ①】注册    ：「还没有账号？注册」→ 邮箱 + 密码 ×2
                      → 立刻建号（status='pending'）+ 发确认邮件 → 支路 ②
【支路 ②】等确认    ：/verify/?vid=..&token=..  ← 邮件里那条链接（独立一页）
【支路 ③】忘记密码 ：「忘记密码」→ 输邮箱 → 服务端发重设邮件
【支路 ④】重设密码  ：/reset/?rid=..&token=..   ← 邮件里那条链接（独立一页）
                      → 新密码 → **吊销全部会话** → 回登录页
```

**注册与快捷登录不是同一件事**（这一条与上面的 §4「注册 / 登录 合一」口径**并存**，
两者说的是两件事，别混）：

| | 快捷登录（随机码） | 注册（邮箱 + 密码） |
|---|---|---|
| 触发 | 主动作页签「快捷登录」 | 藏在「还没有账号？注册」文字链后面 |
| 何时建号 | **收到码才建号**（`findOrCreateAccount`） | **填完就建号**（口令要有地方放） |
| 邮箱确认 | 不需要（能收到码本身就证明了可达） | 需要（发确认邮件） |
| 口令 | 没有 | 有（scrypt 摘要） |

两条路都保留，**不是过渡期的临时状态**：家长群体记不住口令
（§3.1 写着「忘记密码是最高频的求助」），所以「不想记口令的人」
必须还有得走。反过来，只有随机码不够 —— 找回凭证、跨设备、将来的
第三方绑定都要一个稳定的账号锚点。

### 4.4.2 邮箱明文**落库**（推翻 §6.1 与 §2.2 的旧口径）

> ⚠️ **这是一次口径推翻，不是补充。** Issue #132 那一版写的是
> 「邮箱不以明文落盘，只存 `email_hash` + `email_mask`」；
> Issue #197 用户裁的是「**要求用户邮箱必须记录到数据库**」。
> 以本文为准：**明文落库**。

| 列 | 是什么 | 谁用它 |
|---|---|---|
| `accounts.email` | **明文**（`normalizeEmailForStore()`＝trim + 去零宽，**保留大小写**） | 显示（个人中心说「你的邮箱是 xxx」）、管理员名录、发信 |
| `accounts.email_hash` | `SHA-256(pepper \| 归一化邮箱)`，归一化**含小写折叠** | **登录查找**（`getAccountByHash`）、老数据平滑 |
| `accounts.email_mask` | `a***@b.com` | 界面回显、按掩码发放 |

**四条必须一起看的连带影响**：

1. **登录查找仍走 `email_hash`**，所以「大小写不同算同一个账号」这条历史行为
   **一个字都没变**。`email` 那一列只是**显示**用的，不参与查找 ——
   拿它去查的话，「A@b.com」与「a@b.com」会变成两个账号。
2. **明文只下发给「你自己」**（`/api/me`、登录 / 注册的响应）与**管理员**
   （`POST /api/admin/accounts`，且那条接口本身有角色闸）。
   别人的邮箱永远只以掩码出现。
3. **`email_hash` 留着**，不是历史包袱：老行不必回填明文就能继续登录；
   而且「按明文查账号」这条路永远不必开。
4. **老行可以是空明文**（`email` 默认空串）。界面遇到空值时**如实回落掩码**，
   绝不编一个 —— 编出来的明文比掩码更糟（掩码至少是真的）。

### 4.4.3 口令：怎么存、怎么判、怎么找回

| 项 | 值 | 落点 |
|---|---|---|
| 算法 | `scrypt(N=16384, r=8, p=1, len=32)`，Node 自带 `crypto` | `identity.hashPassword()` |
| 摘要串 | `scrypt$N$r$p$<saltHex>$<hashHex>` —— **参数写在串里** | 同上 |
| 盐 | 每个账号 16 字节随机 | `identity.newPasswordSalt()` |
| 最短 | 8 个**码点**（不是 UTF-16 长度） | `core.checkPassword()` / `PASSWORD_MIN` |
| 最长 | 72 个字符（防 DoS：scrypt 对超长输入一样要算） | `PASSWORD_MAX` |

**为什么参数写在摘要串里**：将来调 `N` 值，老用户必须还能登进来。
参数不写进串的下场是「换了参数之后所有老用户登不上」，
而那时**没有任何办法区分「口令错」与「参数变了」**。

**为什么最短按码点数**：`"😀😀😀😀😀😀😀".length === 14`（每个代理对算 2），
按 `.length` 判的话「七个 emoji」会被算成十四位而通过 —— 而它其实只有 7 个字符。

**明文口令出现在哪**：只在 ① 生成它的那一次函数调用内、② 用户的输入框里。
库里、日志里、响应体里、URL 里**都不出现**。
`test/api.test.js` 第廿二节逐条钉住，另有一条源码扫描断言守着
「`js/login.js` / `js/reset.js` 里没有一行同时出现口令与本地存储 / URL」。

**忘记密码 = 重设，不是找回**。本站拿不回原密码（只有单向摘要），
所以「忘记密码」这条路走到头是「设一个新密码」。这一点在
`/terms/` 里如实写出来了 —— 用户以为能找回原密码、结果发现只能重设，
那是体验事故。

### 4.4.4 两张一次性令牌表（**不并进 `codes`**）

| 表 | purpose | 谁发 | TTL | 形态 |
|---|---|---|---|---|
| `verifications` | `verify` | 注册时、个人中心点「重发确认邮件」 | **24 小时** | 邮件里那条链接 |
| `resets` | `reset` | 忘记密码第一步 | **1 小时** | 邮件里那条链接 |
| `codes`（既有） | `login` / `reset` | 快捷登录 | 10 分钟 | 6 位数字 |

**为什么不合成一张表**：两者是两种完全不同的凭据 ——
一个是 6 位数字（空间 1e6，靠失败上限与短 TTL 防猜），
一个是 64 位 hex（空间 2^256，靠 TTL 与「用过一次」防重放）。
合成一张表的下场是 **TTL、失败上限、作废规则互相污染**，
而症状是「确认链接十分钟就过期了」（被码的 TTL 带上）这种谁也查不出原因的怪事。

三条共用纪律（三张表都一样）：
- 落库的**只有摘要**（`tokenHash(uid, purpose, token, pepper)`），明文令牌只在邮件里
- **发新的即作废旧链接**（`voidVerifications` / `voidResets`）
- 形状不对（不是 64 位 hex）**不进库** —— 省一次查询，也少一条脏数据

### 4.4.5 四条「不假装」与三条「不泄露」

**不假装**（错了就说错了，成了就说成了）：

| 情形 | 如实说什么 |
|---|---|
| 发信商没配（console 通道） | `verifySent:false` → 界面写「这台服务器现在**没能**把确认邮件发出去」 |
| 服务端连不上 | 口令那四屏**整体不可用**（如实说），**绝不**回落本机 —— 本机版给不出「注册成功」这个真承诺 |
| 「邮箱还没确认」 | 不拦人进门，但**必须说出来**（个人中心那一行 + 登录后一句 toast） |
| 注册时邮箱已存在 | 回**同一个响应**（`created:false` 但不报「已注册」），同时补口令 + 重发确认邮件 |

**不泄露**：

1. `login`：口令错与账号不存在回**同一个响应**，而且**耗时也一样**
   （账号不存在时照样算一次 scrypt；不然「这个邮箱注册过没有」
   就成了一件可以测出来的事）
2. `reset-request`：存在与不存在回**逐字相同**的响应
   （`test/api.test.js` 在生产形态那一档上直接比 JSON）
3. 两处的文案都**不出现**「没注册过 / 不存在」这类断言；
   允许的是**条件句**（「如果这个邮箱在本站注册过…」）——
   判断留给收件箱，界面不替服务端回答

### 4.4.6 重设口令必须吊销全部会话

这是**这一件事的一半含义**，不是可选的收尾：口令被换，说明原来那个
**可能已经泄露**，那么所有拿旧口令 / 旧会话进来的人都必须出去。
省掉它的下场是「用户改了密码，但偷到 Cookie 的人还在里面」——
而那恰恰是最需要改密码的那一种情形。

`resetConfirm` 一次做齐五件（少一件都是半截功能）：
① 令牌校验（形状 / 过期 / 重放 / 定长比较）→ ② 口令形状校验（与注册**同一处**
`checkPassword`，不是两套规则）→ ③ 写新摘要（新盐）→ ④ `revokeSessions(uid)`
→ ⑤ 从 `locked` 里解出来（能收到邮件、能点开、能填新口令，就是本人；
还锁着是自相矛盾）。

**两件刻意不做的事**：

- ❌ **不顺手确认邮箱** —— 收到重设邮件 ≠ 邮箱已确认。
  写成「收到了 ⇒ 一定确认过」在下一次「改主邮箱」时会出错，两件事各写各的。
- ❌ **不顺手解开 `suspended`** —— 只把 `pending` 提成 `active`**这一个方向**。
  顺手解开的后果是「封掉的账号点一下邮件就复活了」。

### 4.4.7 口令失败：计数落在**账号**上

| 项 | 值 | 为什么 |
|---|---|---|
| 判据 | **账号**（`uid`），不是设备 / IP | 撞库打的是**同一个账号**（一份泄露的口令表逐个试）；按 IP 计数拦不住分布式尝试 |
| 上限 | 连续 10 次 → `status='locked'` | 与 §5.5 的「锁 24 小时」同一形状 |
| 成功一次 | **把失败窗口清空** | 不清的下场是「错九次、对一次、再错一次 → 锁号」，而那个用户其实只错了一次 |
| 锁着的时候 | **对的口令也进不来**（423） | 锁是终态，不是「再试一次就好」 |
| 设备档 | `login` 桶另有 20 次/小时 的退避 | 两条一起：设备档是**退避**、锁号是**终态** |

**为什么失败窗口不能拿 `hits` 凑合**：`hits` 是单调累加的（只增不减），
拿它当失败计数就没有「清空」这件事。所以失败窗口有自己的一对表
（`fails` / `failWin` 语义），`limiter.fail()` / `limiter.fails()` / `limiter.clearFails()`。

### 4.4.8 客户端：一页四屏 + 两张独立页

| 落点 | 是什么 | 为什么在这儿 |
|---|---|---|
| `/login/` | **两个页签**（密码登录 / 快捷登录）+ 注册、忘记密码两屏支路 | 一页只有**一件主动作**（实心按钮），其余动作收成文字链 —— 上一轮被点名的「一页里三颗一样重的按钮」不许再出现 |
| `/verify/` | 确认邮箱（读 `?vid=&token=`） | 用户可能在**另一台设备**上点开邮件；挂在登录页上的话，点开链接只会落到一个空白登录页 |
| `/reset/` | 重设密码（读 `?rid=&token=`） | 同上 |

三张页都 `data-dock="off"`（做完就走），返回落点都指 `/login/`。

**一页四屏怎么保证「一次只有一件事」**：四个邮箱输入框分住在四个
互斥的 `[hidden]` pane 里（`display:none` 的那个不显示），
由 `LoginPage.setMode()` **一处**切换。`test/account-pages.test.js`
的第十一节从「数几个输入框」改成「**结构**上每个框都在自己的 pane 里」——
数字会随流程增减而变，结构不该变。

**URL 里的令牌**：`/verify/` 读出参数即 `history.replaceState` 抹掉
（进浏览器历史、被分享时带走、被截图带走，都是凭据泄露）；
`/reset/` 则**抹在提交成功之后** —— 那一页要等用户填完两次口令才发请求。
两处差异是刻意的。

### 4.4.9 管理后台：两张名单**不是一张表**

| | 「服务端名单」（§3.5 · 2.2） | 「全部账号」（Issue #197） |
|---|---|---|
| 接口 | `POST /api/admin/grants` | `POST /api/admin/accounts` |
| 是什么 | **台账**：发过什么 | **名录**：都有谁 |
| 列出 | `plan !== free` | **全部**（除 deleted） |
| 邮箱 | **只回掩码** | **回明文** —— 那是它存在的理由 |
| 给的操作 | 改层级 | **只读**（发放仍按掩码在上面那张表上做） |

用户原话「我还是要看到这些用户」—— 而掩码 `a***@qq.com` **认不出是谁**。
所以那张需要「认人」的表必须回明文（这也正是 `accounts.email` 落库的第二个理由）。

四条边界（`core.adminAccounts` 里逐条写着）：
① 角色闸在服务端（不是 owner / admin 一律 403，界面上藏入口不是安全边界）
② **绝不回** `password_hash` / `password_salt`
③ **绝不回** `email_hash`（泄出去等于把「这个人是不是本站用户」变成可查询的事实）
④ 不回进度 / 会话 / 确认令牌

**登记的能力**：`Issue #197` 没有引入任何新的权益能力 ——
注册、确认、登录、忘记密码、重设都是**所有人**都有的基本功能。
口令与随机码也不是「两条能力」：它们只是同一件事（拿到会话）的两条路。

## 5. 随机码规则（安全核心）

### 5.1 码的形态

| 项 | 值 | 理由 |
|---|---|---|
| 字符集 | `0-9`（纯数字） | 邮箱里好认好输，无 O/0 混淆 |
| 长度 | **6 位** | 10^6；配合 §6.2 频控足够 |
| 有效期 | **10 分钟** | 够慢手用户；比常见的 5 分钟宽松一点 |
| 使用次数 | **1 次**（成功即失效） | 防重放 |
| 校验失败上限 | **5 次** | 之后该码作废，必须重发 |
| 比较方式 | 定长比较 + 失败也走完循环 | 防时序侧信道（服务端实现要求） |

### 5.2 用途绑定 purpose（同码不同用，互不通用）

```js
PURPOSE = {
  login:  "登录 / 注册",     // 双方共用一个 purpose
  reset:  "重设凭证"         // 本期无密码，等价于"吊销全部会话 + 清设备信任"
}
```

**`login` 的码不能用于 `reset`，反之亦然**。将来加 `bind`（绑定新邮箱/手机号）时同样独立。

### 5.3 码记录（落盘形态）

```jsonc
// poem_auth_v1.codes[<codeId>]
{
  "codeId": "c_7f2a…",           // 随机，不是码本身
  "uid": "u_8f3k2m9q",
  "purpose": "login",
  "channel": "email",
  "sentTo": "a***@b.com",        // 掩码，用于界面回显"已发往"
  "codeHash": "…",               // 见 5.4
  "salt": "…",
  "issuedAt": 1757900000000,
  "expiresAt": 1757900600000,
  "attempts": 0,
  "consumedAt": null
}
```

同一 `uid + purpose` 同时**只保留最新一枚**（发新的即作废旧记录）。

### 5.4 不允许存明文码

- 存储层只留 `codeHash = SHA-256(uid + purpose + code + salt)`（`salt` 每码随机 16 字节）
- 用户输入时同样按此公式现算比对
- **服务端版强制要求**：任何日志、错误上报、监控里**禁止出现明文码**（写进 review checklist）
- 明文码只在两处短暂存在：① 生成它的那一次函数调用内；② 用户的邮箱里
- **`ALLOW_CODE_ECHO` 那条冒烟口子必须跟着「真送出去了」才作数。**
  它唯一的用途是本地联调与 CI 里取码，而这两个环境恰恰是「发信商时通时不通」
  的地方。原先 `sendCode` 的 `catch` 把中转那一条响应原样回了出去 ——
  于是**发信一失败，明文码就跟着 5xx 回给了调用方**。
  现在的判据是一个只在 `sendVia` 真回来之后才置真的 `echoAllowed`：
  异常路径、发信失败路径都不带 `devCode`。
  这条钉进了 `test/api.test.js` 第二十三节（④）。
- **id 生成不许写成「撞了就重摇」**。`codeId` / `uid` / `sid` 一律走
  「随机取一次 + 确定性线性探测」，步数上限明确。写成
  `do { x = rand() } while (撞了)` 的版本在随机源退化时是**死循环** ——
  实测的现场表现是：第一次发码正常，第二次调用整个线程卡死、不报任何错。
  这条已钉进测试（`test/auth.test.js` 第十二节）。

### 5.5 阶梯锁定（防暴力猜 6 位）

| 连续失败 | 处理 |
|---|---|
| 1~4 次 | 提示剩余次数 |
| 第 5 次（该码） | **该码立即作废**，必须重发，同时记「1 轮失败」 |
| 单账号当日发码 > 10 次 | **锁 1 小时**（`lockedUntil`） |
| 单账号连续 3 轮「发码后一次都没对」 | **锁 24 小时** |
| 全局异常（服务端版） | 单 IP / 单设备阈值触发人机校验（§11 三期） |

> ⚠️ 这条是**实测修正过的**。最初写的是「累计错 3 次就锁 24 小时」，
> 写进测试才发现它同时满足两个条件、结果反了：单枚码本身就能错 5 次，
> 正常用户手抖三次就被锁一天；而手改 localStorage 清掉计数又能立刻重来。
> 现在的判定对象是**「整轮失败」**（发一枚码 → 一次都没对 → 才算一轮），
> 既不会误伤正常用户，也不会被单枚码的 5 次重试放大成 5 倍机会。

锁定与失败计数**只认 uid，不认邮箱字符串**（防止大小写/别名绕过）。

**服务端这一半直到 Issue #197 才真的落地。** 上面这张表从 1A 期起就写着
「单账号连续 3 轮 → 锁 24 小时」，而 `api/_lib/core.js` 里**从来没有实现它** ——
`verifyCode` 只判「**这一枚码**错了几次」（`codeMaxAttempts`），
换一枚码就重新从 5 次数起。实测（`test/api.test.js` 第二十三节）：
一个坏客户端对同一个邮箱连着发码、每枚码错 5 次，可以**无限**进行下去。
所以这句话以前是**文档跑在代码前面**，现在两端对齐了：

| 项 | 服务端落点 |
|---|---|
| 「1 轮」的判据 | 一枚码**刚好被第 5 次错误作废**那一刻记一轮（语义判据，不看时钟） |
| 轮数 | `limiter._hits["wrong\|<uid>"]` 的长度 |
| 上限 / 锁多久 | `WRONG_ROUNDS_LIMIT`（默认 3）/ `ACCOUNT_LOCK_MS`（默认 24h） |
| 「锁」写在哪 | `accounts.status = "locked"` + `accounts.locked_until` |
| 谁读它 | `sendCode` 开头那一条（还在锁里 → 423 带 `retryAfter`；**已过期 → 当场解锁**） |
| 出口 IP | `WRONG.ip` 那一档，判据是 `轮数上限 × 单码上限` 次错误（挡住「换小号猜」） |

> ⚠️ **锁必须会到期**。原先代码里那条 `if (acc.status === "locked") → 423`
> 是**只读不写**的：没有任何一处会把 `status` 写成 `"locked"`，
> 于是它既是死代码，又给后来的人一个错觉「锁定已经做好了」。
> 现在写进去了，就必须同时写**解锁**（`locked_until` 到期即改回 `active`
> 并清掉轮数账）—— 否则「锁 24 小时」会变成「锁一辈子」，
> 而界面上写的还是「1 小时后再试」。

**频控的账本只有一个，而且必须是原子的。** 服务端的频控器是**进程内**的
（`makeRateLimiter`），它的正确用法是 `take()`（判完当场落账），
**不是** `check()` 之后再找地方 `hit()` —— 后者中间隔着发信商那次真实的
网络往返，并发打进来时每一条请求都在空窗口上通过（实测：连点两次重发，
第二次也放行）。同一条纪律也覆盖**所有被拒的走法**：码长不对、
码过期、码已用这些早退路径**都要落账**，否则那道闸只是个建议。

> ⚠️ 多实例下这本账是**尽力而为**的，接口如实自报：
> `/api/me` 的 `channel.rate === "instance"`。要跨实例必须把窗口搬到
> 共享存储，那是另一件事；在它落地之前，界面不许把「次数有限」说得比事实更硬。

## 6. 频控、防滥用与隐私

### 6.1 邮箱不在**本机**落明文（服务端口径见 §4.4.2）

> ⚠️ **口径已被 §4.4.2 部分推翻**：Issue #197 起，**服务端**的 `accounts.email`
> 确实是明文（用户裁决「要求用户邮箱必须记录到数据库」）。
> 本节剩下的是**本机那一半**（`js/auth-core.js` 的 `poem_auth_v1`）——
> 本机存储仍然只存摘要 + 掩码，那一条没变。



本机模式下数据不出设备，但浏览器数据可能被导出备份、被同机他人看到。
因此账号记录里只存：

```
emailHash = SHA-256(normalized(email) + PEPPER)   // 用于查重与登录比对
emailMask = "a***@b.com"                          // 用于界面回显
```

- `PEPPER` 本机随机生成一次，存 `poem_auth_v1.pepper`，**不导出**（导出备份里剔除）
- 换句话说：拿到备份文件也**还原不出完整邮箱**，但换个设备无法用同一份账号数据登录 ——
  这是刻意的取舍：本机模式不追求跨设备，跨设备要等三期有服务端

### 6.2 三层频控（每层独立计时，**取最严**）

| 层 | 键（哈希后） | 限制 |
|---|---|---|
| 邮箱 | `identityHash` | **重发冷却 60 秒**；1 小时 5 次；24 小时 10 次 |
| 设备 | `deviceId`（随机 UUID，存本机，**非指纹**） | 1 小时 10 次；24 小时 30 次 |
| 出口 IP（**服务端版**） | `x-forwarded-for` 第一段 | 1 小时 30 次；24 小时 100 次 |
| 全局 | 常量 | 1 小时 20 次；24 小时 60 次（本机模式兜底） |

> ⚠️ **服务端版的四层里有三层要看「调用方是谁」，而这件事只有 IP 改不动**。
> `deviceId` 是**客户端自己给的**（`x-kb-device` 头或请求体），
> 每天换一个就绕过了设备档；邮箱更是攻击者自己挑的。
> 所以 `/api/verify-code` 与 `/api/send-code` 都必须把 IP 传给内核
> （`api/_routes/verify-code.js` 里那一行 `ip: d.ip` 就是它）——
> 漏传的后果不是报错，而是**那一档永远落在 `"unknown"` 这一个桶里**：
> 桶被刷满时**所有用户一起被拒**（DoS），而真正的攻击者换个网络就走了。

**校验口（`/api/verify-code`）的闸与发码口不是同一组**，各管各的：

| 闸 | 挡的是什么 | 落点 |
|---|---|---|
| 设备档（`verify:<deviceId>`） | 一台机器猛试 | `E_RATE_DEVICE` 429 |
| IP 档（`verify:<ip>`） | 一个网络猛试 | `E_RATE_IP` 429 |
| 该码的 5 次（`codes.attempts`） | 单枚码被猜 | `E_CODE_WRONG` → `E_CODE_VOID` |
| 账号的连续失败轮数 | **换着码猜**（§5.5） | `E_LOCKED` 423 |
| 出口 IP 的猜错次数 | **换小号猜** | `E_RATE_IP` 429 |

> ⚠️ 判据分开的另一个原因：**正常用户的请求也会落进 IP 档**。
> 如果「猜错计数」与「限流」共用一本账，一个共享出口（学校机房、
> 运营商 CGNAT）里的几十个用户会互相把对方的额度吃满，
> 而真正的猜错计数看起来还很宽松。

倒计时期间按钮置灰并显示「还需等待 47 秒」。

> 注意「60 秒冷却」与「频控档位」是两件事：前者只管「同一枚码别连点」，
> 后者管「这段窗口里一共要了几枚」。把冷却也算进频控档位，
> 会让「正常的三次重发」被误判成刷量 —— 这也是实测改过来的。
**`deviceId` 是随机生成的本地值，不采集 UA/屏幕/字体等任何指纹特征** —— 与 `/privacy/` 的
「不采集设备标识」承诺保持一致（这句承诺本身要不要改，见 §12）。

### 6.3 设备信任期（减少重复收信）

- 登录成功后，本机记 `trustedUntil = now + 30 天`
- 信任期内打开 `/login/`，顶部直接给「继续以 a***@b.com 进入」，**一点即入，不发码**
- 但**每次登录都写 `lastLoginAt`**，且会话过期后必须重新收码（信任期不等于永久会话）
- 提供「退出并取消信任本设备」，以及设置页「退出全部设备」（本期等价于清本机会话）

### 6.4 会话规则

| 项 | 值 |
|---|---|
| 有效期 | 30 天 |
| 续期 | 剩余 < 15 天且用户有操作时静默续到 30 天 |
| **续期不许写成「每次登录都签新的」** | 见下 |

> ⚠️ **服务端这一条也翻过一次车（Issue #197）。**
> 设计里那句「剩余 < 15 天时静默续到 30 天」是**有条件的**，
> 而 `api/_routes/verify-code.js` 原先做的是「每一次登录都签一枚新 Cookie」——
> 那等于**无上限的滑动窗口**：用户只要别空过 30 天，
> 这一枚会话就能活 60 天、90 天、无限期，而库里那一行 `sessions`
> 的 `exp` 还停在最初那一刻（续期从不落库）。
> 判据现在收在 `session.shouldRenew()` 一处：
> **剩余不足一半**才续（`(exp - now) < sessionDays/2` ——
> 不写死 15 天，因为 `sessionDays` 改成 7 时「写死 15 天」会让每一次请求都续期，
> 又滑回去）；不该续时**不发 `Set-Cookie`**，浏览器手里那一枚原封不动，
> 响应里多一个 `sessionKept:true` 让界面与测试都看得出这一次是沿用。
| 存储位置 | `localStorage`（本期无服务端，HttpOnly Cookie 无意义） |
| 会话内容 | `{sid, uid, scope, iat, exp, nonce}`，**不含邮箱**；`sid` 唯一性同上 |
| 退出 | 清会话 + 清 `pending`；**不动任何进度数据** |
| 注销账号 | 二次确认 + 要求重输一次邮箱 → 清账号、会话、信任期；进度数据单独询问是否一并清空 |

> 服务端版必须改为 `HttpOnly + Secure + SameSite=Lax` 的加密 Cookie，
> **禁止用 localStorage 存长寿命 token**。本期是例外，因为它只能在用户自己机器上自我验证。

### 6.5 一次性邮箱（临时邮箱）

- 维护一份「常见一次性邮箱域名前缀表」（如 `mailinator`、`10minutemail`、`guerrillamail` 等）
- 命中时**只在发送前给一句提示**：「临时邮箱收不到后续邮件，可能丢失账号，确定继续？」
- **不阻断**：挡住的是真用户，挡不住有心人，而收益是负的
- 表本身放 `js/auth-core.js`，可由测试替换（不联网）

## 7. 【关键】本期没有后端，码怎么送到用户手里

这是这份设计里唯一"将就"的地方，必须说清楚，不能含糊。

### 7.1 本期的做法：本地发码 + 用户自送（明确标注为「本地体验版」）

1. 前端生成码，存哈希到本机
2. 点击「发送随机码」→ 界面弹出一个本地对话框，内含：
   - 复制按钮：把码复制到剪贴板
   - `mailto:` 按钮：打开用户自己的邮箱客户端，主题/正文预填「【跬步】登录码 XXXXXX」
   - **明文提示**：「当前为本地体验版：本应用没有服务器，码由你自己保管。
     真机上请勿把码发给他人。」
3. 用户回填即可登录

**它不比「输两次邮箱」更安全，也不比它更不安全** —— 因为它本来就是本机自证。
所以**绝不能把它宣传成"邮件认证已经做好了"**。

### 7.2 服务端版（**1A 期已落地**，接口见下）

> ✅ **已实现**（2026-09-15）。落地时路径从设计里的 `/auth/*` 改成 `/api/*` ——
> Vercel Serverless 的目录约定就是 `api/`，用 `/auth/*` 要多配一层 rewrite，
> 而 rewrite 会让「哪个文件对应哪个接口」变得不可见。六个接口的实现在
> `api/{send-code,verify-code,me,account}.js` 与 `api/sync/{pull,push}.js`，
> 业务内核全在 `api/_lib/core.js`（这样才写得了测试），
> 客户端的 `transport` 是 `js/auth-api.js`。
> 上面「本期的做法」（本地发码 + 用户自送）**保留为降级路径**：
> 服务端没配好 / 连不上 / 断网时自动回落，界面如实标注「本机体验版」。

```
POST   /api/send-code   {email, purpose, deviceId}   → 202 {codeId, expiresAt, cooldown, transport, delivered, store}
POST   /api/verify-code {codeId, code, deviceId}     → 200 {account} + Set-Cookie: kbsid=...
                                                       400/423 {code, message, remaining?, retryAfter?}
GET    /api/me                                        → 200 {uid, nickname, plan:{tier,until}, features[], mask,
                                                            channel:{mail,delivered,db,sms}}   ← 2C 补的开通状态
                                                       401 {code:"E_NO_SESSION"}
POST   /api/sync/pull   {since, deviceId}            → 200 {recs[], serverTime}
POST   /api/sync/push   {recs[], deviceId}           → 200 {applied, conflicts[], serverTime}
DELETE /api/account     {confirm:true, deviceId}     → 200 {deleted, export, note} + 清 Cookie
```

**与设计原稿的三处差异**（都是实测顶出来的）：

1. **`/auth/*` → `/api/*`**，理由见上（Vercel 目录约定；少一层 rewrite 就少一层不可见映射）
2. **注销不返回 `exportUrl`** —— 本期没有对象存储放导出文件。
   数据**直接随响应回**，用户自己存。假装有个下载链接比不做更糟。
3. **退出登录没有单独接口** —— 会话是签名 Cookie，前端清 Cookie 即可；
   服务端那条 `revokeSessions` 只在「注销」与「重设凭证」时用（那两件才需要真正吊销）。
   `/api/session` 那条设计里写了但 1A 没建：它会是一个「删了也不影响任何断言」
   的接口，而「无害的冗余接口」正是之后会被误用的那一类。

同一套状态机与错误码（§13），客户端只换 `transport` 实现。

> **2C 补：`/api/me` 如实自报开通状态。**
> 界面在说「由服务器判定」时，得让用户看得见**这台服务器是什么状态**：
> `channel: { mail:"sendgrid"|"console", delivered, db:"db"|"memory", sms }`。
> 三个字段全是事实，且全部取自既有判定（`cfg.mail()` / `cfg.hasDb()`），不另算一份。
> 客户端**收下但不落盘、不参与判权**（`AccountApi.channel()`）——
> 缓存一份必然与服务端真实状态漂移。
> 未登录时 `/api/me` 仍是 401，**不下发任何开通状态**。
> 开通到哪一步、缺哪个变量、怎么补：`npm run doctor`（§7.3）。

### 7.3 配置怎么核对：可执行的自检（2C）

「接服务端」这一步的配置项有 13 个，散在会话 / 数据库 / 发信 / 短信 / 冒烟五组里。
自检把「缺哪个、缺了会怎样、怎么补」一次说清，**且不部署就能问**：

```
npm run doctor                 # 人看的一段文字（可直接贴进 Issue）
npm run doctor -- --json       # 程序看的形状；退出码 = 体检结论
npm run env:example > .env.example   # 生成可直接粘贴的模板（唯一来源）
```

三档分得清：**必须**（`SESSION_SECRET`、Supabase 那一对）／
**这一件需要**（发信商密钥）／**可选**。
**一个都不配也照样能完全离线使用** —— 自检把这句话写在报告里，
免得「未配置」被读成「坏掉」。

清单定义在 `api/_lib/ops.js` 的 `ENTRY` 里，**自检与 `.env.example` 读的是同一份** ——
手抄的清单必然与代码分叉，而本项目里这种分叉已经出现过好几次。

## 9. 【关键】登录时本机已有进度怎么办

这是最容易出事故的地方。规则如下（`mergePolicy`）：

| 场景 | 处理 | 理由 |
|---|---|---|
| A. 本机进度为空，账号有数据 | 拉账号数据覆盖本机 | 新设备首次登录 |
| B. 本机有进度，账号为空（新注册） | **把本机进度"认领"进账号** | 否则用户一注册就丢光数据，最恶劣的体验 |
| C. 两边都有，且是同一账号同一设备 | 按 `id` 逐条取「复习次数多 / `nextReviewAt` 更晚」者 | 打卡要单调，不能因为同步回退 |
| D. 两边都有，但无法判断来源 | **不自动合并**，弹选择：「保留本机 / 保留账号 / 先导出再决定」（**已由用户裁决确认**，细则见 §12.3） | 宁可不合并，也不静默覆盖 |
| E. 用户在 A 设备登录了 B 的账号 | 提示「本机有另一份进度（3 首诗）」，需显式选择 | 家庭共用一台设备很常见 |

**只读页面绝不可触发任何合并或写盘**（现有测试已守这条，新增用例继续守）。

合并的粒度只到「进度记录 + 昵称 + 账号域设置」，**设备偏好一律不同步**
（字号、注音档、连读档、播放模式、iOS 引导条已关）。

**账号域 = `grade` / `term` / `scope` / `dailyCount` / `algo` + `username`**
（用户已于 2026-09-15 裁决，见 §12.2），

## 10. 异常与边界（逐条可测）

| 场景 | 期望行为 |
|---|---|
| 邮箱格式错 | 就地提示，不进入 `emailEntered`，不计入失败次数 |
| 邮箱带空格/大写/零宽字符 | 归一化后视为同一邮箱 |
| 连续点「发送随机码」 | 第 2 次起按钮置灰 + 倒计时，**不发新码** |
| 收到两封码，用旧码 | 拒绝（旧码已作废），提示「请用最新一封」 |
| 码过期后再输 | 明确区分「已过期」与「码错误」，过期可直接重发 |
| 输错 5 次 | 该码作废，必须重发；界面不透露"还剩几次"以外的信息 |
| 关掉页面再回来 | 从 `pending` 恢复，倒计时继续走 |
| 系统时间被改早/改晚 | 以 `issuedAt` 单调时钟为准；检测到时间倒退则**直接作废全部码** |
| 存储被写脏（手改 localStorage） | 全部字段做运行时校验，非法值回落默认，不抛异常 |
| localStorage 不可用（隐私模式） | 降级为「内存会话」，本次可用、刷新即退；给出说明 |
| 存储写满（QuotaExceeded） | 捕获、提示、不丢当前输入；会话优先于日志 |
| 用户注销 | 二次确认 + 重输邮箱确认；进度数据单独确认 |
| 会话过期 | 静默降级为 local 模式，**绝不弹窗打断背诵** |
| 备份导入含账号字段 | 忽略 `plan` / `security` / `identities` 的可疑字段（§2.2 硬约束） |

## 12. 合规：用户已裁决的三件事（2026-09-15）

> **总原则（用户原话）**：「用户协议和隐私条款永远遵从于代码的实际情况，
> 代码改了相应内容当然要跟着改。」
> 因此条款的修订**不跟路线图走、也不跟"将来会不会接服务端"走，只跟当前代码走**：
> 代码里实现了什么，条款就写什么；代码没实现的事，条款一个字都不许提前透露。

### 12.1 裁决一：`/privacy/` 的「不上传、不云同步 / 无注册无登录」

**裁决：现在就改，不等接服务端。**

做法（已随本次一并落地）：

| 今天的写法 | 改成 | 依据 |
|---|---|---|
| 「不需要注册」 | 「**不需要注册也能用全部功能**；也可选填邮箱建一个**只存在本机的账号**」 | 代码里有 `AuthCore` 的 local/code 模式（本机落盘），但没有服务端 |
| 「不上传、不云同步」 | 「**不上传、不云同步**：目前没有任何服务器，全部数据（含账号记录）只在本机」 | 事实未变 —— 本期确实一个请求都不发 |
| 「不收集手机号、邮箱、姓名…」 | 「不收集手机号、姓名、学校、位置；**邮箱仅在你自己主动填写时收集，且只以摘要 + 掩码存在本机**，不发送给任何第三方」 | 邮箱算个人信息（见 12.3），"什么都不收集"已不准确 |

**为什么不是"等接服务端时统一改"**：如果页面上已经出现"用邮箱登录"，
而条款仍写"无注册、无登录"，那条款就是一句**当场被自己违反**的话；
反过来，若为了保住旧条款而把 `/login/` 藏起来不进导航，那条款就成了**代码的枷锁**，
违反用户刚立的原则。按"条款跟随代码"的口径，正确做法是：
**代码实现到哪一步，条款就如实写到哪一步**——本期如实写「本机账号、无服务器、不发请求」。

落实清单（本次已做）：
- `privacy/index.html`：§一「收集什么」、§二「数据存在哪」、§三「儿童隐私」三处改写
- `terms/index.html`：§2「使用方式」、§5「儿童信息」两处改写
- `test/legal.test.js`：断言从「无注册无登录」改为「**本地账号 + 不上传不云同步**」，
  并新增一条**反向断言**：条款里**不得出现**「云同步」「已接入服务器」等未实现的说法
  （防止文案跑在代码前面 —— 这是比"文案落后"更糟的错）

### 12.2 裁决二：`grade / term / scope / dailyCount / algo` = **账号域（跨设备一致）**

**裁决：算，保持跨设备同步。**

依据：这五个字段直接决定「排哪几首、每天几首、怎么复习」。若各自为政，
会出现「电脑上背三年级上册、手机上排二年级下册」——同一份进度、两套排程，
是比"字号不一致"严重得多的错误。因此：

| 字段 | 归属 | 同步 |
|---|---|---|
| `grade`（年级） | **账号域** | ✅ |
| `term`（学期） | **账号域** | ✅ |
| `scope`（背诵范围） | **账号域** | ✅ |
| `dailyCount`（每日数量） | **账号域** | ✅ |
| `algo`（复习算法） | **账号域** | ✅ |
| `username`（昵称） | **账号域** | ✅ |
| `helper`（注音开关） | 设备域 | ❌ |
| 字号 / 对齐 / 连读档 / 播放模式 / iOS 引导条 | 设备域 | ❌ |

**这条裁决有连带影响，必须写清（否则会做成"改名不生效"或"一同步就全变"）**：

1. 现在 `grade/term/scope/dailyCount/algo` 与 `username/helper` **同躺在
   `poem_recite_settings_v1` 一个对象里**（见 §9 与 Issue #132 的阶段 0 设计）。
   要让前五个"跨设备一致"、后一个"各设备不同"，
   **本阶段 0 的"设置域按字段拆家"就从"建议"变成"必须"**：
   - 账号域 → `poem_recite_settings_v1`（沿用旧键名，最小改动）+ `poem_profile_v1`
   - 设备域 → `poem_device_prefs_v1`

   > ✅ **已落地（2026-09-15）**：`js/progress-store.js` 是这三域的唯一一份定义，
   > `js/storage.js` 退化成薄转发层。拆家**本期只动了 `helper` 一件** ——
   > `grade/term/scope/dailyCount/algo` 本来就该留在老键里（账号域沿用旧键名），
   > 字号 / 对齐 / 连读档 / 播放模式仍然原地不动（设备域的老键）。
   > ⚠️ **一个实测顶出来的口径**：`helper` 写的时候必须**两把键一起写**
   > （新键是正主、老键里那份是镜像），因为集子页与设置页至今从老键读它；
   > 只写新键会出现「首页说已开启、集子页是纯文本」。
   > 导出备份时 `settings.helper` 也要带上（老版本导入时才不会把它变回默认）。
   > 落地细节与另外两处偏差见 `docs/architecture.md` §3.3 / §3.4。
2. **改了账号域设置要能触发重排**：`scope/grade/term` 一变，`poem_plan_*` 缓存必须失效
   （现有逻辑已有失效机制），跨设备同步到达时**同样要清缓存重算**，否则"同步了但今日任务没变"。
3. **`profile.nickname` 就是账号域里的 `username`**（§2.1），两者不是两回事。

### 12.3 裁决三：登录时「两边都有且无法判断来源」→ 弹选择

**裁决：认同。弹「保留本机 / 保留账号 / 先导出再决定」三项。**

即 §9 表格里的 **D 场景，正式定为"不自动合并"**，三个选项各自的语义：

| 选项 | 做什么 | 风险 |
|---|---|---|
| **保留本机** | 用本机进度覆盖账号，并把本机进度推到账号 | 账号侧旧进度被覆盖（但用户已看到两边篇数） |
| **保留账号** | 用账号进度覆盖本机 | 本机进度被覆盖（**先自动存一份本机快照**，可回退） |
| **先导出再决定** | 把本机进度导出为 JSON 文件（复用 `Storage.exportJSON`），停在选择页不写盘 | 无 |

配套三条硬规则（写进测试）：
1. **弹选择之前，两个选项的"篇数 / 截至时间"必须都显示出来** —— 不让用户在不知道代价的情况下选
2. **"保留账号"前先静默落一份本机快照**（`poem_pre_merge_backup_v1`），给后悔药
3. **只读页面（首页浏览、集子页翻阅）绝不触发该弹窗**，也不写任何盘
