## 0. 一句话结论

**主键选邮箱，登录凭证一律走邮箱随机码（无密码）；本期全部落在浏览器本机，
不发送任何网络请求；服务端只是「同一份协议换一个实现」，届时客户端零改造。**
短信登录不是「另一套流程」，只是 `channel: "email" | "sms"` 的一个取值 —— 见 §8。
条款口径已按「**条款永远跟随代码**」裁决并落地：代码实现到哪，条款就如实写到哪，见 §12。

## 1. 三条不可退让的边界（先立规矩，再谈流程）

1. **不花钱、不备案也能跑**
   本期不买短信、不买域名、不买服务器。邮箱通道由用户自己的邮箱服务商提供。

2. **不破坏「打开即用、可离线」**
   没登录的人，功能与今天**完全一致**。账号只增加「数据不丢」与「跨设备同步」两件事，
   不拿任何现有功能当人质。

3. **不假装安全**
   本期没有服务端，所有校验都在用户自己的浏览器里，**任何人都能绕过**。
   因此本期定位是「身份与数据的归属登记」，不是「防篡改的鉴权」。
   凡是用它当收费/权益凭据的用途，**本期一律不做**（详 §3.4、§12）。

## 2. 术语与账户形态

| 术语 | 含义 |
|---|---|
| **账号** | 一行账号记录，主键是 `uid`（不可变），登录标识是邮箱 |
| **身份标识 identity** | `{channel, value}`，如 `{email, a@b.com}`、`{sms, 138…}` |
| **会话 session** | 一次登录的凭据，本期为 30 天有效 + 可续期 |
| **随机码 code** | 短时效、单次使用的登录码，取代密码 |
| **档案 profile** | 账号下的展示信息（昵称），**不是儿童实名** |

### 2.1 账户形态：一人一账号，儿童不做独立账号

跬步面向家庭。**只允许成年人建号**，孩子的昵称是账号下的一个「展示名」，
不是独立账号（理由：未成年人实名/同意合规成本高，且无任何产品收益）。

- `profile.nickname` 就是今天设置页的那个「用户名」，`maxlength=12`，纯展示
- 账号可以登记多个昵称（`profiles[]`），将来做「家庭子档案」时不用改表结构
  > ✅ **已落地（2026-09-17，Issue #159）**：`profiles[]` 的形状真的没改
  > （`poem_profiles_v1 = {v:2, profiles:[{id,nickname,avatar,born}], current}`），
  > 表结构一行未动（`accounts` 至今没有 child / parent / family_id 任何一列）。
  > 「多个孩子各背各的」不是靠给孩子建账号，而是靠**本机的键分家**：
  > 进度 / 设置 / 已读跟着子档案走，设备域不跟（`docs/architecture.md` §5.2 ④）。
- **本期不做「图片头像」**（用户上传一张图）：一律不收集用户的图片
  —— ⚠️ 口径已收窄，见 §2.3：**做字符印头像，不做图片头像**
- **本期不做生日/学校/年级实名**：一律不收集

### 2.3 头像口径：做**字符印**，不做图片头像（2026-09-15 裁）

用户裁决（Issue #132，2026-09-15）：「头像建议听你的」「点头，要做，然后按合规的思路去做」。
本文的裁定：**图片头像现在不做，字符印现在就做**，落地为 `js/avatar.js`（纯逻辑、零 DOM、零网络）。

**为什么不做图片头像**：它的每一项成本 —— 对象存储、内容审核、CDN、
**儿童真人照片上传** —— 都由「用户上传一张图」这一件事引爆，
而它对「背诗」这件事毫无帮助。免费 Supabase 那 1 GB 存储**够放**十万张 96×96 WebP
（约 6~10 KB/张），所以瓶颈从来不是容量，是三件事：

1. **CDN 加载不可控** —— 头像每页都渲染，加载不出来就是
   「全站每个页面右上角都有个坏图标」，比不做的观感差得多
2. **儿童真人照片上传是最敏感的一类个人信息** —— 头像通常就是真人照片；
   进度上云已裁为「上」（`docs/architecture.md` §4.2，方案 B，2026-09-15），
   但这不构成「连头像也一起传」的理由，头像比进度敏感一个量级
3. **它把 `/privacy/` 的「默认只存本机」当场作废** —— 为一张头像破这条，性价比是负的

**字符印是什么**：一枚圆的方角印（`border-radius: 26%`），里面一个汉字。
内容源**只有两个**：用户从**固定字集**里挑的一个字、昵称的第一个字；
底色只有**固定四色**（朱砂 / 天青 / 松绿 / 赭石）。全部存本机，盘上不到 100 字节。

**四档次序与默认值**（`Avatar.display()` 的可测规则）：

| 档 | 字从哪来 | `source` | title 文案 |
|---|---|---|---|
| ① | 用户选的字（`avatar.char`） | `chosen` | 「你选的字」 |
| ② | 昵称第一个字（按**码点**取，不劈开 emoji） | `nickname` | 「取自昵称首字」 |
| ③ | 默认「诗」字（与 App 图标同源） | `default` | 「默认字」 |

**三条硬规矩**（`test/avatar.test.js` 逐条钉住）：

1. **永不空**：任何脏值 / 解析失败 / 没有存储，都回落默认「诗」字，绝不出裂图
2. **不用邮箱首字母**：那等于把邮箱摘要的一半直接画在屏幕上，与
   §6.1「邮箱只以摘要 + 掩码存在本机」自相矛盾
3. **不做 base64 存图**：会把 localStorage 撑爆，还污染导出备份；
   渲染走 `<span>` + 一个字符，不发任何请求

**固定字集**（12 字）：诗 书 山 月 风 云 松 竹 梅 兰 菊 莲。
不弹键盘让用户自由输入 —— 自由输入会带来生僻字（字体子集里没有，半个字被吃掉）
与「填了真名/学校」这类要审核的内容；固定集合把这两个问题一次消掉，
也让字符印真的只是「从枚举里挑一个索引」。**集合外的字与任意色值一律拒收**（不写盘）。

#### 2.3.1 档案键 `poem_profile_v1`（账号域）

头像与昵称**住同一份档案**（`docs/architecture.md` §3.1 已裁决 `username` 属账号域）：

```jsonc
// localStorage: poem_profile_v1
{
  "v": 1,
  "nickname": "小明",                        // = 今天设置页那个「用户名」，maxlength 12
  "avatar": { "char": "梅", "ink": "pine" }  // 都可是空串：空 = 回到三档回落
}
```

- `char` 必须是 `Avatar.CHARS` 里的一个，`ink` 必须是 `INK_KEYS` 里的一个
- 非法 / 缺省值**归一化为空串**（不是写成默认字）——
  「盘上没存过」与「用户主动选了诗」必须能分开，界面 title 才能如实写来源
- **兼容读**：昵称取值 `poem_profile_v1` → 老 `poem_recite_settings_v1.username` → 空串
  （`Avatar.nickname()` 已按此实现）
- **本轮的写**：设置页/首页改昵称时**同时**写 `poem_profile_v1`（新增，镜像）
  与老 `settings.username`（**不动**，各页仍在读它）——
  两条键在此期间保持一致，老代码零改动。
  ⚠️ 「写新键 + 清老字段」那一步属于**阶段 0 的 `ProgressStore` 迁移**
  （`docs/architecture.md` §3.1 ④），本轮不做：清老字段会牵动
  `js/storage.js` 的 `getSettings()` 与三个写入点，超出头像这件事的范围
- **不碰设备域**：头像属身份不属设备偏好，进 `poem_profile_v1`
  而不是 `poem_device_prefs_v1` —— 手机与电脑上必须是同一枚印

#### 2.3.2 分域隔离（对照 `docs/architecture.md` §3.1 的拆家表）

| 键 | 归属 | 头像会写它吗 |
|---|---|---|
| `poem_profile_v1` | **账号域**（跨设备一致） | ✅ 只有它 |
| `poem_device_prefs_v1` | 设备域（各设备不同） | ❌ 绝不 |
| `poem_recite_progress_v1` | 进度域 | ❌ 绝不 |
| `poem_plan_grant_v1` | 权益发放名单 | ❌ 绝不（头像与权益是两件事） |

#### 2.3.3 条款：`/privacy/` 只需**如实补一句**

字符印不是「用户产生的内容」，是从枚举里挑的索引，**不构成收集**：
`/privacy/` 现有那句「昵称请只填小名」不用动、「不收集」承诺继续成立。
本轮只在「存在本机」那条的枚举里补上「头像印记」，口径仍是
「全部通过 localStorage 只保存在你的设备上，不上传、不云同步」。

⚠️ **一旦哪天改成允许上传图片，三处必须同时改**：
`/privacy/`、`/terms/`、`test/legal.test.js` 的反向断言，
并按「条款跟随代码」原则，代码没实现就不许提前写。

### 2.2 账号记录（与存储实现无关的字段定义）

```jsonc
{
  "uid": "u_8f3k2m9q",          // 不可变主键，永不复用
  "identities": [                // 登录标识，可多枚，每枚唯一
    { "channel": "email", "value": "a@b.com", "verifiedAt": "2026-09-15T02:00:00Z" },
    { "channel": "sms",   "value": "13800138000", "verifiedAt": "—" }   // 未来
  ],
  "profile": { "nickname": "小明" },
  "createdAt": "2026-09-15T02:00:00Z",
  "updatedAt": "2026-09-15T02:00:00Z",
  "lastLoginAt": "2026-09-15T02:00:00Z",
  "status": "active",            // active | suspended | deleting | deleted
  "plan": { "tier": "free", "until": null },   // 本期恒为 free，预留 pro/max
  "security": {
    "pwVersion": null,           // 无密码方案，留字段以便将来"改密"兼容
    "codesToday": 3,             // 当日发码次数（频控用）
    "codesDay": "2026-09-15",
    "failCount": 0,              // 连续失败次数
    "lockedUntil": null
  }
}
```

**五个硬约束**（写在测试里，见 §10）：
- `uid` 一旦分配，**永久不复用**（注销后也不回收，避免「新用户接管旧数据」）
- `identities[].value` 在**同一 channel 内唯一**；邮箱一律 `trim + 小写` 后比对
- 真实邮箱**不以明文落盘**（本期存 `emailHash + 掩码`，见 §6.1）
- `plan` / `security` / `status` **不属于用户可编辑数据**，导入备份时忽略
- 只有 `channel: "email" | "sms"` 两种，其余 channel 直接拒绝

## 3. 认证的三种模式（本期只开前两种）

| 模式 | 触发 | 适用 | 本期 |
|---|---|---|---|
| **本机模式**（local） | 默认 | 只想用、不想给邮箱 | ✅ |
| **邮箱码模式**（code） | 用户主动「用邮箱登录」 | 换设备、防数据丢失 | ✅ |
| 服务端鉴权模式（server） | 将来接后端 | 权益校验、支付 | ⛔ 预留 |

三者**共用同一套界面与同一个账号对象**，区别只在「谁签发会话」：

```
local  : 会话由 AuthCore.issueSession() 本机签发，scope = "local"
code   : 会话由服务端在 verify 成功时签发，scope = "account"
```

### 3.1 为什么用「随机码」而不是「密码」

- 家长群体记不住密码，**忘记密码是最高频的求助**
- 无密码就没有「密码泄漏 / 撞库 / 加盐存储」这一整类问题
- 与将来的短信登录**语义完全一致**：都是「一次性短码换会话」
- 代价：每次登录都要收信 —— 用 §6.3 的「设备信任期」抵消

### 3.2 为什么不是「邮箱 + 密码」「用户名 + 密码」

- 用户名登录要做昵称查重 + 找回 + 防枚举，成本高于收益，且与现有 `username` 展示语义冲突
- 自建密码存储要么自研（风险高）要么依赖后端（本期没有）

### 3.3 为什么不是第三方 OAuth（Google/GitHub/微信）

- 面向国内家长，Google/GitHub 无意义
- 微信网页授权需要 **已认证服务号 + 企业主体 + 备案域名**（详见 issue 前序讨论），与「不花钱」冲突
- 但**接口留了口子**：`identities[].channel` 可以扩到 `wechat`，`linkIdentity` 流程不变
- ⚠️ 微信登录（以及**微信小程序版**）已进「现在不做、以后做」的清单：
  [`docs/todo.md`](todo.md) 第 2、3 条

### 3.5 权益总闸：free / pro / max 三层（已落地，2026-09-15 裁）

> 所以上面那张表里的「飞花令 / 现场考试」是 **Max** 起，题库复习是 **Pro** 起 ——

落地为 `js/entitlement.js`（纯逻辑、零 DOM、零网络），三条规矩：

1. **唯一出口**：全站只允许 `Entitlement.can(cap, ctx)` 回答「能不能用」。
   页面里不许出现 `plan === "pro"` / `tier === "max"` 这类判断（有源码扫描测试守住）。
   将来本机发放名单换成服务端 `/api/me` 下发时，**只换这一个实现**，页面一行不动。
2. **免费不残缺**：free 拥有今天能用的**全部**功能（261 首课内 + 2320 篇集子 +
   排程 + 注音 + 导出 JSON）；pro / max 只**加**新能力与额度，不收回任何现有功能。
3. **登录是语音播放的硬条件**：`read.aloud` 这一条能力 `login: true` ——
   游客不能用，登录后的 free 可以用。判据写在**声音的唯一出口** `js/speech.js` 里，
   按钮的置灰状态读 `Speech.allowed()`，两者同源，不会出现「按钮亮着却没声音」。

> ⚠️ **额度不同的能力不许互为别名**。`ai.explain`（pro，50 次）与
> `ai.explain.big`（max，500 次）一度写成一条别名，结果 pro 也拿到了 500 次档；
> 现在是两条独立的能力，各有自己的 `minTier` 与 `quota`（测试里顶回来的）。

**本机发放名单**（`poem_plan_grant_v1`）：管理员按**邮箱掩码**发层级，
可导出 / 粘贴到另一台设备，登录取到掩码后匹配生效。
本期明说清楚：**这是「手工发邀请码」的本机版，对方改存储就能升级** ——
真正的权威发放要等 1 期服务端（`POST /admin/grant`），届时名单文件原样搬过去。

> ✅ **2.2 已落地（2026-09-17）**：权威发放做完了，但**名单文件没有「搬过去」** ——
> 落地时发现「搬」这个说法本身就不对。真正权威的那一份**从来不是一份名单文件**，
> 而是 `accounts.plan` / `accounts.plan_until` 那两列：
> 多维护一张「发放记录表」，就多一处会与账号本身漂移的地方
> （而那张表一旦与 accounts 对不上，「收回」这件事就有一半不生效）。
>
> 所以现在的形态是：
>
> | | 服务端（权威） | 本机（降级路径） |
> |---|---|---|
> | 存在哪 | `accounts.plan` / `plan_until` | `poem_plan_grant_v1` |
> | 接口 | `POST /api/admin/grant`、`POST /api/admin/grants`（读）、`DELETE`（收回） | 无（就存在本机） |
> | 传不传得出去 | 不用传 —— 对方刷新即生效 | **要对方自己导入** |
> | 改得动吗 | 改不动 | 改一行存储就能改 |
>
> **两份不自动同步**：本机名单那条「传不出去」的局限**仍然成立**，
> 只是它不再是唯一的路（`docs/architecture.md` §4.14）。
> 发放的**前提**是对方先登录过一次（库里得先有那一行）——
> `matched:0` 如实回，**不建幽灵账号**（掩码不可逆，造出来的是永远登不上的行）。

### 3.6.2 账号入口动线（D 步，已落地）

三张账号页建好之后，剩下**最后一块**：从一个「未登录的人」到 `/login/` 的路。
这一块不写清楚，页面就只是「存在」，用户找不到 —— 那比不建更浪费。

**四页签里没有账号的位置**（背诵 / 课外 / 搜索 / 设置，每格才两三个字，
再加一格手机上一行就挤变形，`test/ui-consistency.test.js` 守的就是这件事）。
所以入口只能从「已有结构」里长出来，一共三个落点：

| 落点 | 谁渲染 | 指向 | 什么时候出现 |
|---|---|---|---|
| 顶栏右上角那枚**印** | `js/chrome.js` | `/profile/` | **每一页、每一状态**（未登录也画，那是恒定的身份锚点） |
| 个人中心身份卡里的**账号入口** | `js/profile.js` | `/login/` | 总是（这就是它的存在理由） |
| 设置主页那张**账号卡** | `js/settings-nav.js` | 未登录 → `/login/`；已登录 → `/profile/` | 设置主页顶上，四条入口之前 |

**两条独立的路**：未登录的人的动线是
① 首页那枚印 → `/profile/` → 账号入口 → `/login/`，
或 ② 设置主页 → 账号卡 → `/login/`。任一文件漏了，都还剩一条 —— 但也只剩一条。

**返回落点**（`data-back`，由 `js/chrome.js` 的 `pageBackHref()` 统一出）：

```
/login/     → /profile/    （登录是身份的事；落回设置页等于又多绕一层）
/profile/   → /settings/   （入口在设置里）
/admin/     → /profile/    （管理后台是从个人中心进去的）
/settings/general/ → /settings/  （四张二级页同一条）
```

登录**成功之后**也回 `/profile/` —— 与顶栏返回键同一条动线，不出现两条。

**两条刻意收着的口径**：

1. **已登录时不再摆「去登录」**（自相矛盾）。设置主页那张卡此时换成
   「一行身份 + 个人中心」；想退出 / 注销的人在个人中心里，与那两件事放在一起。
2. **不做「到了 `/login/` 就把已登录的人弹回来」那种聪明** ——
   点一下就被弹回去，用户只会以为按钮坏了。`/login/` 自己认会话与信任期：
   信任期内顶部给「继续以 `a***@b.com` 进入」，会话还在时同样能继续。

**设置主页那张卡是「自己会收敛的」**：拿不到内核（老缓存、脚本顺序不对）时
**整张卡不画**（`#account-entry` 保持 `hidden`），宁可少一张卡，
也不长出一颗点了不知道去哪儿的按钮。

### 3.6.1 `/login/` `/profile/` `/admin/` 三张页（已落地）

「账号」在设计里活了很久、在界面上一直只是一行只读状态。三张页落地之后，
它第一次成为**用户可以自己走完的流程**：

| 页 | 做什么 | 不做什么 |
|---|---|---|
| `/login/` | 输邮箱 → 收码 → 填码 →（可选）补昵称；信任期内一点即入 | 不假装有服务器（见 §7.1）；不发任何网络请求。「重设凭证」那块页面入口已撤（#163：一页只有一套「输邮箱 → 收码」表单），能力本身保留 |
| `/profile/` | 印 + 昵称 + 掩码 + 层级徽章；本机数据概览；权限清单；退出；注销（二次确认 + 重输邮箱）；`owner` 时给管理入口 | 不改昵称与头像（那在设置 · 通用里）；不摆点了没反应的按钮 |
| `/admin/` | 按邮箱掩码发放层级；名单增删；导出 / 导入；「以 Free 身份预览」；清空（二次确认） | 非 `owner` 时**整页如实拒绝**且不渲染任何发放信息 |
| `/plans/` | 四列（未登录 / Free / Pro / Max）逐条对照；「你现在在这」那一列高亮；表尾每列可用项数（见 §3.6.2） | 不做收款、不做促销话术；不写任何存储 |

**四条硬规矩（已钉进 `test/account-pages.test.js`）：**

1. **页面不许自己拼 `plan` / `tier`** —— 徽章与清单一律走
   `Entitlement.tierLabel()` / `matrix()` / `isOwner()`；页面里不出现
   `poem_plan_v1` / `poem_plan_grant_v1` / `poem_owner_v1` 任何一个键名
2. **本地体验版必须如实标注** —— `/login/` 上写着「本应用没有服务器，
   随机码由你这台设备生成」；文案用的是「已**生成**随机码」而不是
   「已发送」；有反向断言拦着「邮件已发送」这类说法
3. **退出与注销都不碰进度** —— 界面上如实写出来。实测：注销后
   `poem_recite_progress_v1` 与 `poem_profile_v1` 原封不动
4. **三张页一个字节都不写进度键** —— 有源码扫描守着（六把进度/设置键名一律不许出现）

**`role` 与 `tier` 是两条正交的轴。** `Entitlement.isOwner()` 是全站唯一
回答「谁能进管理后台」的函数，落在 `poem_owner_v1` 上：

> ⚠️ **2.2 起要分清两件事**：`isOwner()` 管的是「这一页画不画给你」，
> 而**真正拦人的是服务端**（`accounts.role`）—— `POST /api/admin/grant`
> 对有会话但不是 owner / admin 的请求如实回 **403**。
> 「入口藏起来」**不是**安全边界，这条从 1A 起就写着，2.2 让它第一次**真的成立**
> （在那之前，服务端根本没有能改别人数据的接口，所谓安全边界无从谈起）。

- **首次打开的这个浏览器自动成为本机主人**（幂等）。没有这个兜底，
  `/admin/` 会永远对所有人关着，那一页等于不存在
- `/profile/` 的管理入口与 `/admin/` 的准入**走同一个出口** ——
  不会出现「入口看得见、点进去被拒」这种自相矛盾的组合
- 层级仍是 `free`：**管理员不是「买了 Max 的人」**
- 1 期接服务端后 `isOwner` 改读 `/api/me` 下发的 `role`，页面一行不动

**`js/admin-page.js` 这个名字有来历。** 管理页的逻辑**不叫** `js/admin.js`：
早年「访问统计」被整体删除时，`js/admin.js` 正是那个统计脚本的名字，
而 `test/legal.test.js` 立了一条反向断言「这个文件必须不存在」。
复用同名会让那条**正确**的防线变红 —— 改名比改断言好（断言守的是事实）。

**顶栏头像这一轮也改了规格**（用户 2026-09-15 要求）：
「右上角方形圆角还是替换成和 logo 一模一样大小的圆形」。
于是顶栏那一枚与 `.brand-mark` **同径 42px、整圆、印色铺满**，
`js/chrome.js` 不再自己传 `size`（尺寸只剩 CSS 一处来源）。
同时头像的落点从「暂定设置页」回到 `/profile/` ——
「点头像看自己」是肌肉记忆，中间隔一层设置页就不叫锚点了。

### 3.6.2 `/plans/` 层级对比页（已落地，2026-09-15 用户提）

用户的原始问题（Issue #132）：

> 「我看到了个人中心有个权限部分，这部分内容是不是应该有个专门的像其他网站
> 不同角色进行 4 列或者 5 列对比页面？最左侧是对比项目，右侧四列分别是匿名用户、
> 登录 free 用户、登录 pro 用户、登录 max 用户，下面用好看的打钩或者打叉。」

落地为 `/plans/`：**四列 × 逐条对照**，从 `/profile/` 的「权限」进去，看完就走。

| 列 | 是什么 | `can()` 收到的 ctx |
|---|---|---|
| 未登录 | 游客（匿名） | `{ tier: "free", signedIn: false }` |
| Free | 登录后的免费层 | `{ tier: "free", signedIn: true }` |
| Pro | 登录后的 Pro | `{ tier: "pro", signedIn: true }` |
| Max | 登录后的 Max | `{ tier: "max", signedIn: true }` |

**为什么是四列而不是把「游客」并进 free：** 游客与 free 之间差的是
`signedIn` 这个布尔，不是层级。今天全表只差一条（`read.aloud` ——
语音朗读要登录），但它恰恰是最容易被误解的一条（用户会把
「游客不能听」读成「免费版不能听」）。**单独一列，是把这件事说清楚的唯一办法。**

**这张表不许手抄。** 每一格都由 `Entitlement.compare()` 当场问 `can()` 算出来
（与 `/profile/` 的清单同源：那边是 `matrix()`，这边是 `compare()`）。
手抄一份的下场是内核改了门槛、这张表还是老话 —— 而这张表恰恰是
**用户唯一会逐条对着看的页面**。`test/plans-page.test.js` 里有一条断言
把「每一格 === `can()` 的答案」逐格比一遍，不一致就红。

**三条已经钉进测试的口径：**

1. **未登录 ≠ free，且只差一条** —— 断言直接数「两列不一致的能力条数 === 1」，
   将来多锁一条免费功能会立刻红（那正是要人来确认的事）
2. **单调不回退** —— Free 有的 Pro 一定有、Pro 有的 Max 一定有。
   这条防的是「顺手把某项标成 pro-only 就把它从 free 收走了」这类误伤
3. **表尾必须与表身相符** —— 「能用 12/15」这种数字由同一份 `cells` 算出来，
   不许另算一遍（两个数字对不上是最难解释的 bug）

**诚实口径（本期特有）：** 表尾写明层级是**本机登记**、**不是付费凭据**、
没有收款也没有支付入口；页面里不出现「立即购买」「限时优惠」这类话
（本期确实收不了钱，写上就是假的）。`/plans/` 一个字节都不写存储 ——
看表不该留下痕迹。

## 3.6 「账号」在界面上长什么样（已落地在 /settings/general/）

设计走到这一步，账号一直只活在 `js/auth-core.js` 里 —— 用户看不到它。
二级设置页给了它唯一的展示位：`/settings/general/` 的「账号」这一项。

**只读展示 + 退出，不做别的**（理由：`/login/` 与 `/profile/` 还没建，
做半截的登录流程比不做更糟）：

| 状态 | 界面写什么 |
|---|---|
| 未登录 | 「未登录（游客）」+ 层级徽章（Free）+ 一句「不登录也能用全部功能；账号只影响语音朗读与将来的同步」+ 指向 `/login/`（还没建） |
| 已登录 | 「已登录」+ 邮箱掩码（`a***@b.com`）+ 层级徽章 + **权限清单**（`Entitlement.matrix()` 逐条列出能用什么、门槛是什么）+ 一颗「退出登录」 |

> ⚠️ 上表是当时（账号页还没建）的口径，**已被后续几轮覆盖**，只留作历史：
> - 权限清单从设置页与个人中心先后撤掉，只剩 `/plans/` 一处（Issue #163）；
> - 「登录取向」的文案收成三个字：**「登录可用」**（Issue #163 第三轮，
>   `Entitlement.denyReason()` 里那一句就是全站唯一来源）；
> - 个人中心那张「未登录引导卡」整块撤掉，事实写在那一颗按钮上
>   （「登录可用语音朗读」）。当前口径见 `docs/architecture.md` §4.18。

三条硬规矩：

1. **页面上不许自己拼 plan / tier** —— 徽章文案与权限清单都走
   `Entitlement.tierLabel()` 与 `Entitlement.matrix()`，`test/entitlement.test.js`
   的源码扫描守着（「页面上不许自己拼 plan」那一条）
2. **退出只清会话** —— `AuthCore.signOut(store)` 的第一句注释就是
   「只清会话，绝不碰进度数据」，界面上也如实这么写：「退出只结束这次登录，
   不会删掉任何背诵进度」
3. **注销不做假动作** —— 注销要「二次确认 + 重输一次邮箱」，那一步依赖
   `/profile/`（还没建），所以界面上**只给退出**，并如实写明「注销账号在
   个人中心（/profile/）里做」，不摆一颗点了会 404 的按钮

顺带钉住的合规口径：账号那一项**原样复述** `/privacy/` 的那句话 ——
「本机账号与进度一样只存在本机，不上传、不云同步」。
条款怎么写，界面就怎么写（§12 的「条款跟随代码」）。

## 4. 完整流程：注册 / 登录 合一

**注册与登录是同一个动作**（邮箱码方案的天然优势）：输邮箱 → 收码 → 填码 →
若该邮箱没有账号则建号，有则登录。用户不需要理解「我在注册还是登录」。

```
[入口] /login/
  │
  ├─ ① 输邮箱 ─────────────────────────────────────────────┐
  │    · 前端校验格式（宽松：本地部分不校验字符集大小写）      │
  │    · 归一化：trim → 小写 → 去掉零宽字符                  │
  │    · 命中「一次性邮箱前缀表」→ 提示但**不阻断**（§6.5）    │
  │    · 频控检查（§6.2）：邮箱 / 设备 / 全局三层            │
  │                                                          │
  ├─ ② 点「发送随机码」 → requestCode(identity, purpose)      │
  │    · 生成 6 位数字码（§5.1）                             │
  │    · 本机存 code 记录（§5.3），**不存明文码**（§5.4）      │
  │    · 本期：唤起 mailto: 预填主题与正文（§7）              │
  │    · 服务端版：调 POST /auth/code → 邮件由服务端发         │
  │                                                          │
  ├─ ③ 用户去邮箱取码，回来填 6 位 ─────────────────────────┤
  │    · 6 格数字输入框，自动跳格、支持整段粘贴                │
  │    · 每隔 1 秒检查一次过期，剩余时间倒计时显示             │
  │                                                          │
  ├─ ④ verifyCode(uid, code, purpose)                       │
  │    · 命中 → 建号/取号 → 签发会话 → 进 ⑤                 │
  │    · 不中 → failCount++，按 §5.5 的阶梯锁定              │
  │                                                          │
  └─ ⑤ 登录成功
       · mergePolicy：把本机未登录的进度「认领」进账号（§9）
       · 若 profile.nickname 为空 → 提示补昵称（沿用今天那 12 字输入框）
       · 跳回来源页；PWA 下不整页刷新
```

### 4.1 状态机（不可跳步；每条转移都有测试）

```
idle ──enterEmail──▶ emailEntered ──requestCode──▶ codeSent
                          ▲                            │
                          │                            ├──verify ok──▶ signedIn
                          │                            ├──verify bad─▶ codeSent (failCount+1)
                          └────resend / editEmail──────┤
                                                       ├──expired────▶ codeExpired ──resend──▶ codeSent
                                                       └──locked─────▶ locked ──wait/换设备──▶ idle
signedIn ──signOut──▶ idle
signedIn ──deletingAccount(二次确认)──▶ signedOut+erased
```

规则：
- `codeSent` 下**可以改邮箱重发**，但会清掉旧码（不允许两个邮箱的码并存）
- 任何一步刷新页面，状态从本机 `pending` 记录恢复（`codeSent` 可续）
- `locked` 是终态之一，**不因为重试自动解锁**，只能等 `lockedUntil`

## 5. 随机码规则（安全核心）

### 5.1 码的形态

| 项 | 值 | 理由 |
|---|---|---|
| 字符集 | `0-9`（纯数字） | 邮箱里好认好输，无 O/0 混淆 |
| 长度 | **6 位** | 10^6；配合 §6.2 频控足够 |
| 有效期 | **10 分钟** | 够慢手用户；比常见的 5 分钟宽松一点 |
| 使用次数 | **1 次**（成功即失效） | 防重放 |
| 校验失败上限 | **5 次** | 之后该码作废，必须重发 |
| 比较方式 | 定长比较 + 失败也走完循环 | 防时序侧信道（服务端实现要求） |

### 5.2 用途绑定 purpose（同码不同用，互不通用）

```js
PURPOSE = {
  login:  "登录 / 注册",     // 双方共用一个 purpose
  reset:  "重设凭证"         // 本期无密码，等价于"吊销全部会话 + 清设备信任"
}
```

**`login` 的码不能用于 `reset`，反之亦然**。将来加 `bind`（绑定新邮箱/手机号）时同样独立。

### 5.3 码记录（落盘形态）

```jsonc
// poem_auth_v1.codes[<codeId>]
{
  "codeId": "c_7f2a…",           // 随机，不是码本身
  "uid": "u_8f3k2m9q",
  "purpose": "login",
  "channel": "email",
  "sentTo": "a***@b.com",        // 掩码，用于界面回显"已发往"
  "codeHash": "…",               // 见 5.4
  "salt": "…",
  "issuedAt": 1757900000000,
  "expiresAt": 1757900600000,
  "attempts": 0,
  "consumedAt": null
}
```

同一 `uid + purpose` 同时**只保留最新一枚**（发新的即作废旧记录）。

### 5.4 不允许存明文码

- 存储层只留 `codeHash = SHA-256(uid + purpose + code + salt)`（`salt` 每码随机 16 字节）
- 用户输入时同样按此公式现算比对
- **服务端版强制要求**：任何日志、错误上报、监控里**禁止出现明文码**（写进 review checklist）
- 明文码只在两处短暂存在：① 生成它的那一次函数调用内；② 用户的邮箱里
- **id 生成不许写成「撞了就重摇」**。`codeId` / `uid` / `sid` 一律走
  「随机取一次 + 确定性线性探测」，步数上限明确。写成
  `do { x = rand() } while (撞了)` 的版本在随机源退化时是**死循环** ——
  实测的现场表现是：第一次发码正常，第二次调用整个线程卡死、不报任何错。
  这条已钉进测试（`test/auth.test.js` 第十二节）。

### 5.5 阶梯锁定（防暴力猜 6 位）

| 连续失败 | 处理 |
|---|---|
| 1~4 次 | 提示剩余次数 |
| 第 5 次（该码） | **该码立即作废**，必须重发，同时记「1 轮失败」 |
| 单账号当日发码 > 10 次 | **锁 1 小时**（`lockedUntil`） |
| 单账号连续 3 轮「发码后一次都没对」 | **锁 24 小时** |
| 全局异常（服务端版） | 单 IP / 单设备阈值触发人机校验（§11 三期） |

> ⚠️ 这条是**实测修正过的**。最初写的是「累计错 3 次就锁 24 小时」，
> 写进测试才发现它同时满足两个条件、结果反了：单枚码本身就能错 5 次，
> 正常用户手抖三次就被锁一天；而手改 localStorage 清掉计数又能立刻重来。
> 现在的判定对象是**「整轮失败」**（发一枚码 → 一次都没对 → 才算一轮），
> 既不会误伤正常用户，也不会被单枚码的 5 次重试放大成 5 倍机会。

锁定与失败计数**只认 uid，不认邮箱字符串**（防止大小写/别名绕过）。

## 6. 频控、防滥用与隐私

### 6.1 邮箱不以明文落盘（本机模式也要守）

本机模式下数据不出设备，但浏览器数据可能被导出备份、被同机他人看到。
因此账号记录里只存：

```
emailHash = SHA-256(normalized(email) + PEPPER)   // 用于查重与登录比对
emailMask = "a***@b.com"                          // 用于界面回显
```

- `PEPPER` 本机随机生成一次，存 `poem_auth_v1.pepper`，**不导出**（导出备份里剔除）
- 换句话说：拿到备份文件也**还原不出完整邮箱**，但换个设备无法用同一份账号数据登录 ——
  这是刻意的取舍：本机模式不追求跨设备，跨设备要等三期有服务端

### 6.2 三层频控（每层独立计时，**取最严**）

| 层 | 键（哈希后） | 限制 |
|---|---|---|
| 邮箱 | `identityHash` | **重发冷却 60 秒**；1 小时 5 次；24 小时 10 次 |
| 设备 | `deviceId`（随机 UUID，存本机，**非指纹**） | 1 小时 10 次；24 小时 30 次 |
| 全局 | 常量 | 1 小时 20 次；24 小时 60 次（本机模式兜底） |

倒计时期间按钮置灰并显示「还需等待 47 秒」。

> 注意「60 秒冷却」与「频控档位」是两件事：前者只管「同一枚码别连点」，
> 后者管「这段窗口里一共要了几枚」。把冷却也算进频控档位，
> 会让「正常的三次重发」被误判成刷量 —— 这也是实测改过来的。
**`deviceId` 是随机生成的本地值，不采集 UA/屏幕/字体等任何指纹特征** —— 与 `/privacy/` 的
「不采集设备标识」承诺保持一致（这句承诺本身要不要改，见 §12）。

### 6.3 设备信任期（减少重复收信）

- 登录成功后，本机记 `trustedUntil = now + 30 天`
- 信任期内打开 `/login/`，顶部直接给「继续以 a***@b.com 进入」，**一点即入，不发码**
- 但**每次登录都写 `lastLoginAt`**，且会话过期后必须重新收码（信任期不等于永久会话）
- 提供「退出并取消信任本设备」，以及设置页「退出全部设备」（本期等价于清本机会话）

### 6.4 会话规则

| 项 | 值 |
|---|---|
| 有效期 | 30 天 |
| 续期 | 剩余 < 15 天且用户有操作时静默续到 30 天 |
| 存储位置 | `localStorage`（本期无服务端，HttpOnly Cookie 无意义） |
| 会话内容 | `{sid, uid, scope, iat, exp, nonce}`，**不含邮箱**；`sid` 唯一性同上 |
| 退出 | 清会话 + 清 `pending`；**不动任何进度数据** |
| 注销账号 | 二次确认 + 要求重输一次邮箱 → 清账号、会话、信任期；进度数据单独询问是否一并清空 |

> 服务端版必须改为 `HttpOnly + Secure + SameSite=Lax` 的加密 Cookie，
> **禁止用 localStorage 存长寿命 token**。本期是例外，因为它只能在用户自己机器上自我验证。

### 6.5 一次性邮箱（临时邮箱）

- 维护一份「常见一次性邮箱域名前缀表」（如 `mailinator`、`10minutemail`、`guerrillamail` 等）
- 命中时**只在发送前给一句提示**：「临时邮箱收不到后续邮件，可能丢失账号，确定继续？」
- **不阻断**：挡住的是真用户，挡不住有心人，而收益是负的
- 表本身放 `js/auth-core.js`，可由测试替换（不联网）

## 7. 【关键】本期没有后端，码怎么送到用户手里

这是这份设计里唯一"将就"的地方，必须说清楚，不能含糊。

### 7.1 本期的做法：本地发码 + 用户自送（明确标注为「本地体验版」）

1. 前端生成码，存哈希到本机
2. 点击「发送随机码」→ 界面弹出一个本地对话框，内含：
   - 复制按钮：把码复制到剪贴板
   - `mailto:` 按钮：打开用户自己的邮箱客户端，主题/正文预填「【跬步】登录码 XXXXXX」
   - **明文提示**：「当前为本地体验版：本应用没有服务器，码由你自己保管。
     真机上请勿把码发给他人。」
3. 用户回填即可登录

**它不比「输两次邮箱」更安全，也不比它更不安全** —— 因为它本来就是本机自证。
所以**绝不能把它宣传成"邮件认证已经做好了"**。

### 7.2 服务端版（**1A 期已落地**，接口见下）

> ✅ **已实现**（2026-09-15）。落地时路径从设计里的 `/auth/*` 改成 `/api/*` ——
> Vercel Serverless 的目录约定就是 `api/`，用 `/auth/*` 要多配一层 rewrite，
> 而 rewrite 会让「哪个文件对应哪个接口」变得不可见。六个接口的实现在
> `api/{send-code,verify-code,me,account}.js` 与 `api/sync/{pull,push}.js`，
> 业务内核全在 `api/_lib/core.js`（这样才写得了测试），
> 客户端的 `transport` 是 `js/auth-api.js`。
> 上面「本期的做法」（本地发码 + 用户自送）**保留为降级路径**：
> 服务端没配好 / 连不上 / 断网时自动回落，界面如实标注「本机体验版」。

```
POST   /api/send-code   {email, purpose, deviceId}   → 202 {codeId, expiresAt, cooldown, transport, delivered, store}
POST   /api/verify-code {codeId, code, deviceId}     → 200 {account} + Set-Cookie: kbsid=...
                                                       400/423 {code, message, remaining?, retryAfter?}
GET    /api/me                                        → 200 {uid, nickname, plan:{tier,until}, features[], mask,
                                                            channel:{mail,delivered,db,sms}}   ← 2C 补的开通状态
                                                       401 {code:"E_NO_SESSION"}
POST   /api/sync/pull   {since, deviceId}            → 200 {recs[], serverTime}
POST   /api/sync/push   {recs[], deviceId}           → 200 {applied, conflicts[], serverTime}
DELETE /api/account     {confirm:true, deviceId}     → 200 {deleted, export, note} + 清 Cookie
```

**与设计原稿的三处差异**（都是实测顶出来的）：

1. **`/auth/*` → `/api/*`**，理由见上（Vercel 目录约定；少一层 rewrite 就少一层不可见映射）
2. **注销不返回 `exportUrl`** —— 本期没有对象存储放导出文件。
   数据**直接随响应回**，用户自己存。假装有个下载链接比不做更糟。
3. **退出登录没有单独接口** —— 会话是签名 Cookie，前端清 Cookie 即可；
   服务端那条 `revokeSessions` 只在「注销」与「重设凭证」时用（那两件才需要真正吊销）。
   `/api/session` 那条设计里写了但 1A 没建：它会是一个「删了也不影响任何断言」
   的接口，而「无害的冗余接口」正是之后会被误用的那一类。

同一套状态机与错误码（§13），客户端只换 `transport` 实现。

> **2C 补：`/api/me` 如实自报开通状态。**
> 界面在说「由服务器判定」时，得让用户看得见**这台服务器是什么状态**：
> `channel: { mail:"sendgrid"|"console", delivered, db:"db"|"memory", sms }`。
> 三个字段全是事实，且全部取自既有判定（`cfg.mail()` / `cfg.hasDb()`），不另算一份。
> 客户端**收下但不落盘、不参与判权**（`AccountApi.channel()`）——
> 缓存一份必然与服务端真实状态漂移。
> 未登录时 `/api/me` 仍是 401，**不下发任何开通状态**。
> 开通到哪一步、缺哪个变量、怎么补：`npm run doctor`（§7.3）。

### 7.3 配置怎么核对：可执行的自检（2C）

「接服务端」这一步的配置项有 13 个，散在会话 / 数据库 / 发信 / 短信 / 冒烟五组里。
自检把「缺哪个、缺了会怎样、怎么补」一次说清，**且不部署就能问**：

```
npm run doctor                 # 人看的一段文字（可直接贴进 Issue）
npm run doctor -- --json       # 程序看的形状；退出码 = 体检结论
npm run env:example > .env.example   # 生成可直接粘贴的模板（唯一来源）
```

三档分得清：**必须**（`SESSION_SECRET`、Supabase 那一对）／
**这一件需要**（发信商密钥）／**可选**。
**一个都不配也照样能完全离线使用** —— 自检把这句话写在报告里，
免得「未配置」被读成「坏掉」。

清单定义在 `api/_lib/ops.js` 的 `ENTRY` 里，**自检与 `.env.example` 读的是同一份** ——
手抄的清单必然与代码分叉，而本项目里这种分叉已经出现过好几次。

## 9. 【关键】登录时本机已有进度怎么办

这是最容易出事故的地方。规则如下（`mergePolicy`）：

| 场景 | 处理 | 理由 |
|---|---|---|
| A. 本机进度为空，账号有数据 | 拉账号数据覆盖本机 | 新设备首次登录 |
| B. 本机有进度，账号为空（新注册） | **把本机进度"认领"进账号** | 否则用户一注册就丢光数据，最恶劣的体验 |
| C. 两边都有，且是同一账号同一设备 | 按 `id` 逐条取「复习次数多 / `nextReviewAt` 更晚」者 | 打卡要单调，不能因为同步回退 |
| D. 两边都有，但无法判断来源 | **不自动合并**，弹选择：「保留本机 / 保留账号 / 先导出再决定」（**已由用户裁决确认**，细则见 §12.3） | 宁可不合并，也不静默覆盖 |
| E. 用户在 A 设备登录了 B 的账号 | 提示「本机有另一份进度（3 首诗）」，需显式选择 | 家庭共用一台设备很常见 |

**只读页面绝不可触发任何合并或写盘**（现有测试已守这条，新增用例继续守）。

合并的粒度只到「进度记录 + 昵称 + 账号域设置」，**设备偏好一律不同步**
（字号、注音档、连读档、播放模式、iOS 引导条已关）。

**账号域 = `grade` / `term` / `scope` / `dailyCount` / `algo` + `username`**
（用户已于 2026-09-15 裁决，见 §12.2），
**设备域 = `helper` / 字号 / 对齐 / 连读档 / 播放模式 / iOS 引导条已关**。
这条口径沿用 Issue #132 阶段 0 的裁定，并且它决定了「阶段 0 必须把
`poem_recite_settings_v1` 按字段拆家」是硬需求而不是优化项。

## 10. 异常与边界（逐条可测）

| 场景 | 期望行为 |
|---|---|
| 邮箱格式错 | 就地提示，不进入 `emailEntered`，不计入失败次数 |
| 邮箱带空格/大写/零宽字符 | 归一化后视为同一邮箱 |
| 连续点「发送随机码」 | 第 2 次起按钮置灰 + 倒计时，**不发新码** |
| 收到两封码，用旧码 | 拒绝（旧码已作废），提示「请用最新一封」 |
| 码过期后再输 | 明确区分「已过期」与「码错误」，过期可直接重发 |
| 输错 5 次 | 该码作废，必须重发；界面不透露"还剩几次"以外的信息 |
| 关掉页面再回来 | 从 `pending` 恢复，倒计时继续走 |
| 系统时间被改早/改晚 | 以 `issuedAt` 单调时钟为准；检测到时间倒退则**直接作废全部码** |
| 存储被写脏（手改 localStorage） | 全部字段做运行时校验，非法值回落默认，不抛异常 |
| localStorage 不可用（隐私模式） | 降级为「内存会话」，本次可用、刷新即退；给出说明 |
| 存储写满（QuotaExceeded） | 捕获、提示、不丢当前输入；会话优先于日志 |
| 用户注销 | 二次确认 + 重输邮箱确认；进度数据单独确认 |
| 会话过期 | 静默降级为 local 模式，**绝不弹窗打断背诵** |
| 备份导入含账号字段 | 忽略 `plan` / `security` / `identities` 的可疑字段（§2.2 硬约束） |

## 12. 合规：用户已裁决的三件事（2026-09-15）

> **总原则（用户原话）**：「用户协议和隐私条款永远遵从于代码的实际情况，
> 代码改了相应内容当然要跟着改。」
> 因此条款的修订**不跟路线图走、也不跟"将来会不会接服务端"走，只跟当前代码走**：
> 代码里实现了什么，条款就写什么；代码没实现的事，条款一个字都不许提前透露。

### 12.1 裁决一：`/privacy/` 的「不上传、不云同步 / 无注册无登录」

**裁决：现在就改，不等接服务端。**

做法（已随本次一并落地）：

| 今天的写法 | 改成 | 依据 |
|---|---|---|
| 「不需要注册」 | 「**不需要注册也能用全部功能**；也可选填邮箱建一个**只存在本机的账号**」 | 代码里有 `AuthCore` 的 local/code 模式（本机落盘），但没有服务端 |
| 「不上传、不云同步」 | 「**不上传、不云同步**：目前没有任何服务器，全部数据（含账号记录）只在本机」 | 事实未变 —— 本期确实一个请求都不发 |
| 「不收集手机号、邮箱、姓名…」 | 「不收集手机号、姓名、学校、位置；**邮箱仅在你自己主动填写时收集，且只以摘要 + 掩码存在本机**，不发送给任何第三方」 | 邮箱算个人信息（见 12.3），"什么都不收集"已不准确 |

**为什么不是"等接服务端时统一改"**：如果页面上已经出现"用邮箱登录"，
而条款仍写"无注册、无登录"，那条款就是一句**当场被自己违反**的话；
反过来，若为了保住旧条款而把 `/login/` 藏起来不进导航，那条款就成了**代码的枷锁**，
违反用户刚立的原则。按"条款跟随代码"的口径，正确做法是：
**代码实现到哪一步，条款就如实写到哪一步**——本期如实写「本机账号、无服务器、不发请求」。

落实清单（本次已做）：
- `privacy/index.html`：§一「收集什么」、§二「数据存在哪」、§三「儿童隐私」三处改写
- `terms/index.html`：§2「使用方式」、§5「儿童信息」两处改写
- `test/legal.test.js`：断言从「无注册无登录」改为「**本地账号 + 不上传不云同步**」，
  并新增一条**反向断言**：条款里**不得出现**「云同步」「已接入服务器」等未实现的说法
  （防止文案跑在代码前面 —— 这是比"文案落后"更糟的错）

### 12.2 裁决二：`grade / term / scope / dailyCount / algo` = **账号域（跨设备一致）**

**裁决：算，保持跨设备同步。**

依据：这五个字段直接决定「排哪几首、每天几首、怎么复习」。若各自为政，
会出现「电脑上背三年级上册、手机上排二年级下册」——同一份进度、两套排程，
是比"字号不一致"严重得多的错误。因此：

| 字段 | 归属 | 同步 |
|---|---|---|
| `grade`（年级） | **账号域** | ✅ |
| `term`（学期） | **账号域** | ✅ |
| `scope`（背诵范围） | **账号域** | ✅ |
| `dailyCount`（每日数量） | **账号域** | ✅ |
| `algo`（复习算法） | **账号域** | ✅ |
| `username`（昵称） | **账号域** | ✅ |
| `helper`（注音开关） | 设备域 | ❌ |
| 字号 / 对齐 / 连读档 / 播放模式 / iOS 引导条 | 设备域 | ❌ |

**这条裁决有连带影响，必须写清（否则会做成"改名不生效"或"一同步就全变"）**：

1. 现在 `grade/term/scope/dailyCount/algo` 与 `username/helper` **同躺在
   `poem_recite_settings_v1` 一个对象里**（见 §9 与 Issue #132 的阶段 0 设计）。
   要让前五个"跨设备一致"、后一个"各设备不同"，
   **本阶段 0 的"设置域按字段拆家"就从"建议"变成"必须"**：
   - 账号域 → `poem_recite_settings_v1`（沿用旧键名，最小改动）+ `poem_profile_v1`
   - 设备域 → `poem_device_prefs_v1`

   > ✅ **已落地（2026-09-15）**：`js/progress-store.js` 是这三域的唯一一份定义，
   > `js/storage.js` 退化成薄转发层。拆家**本期只动了 `helper` 一件** ——
   > `grade/term/scope/dailyCount/algo` 本来就该留在老键里（账号域沿用旧键名），
   > 字号 / 对齐 / 连读档 / 播放模式仍然原地不动（设备域的老键）。
   > ⚠️ **一个实测顶出来的口径**：`helper` 写的时候必须**两把键一起写**
   > （新键是正主、老键里那份是镜像），因为集子页与设置页至今从老键读它；
   > 只写新键会出现「首页说已开启、集子页是纯文本」。
   > 导出备份时 `settings.helper` 也要带上（老版本导入时才不会把它变回默认）。
   > 落地细节与另外两处偏差见 `docs/architecture.md` §3.3 / §3.4。
2. **改了账号域设置要能触发重排**：`scope/grade/term` 一变，`poem_plan_*` 缓存必须失效
   （现有逻辑已有失效机制），跨设备同步到达时**同样要清缓存重算**，否则"同步了但今日任务没变"。
3. **`profile.nickname` 就是账号域里的 `username`**（§2.1），两者不是两回事。

### 12.3 裁决三：登录时「两边都有且无法判断来源」→ 弹选择

**裁决：认同。弹「保留本机 / 保留账号 / 先导出再决定」三项。**

即 §9 表格里的 **D 场景，正式定为"不自动合并"**，三个选项各自的语义：

| 选项 | 做什么 | 风险 |
|---|---|---|
| **保留本机** | 用本机进度覆盖账号，并把本机进度推到账号 | 账号侧旧进度被覆盖（但用户已看到两边篇数） |
| **保留账号** | 用账号进度覆盖本机 | 本机进度被覆盖（**先自动存一份本机快照**，可回退） |
| **先导出再决定** | 把本机进度导出为 JSON 文件（复用 `Storage.exportJSON`），停在选择页不写盘 | 无 |

配套三条硬规则（写进测试）：
1. **弹选择之前，两个选项的"篇数 / 截至时间"必须都显示出来** —— 不让用户在不知道代价的情况下选
2. **"保留账号"前先静默落一份本机快照**（`poem_pre_merge_backup_v1`），给后悔药
3. **只读页面（首页浏览、集子页翻阅）绝不触发该弹窗**，也不写任何盘
