## 0. 一句话结论

**用 Supabase，免费版不休眠，但它只当「账号目录」和「跨设备进度库」；
发信不走 Supabase，走自己的 `/api` 云函数（**主 Resend**；SendGrid 已转向收费，见 §2.5）；
前端不上 Next.js，继续静态站；后端**每个业务需求一个函数**，不合并成框架。**

> ⚠️ **原始口径是「不超过 6 个 Serverless 函数」**，2.2（权威发放）把它变成 **9 个**，
> 3 期 P0（古诗词大会判分）再加 1 个，现在是 **10 个**。
> 这条改动是有意的，理由不是「想要更多」，而是**原来那 6 个里没有一处能写
> `accounts.plan`** —— 于是「权益由服务端判定」（§2.4 第 8 条）这句话在代码里
> 一直是一条断链：库里所有账号的 `plan` 永远是 `free`，只有手改库才发得动。
> 见 §4.14。**「不超过 6 个」要守的是「不引入框架 / 不引入微服务」那条纪律，
> 不是这个数字本身** —— 所以现在写成「每个业务需求一个函数」，并逐条列出
> 「为什么不能更少」（§2.2）。

```
浏览器（静态 PWA，Vercel 托管，kuibu.app）
  │  js/auth-core.js            ← 已有，纯逻辑，零 DOM
  │  js/sync-store.js           ← 新增，ProgressStore 的远端实现
  ▼
api（同一个 Vercel 项目里的 /api/*，10 个函数）
  ├─ /api/send-code      → Resend 主（不花钱；SendGrid 已收费，见 §2.5）
  ├─ /api/verify-code    → 校验 → 签发会话（HttpOnly Cookie）
  ├─ /api/me             → {uid, plan, features[]}   ← Pro/Max 唯一合法挂载点
  ├─ /api/sync/pull      → 拉服务端进度（增量）
  ├─ /api/sync/push      → 推本机进度（增量、按条覆盖）
  ├─ /api/account        → DELETE 注销（含数据导出）
  ├─ /api/admin/grant    → POST 发放 / DELETE 收回（2.2 权威名单，服务端角色闸）
  ├─ /api/admin/grants   → POST 看名单（只回掩码，只列发过层级的那几条）
  └─ /api/game/answer    → POST 判分（3 期 · **不花钱**：用仓库里的 js/quiz.js，不接 AI 商）
  ▼
Supabase（免费版，Postgres + 一张 accounts 表 + 一张 progress 表）
  └─ 由 GitHub Actions 定时唤醒（见 §1）
```

**三条不可退让的边界（沿用 `docs/auth-design.md` §1）：**
1. **不注册也能用全部功能** —— 登录只增加「数据不丢 + 跨设备」，不拿任何现有功能当人质
2. **打开即用、可离线** —— 首屏不许因为有了后端而变慢；断网照常背
3. **不假装配齐了** —— 代码实现到哪一步，`/privacy/` 与 `/terms/` 就如实写到哪一步

## 1. supabase 免费版不休眠：可行，但必须认清代价

### 1.1 为什么它会休眠（官方口径）

Supabase 免费档（Free plan）的官方规则：

| 项 | 免费档 |
|---|---|
| 活跃项目数 | 2 个 |
| 数据库 | 500 MB |
| 月活用户（MAU） | 50,000 |
| 出口流量 | 5 GB / 月 |
| **空闲暂停** | **项目连续 7 天没有任何请求 → 自动暂停（paused）** |
| 唤醒方式 | 到控制台手工点，或发一个能打到数据库的请求让它自动恢复 |

暂停不是「睡一会儿」，是**整个项目停机**：数据库不可连、Auth 不可用、
REST API 全部返回错误。对用户的表现是「打不开了」，而不是「有点慢」。

> ⚠️ 这条是本方案里**唯一一个会直接砸在用户身上**的平台限制。
> 用户背了一个月，第 8 天打开发现进度拉不下来 —— 这是产品级事故，必须在架构里消掉。

### 1.2 让它不休眠的四种办法（按推荐度排序）

#### 办法 A：GitHub Actions 定时探活（**推荐，零成本，唯一真解**）

原理：暂停的判定是「7 天内没有任何请求」。那么**每 5 天发一个真请求**即可。

本项目现成的条件：代码已经在 GitHub（`ashleyzhang2028/poem`），
`.github/workflows/` 加一个 cron 就完事，**不引入任何新服务、不需要服务器**。

```yaml
# .github/workflows/keepalive.yml
name: supabase-keepalive
on:
  schedule:
    - cron: '0 3 */5 * *'      # 每 5 天一次，留 2 天缓冲
  workflow_dispatch:           # 也留一个手动按钮
jobs:
  ping:
    runs-on: ubuntu-latest
    steps:
      - name: ping supabase
        run: |
          curl -sS -o /dev/null -w '%{http_code}\n' \
            "${{ secrets.SUPABASE_URL }}/rest/v1/accounts?select=uid&limit=1" \
            -H "apikey: ${{ secrets.SUPABASE_ANON_KEY }}" \
            -H "Authorization: Bearer ${{ secrets.SUPABASE_SERVICE_KEY }}"
```

**四个必须做对的地方，否则探活本身会失效：**

1. **必须打到数据库**，不能只 ping 域名或健康检查页 —— Supabase 的状态页
   与根路径不触发数据库活动，只有 PostgREST / Auth 的真实查询算「活动」。
2. **必须每 5 天，不能每 7 天** —— GitHub 的 `schedule` 在高负载时可能延迟数小时，
   偶尔会跳过（官方文档明确：「可能延迟、在高负载时可能被丢弃」）。
   每 5 天一次，即使偶尔跳过一次也仍在 7 天窗口内。
3. **GitHub Actions 对 60 天无提交的仓库会停掉定时任务** —— 本项目天天在改，不成问题；
   但要在 workflow 里留 `workflow_dispatch` 手动口，万一停了能一键补上。
4. **探活失败必须能被发现** —— curl 的非 2xx 要让它红，否则「探活挂了 3 个月」
   会以「某天用户突然登不上」的形式暴露出来。上面的 `-w '%{http_code}\n'`
   配合 `-f` 或后续断言即可。

**这条办法的真实成本：** 每 5 天一次请求，一个月 6 次。
免费档流量 5 GB/月，这个量级可以忽略。

#### 办法 B：把邀请来的「每日真实访问」当探活（**不推荐作为唯一手段**）

有真实用户访问就是真请求，理论上不需要额外探活。**但不能靠它**：
- 跬步现在「打开即用、未登录不用后端」，绝大多数访问**根本不碰 supabase**
- 一旦连续 7 天没人发起登录/同步请求（比如一个寒假），项目就暂停，
  而**第一个想登录的用户恰好撞上暂停**——最坏的时机

所以 B 只能当 A 的补充，不能替代 A。

#### 办法 C：UptimeRobot / cron-job.org 之类的免费监控（**备选**）

可以，但它是**多一个第三方**：多一个能访问你数据库的账号、多一条要写进隐私条款的
数据处理者。既然 GitHub Actions 已经现成，没有理由再引一个。

#### 办法 D：升级 Pro（$25/月）（**现阶段不做**）

这是唯一「官方保证不休眠」的办法，也是唯一能拿到：
- 不暂停的 SLA
- 每日自动备份 + 7 天 PITR
- 可自选区域

**判断：现阶段不做。** 理由不是钱，是**顺序错了** ——
一个还没有一个付费用户的产品，先付每月 175 元保「后端不睡」，
而它的核心问题（没有主体资质、收不了钱）一点没解决。
（顺带：用户 2026-09-17 已决定**不做收费**，「收不了钱」这件事从「还没做到」
变成了「不做」—— §5.0。所以这里更没有必要为「后端不睡」付月费。）
探活方案在工程上等价，只在「忽然被 DDoS / 数据库爆掉」这类场景有差别，
而那时你早就该升级了。

### 1.3 但请记住：探活只是「可用性兜底」，不是「可靠性方案」

即使不休眠，免费档还有几条**探活解决不了**的限制：

| 限制 | 影响 | 应对 |
|---|---|---|
| **没有自动备份**（免费档无 PITR） | 误删数据 = 数据永久消失 | 每周一次 `pg_dump`（同样用 GitHub Actions）导出到仓库 artifact |
| 数据固定在美国 / 新加坡等共享区域，**不能自选** | 机房位置不可控 | 与合规无关（本站不以「国内项目」为前提，见 §4.2）；只按「最小化上传」设计 |
| 出口流量 5 GB/月 | 大文件不能走它 | 进度数据是 KB 级，不会触到 |
| 无 99.9% SLA | 平台故障只能等 | **进度数据必须本机也是完整副本**（见 §3.2 的「本机优先」） |

**最后这条最重要，它决定了整个同步架构的形状：**
> **supabase 里的进度永远不是唯一副本。本机 localStorage 始终是完整、可用的那一份。**
> 后端挂了、暂停了、欠费了，用户照样能背，只是不同步而已。

### 2.2 为什么后端只有 9（+7+1）个函数，而不是一个「正常后端」

因为这个应用的后端需求**真的只有这么多**：

| 需求 | 函数 | 为什么不能更少 |
|---|---|---|
| 发验证码 | `send-code` | 只有它需要密钥、需要频控、需要真的发信 |
| 验证码换会话 | `verify-code` | 只有它能签会话，明文码不许出现在客户端 |
| 知道自己是谁 | `me` | 权益的唯一来源；客户端不得参与判定 |
| 拉进度 | `sync/pull` | 换设备恢复 |
| 推进度 | `sync/push` | 多设备一致 |
| 注销 | `account` | 合规硬要求（个保法删除权） |
| **发放层级**（2.2） | `admin/grant` `POST` | 「权益由服务端判定」这句话要成立，就得有**唯一一处**能写 `accounts.plan`；写在客户端等于没有判定 |
| **收回层级**（2.2） | `admin/grant` `DELETE` | 收回 = 发一个 free（同一处写、同一个语义），不另开一张表 |
| **看名单**（2.2） | `admin/grants` | 发放要有一条**本机就能看的回执**，否则管理员只能靠猜 |
| **注册**（#197） | `register` | 用户填了口令 —— 没有账号就没地方放那个摘要；而口令摘要只能在服务端算（要 pepper、要落库） |
| **口令登录**（#197） | `login` | 实现口令校验、失败锁号、签发同一枚会话 |
| **确认邮箱**（#197） | `verify-email` | 邮件里那条链接的落点。**不要求登录** —— 用户可能在另一台设备上点开 |
| **重发确认**（#197） | `resend-verification` | 「我没收到那封信」必须有一条路；**要登录**，否则任何人都能拿别人邮箱刷确认邮件 |
| **忘记密码**（#197） | `reset-request` | 发重设邮件。**无论邮箱存不存在回同一个响应**（不泄露存在性） |
| **重设密码**（#197） | `reset-confirm` | 换新摘要 + **吊销全部会话** —— 那是「重设」这件事的一半含义；并如实回 `emailVerified`（没确认的人走完这一套**仍然登不进去**，那一句必须说出来） |
| **匿名重发确认**（#197 后半段） | `resend-verification-by-email` | 「没确认就不让登录」这条口径下**唯一的出路**（要登录那条对这条路的人必然 401）。因此它是全站唯一一条「不登录也能让本站发信」的接口：频控四层 + 冷却 + 存在与否回同一形状 + 已确认的不发信 |
| **账号名录**（#197） | `admin/accounts` | 用户裁决「邮箱必须记录到数据库」「我还是要看到这些用户」：一张**只读**的名录，含明文邮箱。它与会「只列发过层级的」那张**不是一张表** |

**不需要的东西，明确列出，免得以后有人「顺手加」：**
- ❌ 不需要 GraphQL / ORM（9 个函数、4 张表，SQL 直接写更清楚）
- ❌ 不需要 Redis / 队列（频控用 `codes` 表的时间窗查询足够）
- ❌ 不需要微服务 / 容器（Serverless 冷启动对这 9 个函数的调用频率完全够用）
- ❌ 不需要 CDN 之外的缓存层（静态资源已经在 Vercel 边缘）
- ❌ 不需要「用户列表 / 后台管理面板」（1 期口径）—— ⚠️ **这一条已被 Issue #197 部分推翻**：
  用户明确要求「我还是要看到这些用户」，于是有了 `admin/accounts` 那张**只读名录**。
  但它的边界仍然收着：**只读**（发放走 `admin/grant` 那条）、
  **只有 owner / admin 拿得到**（服务端角色闸）、
  **不回** `password_hash` / `password_salt` / `email_hash` / 进度 / 会话。

### 2.3 前端为什么**不**上 Next.js

这是本轮最该说清的一条，因为它是你最初的问题之一。

**Next.js 能带来的东西，这个项目一个都不需要：**

| Next.js 的能力 | 跬步需要吗 | 为什么 |
|---|---|---|
| SSR / ISR（服务端渲染） | ❌ | 内容全在客户端、本地生成，**没有任何一页的内容依赖服务端** |
| 路由框架 | ❌ | 13 个静态页面已经跑通，URL 约定（目录化、无 `.html`）是刻意的 |
| API Routes | ⚠️ 部分需要 | 但 Vercel 的 `/api/*` **原生就支持**，不需要 Next.js |
| React 组件化 | ❌ | 现在 25 个模块全是 IIFE + `window`，逻辑层 0 行 DOM（见下） |
| 图片优化 / 字体优化 | ❌ | 字体已**手工子集化**自托管（11 MB，比 Next.js 的自动优化更可控） |
| 打包器 / tree-shaking | ⚠️ 想要 | 但可以用 **不带框架的 Vite/Rollup 单独解决**，成本远低于上 Next.js |

**上 Next.js 的代价（真实存在，不是理论风险）：**

1. **26 个测试文件、12730 行测试几乎全部返工** —— 它们是 jsdom（加载真实 HTML）+
   源码扫描 + puppeteer。改成 React 后 HTML 是运行时生成的，
   「页面加载 js/storage.js」这类断言的对象不复存在
2. **`sw.js` 的缓存策略要重做** —— 现在是「静态资源缓存优先 + 导航在线优先」，
   写得很清楚（`README.md` 的 Service Worker 约定）。Next.js 的资源指纹变了，
   那套约定要重新推一遍
3. **首屏会变慢** —— 现在是「一个 HTML + 4 个字体 + 按需数据」，秒开。
   Next.js 客户端组件 + hydration 至少要加一个 runtime chunk，
   而**离线优先是跬步最硬的产品特性**，不能拿它换架构先进性
4. **PWA 离线承诺要重新验证** —— app shell 预缓存的清单会变（`PRECACHE` 现在是手写的，
   这恰恰是它的优点：改了什么、缓存什么，一眼看得见）

**判断：不迁移。** 如果你想要打包器，正确做法是
**只把 `js/` 那 25 个模块换成 ES modules + Rollup，页面保持静态 HTML 不动** ——
这是 0 期顺带能做的事（见 §3.1），成本约 2 人日，收益是 tree-shaking + 依赖显式化，
且**不需要动任何一页 HTML 的结构**。

### 3.4 落地时顶出来的三件事（与原设计不同，都是实测的结果）

**① `helper` 必须**双写**，不能只写新键。**
设计里写的是「`helper` 搬到 `poem_device_prefs_v1`」。真做起来发现：六部集子页与
设置页**至今仍从 `poem_recite_settings_v1` 读它**（`reader-core.js` 的 `helperOn()`），
只写新键就会出现「首页说已开启、集子页是纯文本」——一份数据、两处说法。
现在的口径是：**新键是正主、老键里那份是镜像，写的时候两把一起写**
（`saveSettings` 与 `setHelper` 都双写），读的时候新键优先。
集子页那段的读写也已改走 `ProgressStore.helper()` / `setHelper()`，与引擎同源。

**② 导出备份里**必须**补上 `helper`。**
老版本导入备份时只认 `settings.helper`，导出时若把它从 `settings` 里摘掉，
用户在另一台设备上导入后会发现「阅读辅助变回默认」。
所以导出是**宽进严出**：导出时按位补齐（`settings` 里带一份 `helper`），
导入时按域过滤（`settings.helper` 与 `device.helper` 都收，写回设备域）。

**③ 引擎必须只认 `pick()` 出来的默认值，**不许**从旧盘上「继承」它自己写下的默认值。**
`saveSettings` 会把 `helper` 的镜像写进老键（见 ①），于是**旧键里一定有它** ——
如果 `helper()` 的回落顺序是「新键 → 老键 → 默认」，那么「老键里那份默认值」
就会被读成「用户选择」，而新键一旦有值就以新键为准……这条读法本身没错，
但 `settings()` 返回的对象里**不能再带 `helper`**：它属设备域，两处都返回就等于
又回到「一份数据两处说法」。现在 `settings()` 只返回账号域白名单 + `username`。

**顺带修掉的一个真 bug（不是设计里的）：** `js/app.js` 启动时
`settings = Storage.getSettings()` 拿到的对象里已经没有 `helper` 了，
`helperEnabled()` 于是判成「开着」——**在关掉了阅读辅助的机器上照样注音，
而设置页显示的是「关闭」**。现在启动与 `PoemApp.reloadSettings()` 之后都调一次
`adoptHelperFromDevice()`，从设备域现读一次写进本地快照。
这条被 `test/auto-read.test.js` 的「阅读辅助关闭 → 打开诗词是纯文本」当场抓住 ——
那一条在改之前是**绿的**，改完变红，说明它真的守着这件事。

### 4.2 数据上云：1 期的唯一实质合规风险（2026-09-15 重裁）

> **用户裁决（Issue #132，2026-09-15）**：「我没说这是一个国内的项目啊，为什么总是说要出境？
> 选择方案 B，不需要出境同意流程及界面。」

**先说清一件事：这不是一个「国内项目」。** 本站部署在 Vercel、语料库自带、
不接任何国内云也不接任何国内 CDN；「国内用户为主」是一个**受众事实**，
不是一条**架构约束**。前几轮把 Supabase 的共享区域一律读成「个人信息出境」，
是在给一个不存在的约束做设计 —— 于是凭空长出了「出境单独同意」勾选框、
「出境同意」流程与被误伤的方案取舍。**这套措辞本节整体删除。**

**但风险本身没消失，只是换了名字。** 真正要处理的是这件事：

- 1 期之前（含 0 期）数据只在本机，`/privacy/` 的「不上传、不云同步」成立
- 1 期一旦把账号与进度送上服务端，就**产生了数据上传**：从「无服务器」变成
  「有数据处理者」，`/privacy/` 必须如实改口，用户必须知情、可关、可删、可带走
- 跬步面向儿童，这是**最敏感的一类**用户 —— 口径要比一般产品更谨慎

**这不是出境问题，是「要不要上传」的问题。** 处理动作与服务器在哪个机房无关，
所以**不做「出境同意」这个独立流程，也不为它建任何界面**。

#### 裁定：**方案 B（进度上云）+ 据实告知，不做出境同意**

用户已选 **B：连进度一起上云**（换设备自动同步，这才是登录真正的价值）。

配足的动作收敛为**三件据实做**的事（都不叫「出境同意」）：

| # | 做什么 | 为什么还要做 |
|---|---|---|
| 1 | **注册/首次登录时据实告知**：说清「进度会保存到服务器以便跨设备同步」，用户点「继续」即视为同意 | 上传就要求知情同意，与机房位置无关；**不做单独勾选框、不做第二张页** |
| 2 | 设置页有「**不使用云端同步**」开关（**默认本地**） | 用户有权拒绝上传；关掉即完全退回 0 期行为 |
| 3 | 「**注销即删除 + 数据导出**」自助可用 | 删除权与可携带权是基本要求，也是 B 方案自己的技术前置 |

**明确不做的**：

- ⛔ 注册页的「个人信息出境单独同意」勾选框（**删掉**，不建）
- ⛔ 任何名为「出境」「跨境」「数据跨境传输」的界面、文案、开关
- ⛔ 为「选择机房 / 区域」而做的设置项（免费档本来也不能自选区域）

| 数据 | 存哪 | 说明 |
|---|---|---|
| `email_hash` + `plan` + `uid` | Supabase | 账号存在的前提；**只有摘要，还原不出邮箱** |
| 会话 Cookie | 浏览器 | 不上云 |
| **学习进度（背诵记录）** | Supabase | ✅ 已裁：**上云**（方案 B），可被开关关闭 |

**`/privacy/` 与 `/terms/` 的改法**：把「不上传、不云同步」如实改成
「默认只存本机；开启云端同步后会上传到服务器，可随时关闭、注销即删除」，
**不提「出境」二字**。这一改动与 1 期代码同批落地（条款跟随代码）。

> 「最小化」的原则不变：账号只存摘要、进度是 KB 级、本机始终保留完整副本
> （见 §1.3 那条「supabase 里的进度永远不是唯一副本」）。

### 4.7 1A 落地时顶出来的六件事（与原设计不同，都是实测的结果）

**① 「重新发送冷却」不是频控的一档，必须单独判。**
设计里把 60 秒冷却写在 `RATE.email` 的窗口里。真做起来发现两者是不同的东西：
频控是「一段时间内最多几次」，冷却是「两次之间至少隔多久」。
混在一起写，`[[3600000, 5]]` 的第一个窗口会**直接放过**连点两次的行为，
而文档 §4.6 第 4 条明确要求「60 秒内只发一封」。
现在冷却由 `limiter.cooldown()` 单独判，测试里有一条专钉它。

**② 错误码的判定顺序会影响用户看到的话。**
「错满 5 次」时我们顺手把码记录也标成「已消费」（等于作废）。若先判 `consumed_at`，
用户会看到「这个验证码已经用过了」—— 而他一次都没对。
现在 `attempts` 先判、`consumed_at` 后判，与前端内核 `js/auth-core.js` **逐条同序**。
（服务端与前端各有一套实现，顺序不一致就会出现「同一个码两种说法」。）

**③ 后端挂掉时的降级分两层，1A 只落了第一层。**
- **第一层（1A 已落）**：接口**不 500** —— 没配库时降级 `memoryStore`；
  没配 `SESSION_SECRET` 时回 **503 `E_NOT_CONFIGURED`**（而不是 500），
  传输层把它翻译成「本站还没开放云端账号，当前是本机体验版」并标记降级。
- **第二层（1B 已补）**：「同步失败不打断背诵」的端到端验证。
  1A 当时还没有同步层，写一条「同步挂了照样背」的测试等于测一个空对象 ——
  那种断言永远绿、什么都不验，比不写更糟，所以当时如实标注为 1B 的活。
  **1B 补上了**：`test/sync.test.js` 第十节用十种坏情况逐条验（见 §4.6 第 8 条）。

**④ 明文验证码这条纪律，最先破的位置是「本地开发的日志」。**
`console` 通道本来顺手把码打到日志里（本地调试方便）。但那违反 §4.3 第 1 条，
而且**破了之后生产也会照打** —— 同一条 log 语句，没有人会记得在部署前删掉。
现在 console 通道只记「本该发往 a***@b.com」，并明确提示「要看码请开 `ALLOW_CODE_ECHO=1`」。
测试里有一条断言直接把 `console.log` 抓下来，扫其中有没有 6 位数字串。

**⑤ `sw.js` 里一个注释都不许有，于是「为什么」只能写在测试那边。**
用户明确要求 `sw.js` 去掉全部注释并禁止再加（`test/theme.test.js` 有硬断言守着）。
`/api/*` 那条早退的**理由**因此写进了 `test/api.test.js` 的注释里 ——
这条看起来是「文档放错了地方」，其实是唯一能同时满足两条约束的位置。

**⑥ `CONFIG.mail()` 差点写成读模块级 `CONFIG`。**
写成 `CONFIG.mailTransport`（而不是 `this.mailTransport`）的后果很隐蔽：
`Object.assign({}, CONFIG, { sendgridKey })` 这类覆盖**完全不生效**，
症状是「明明给了密钥却仍落到 console」，而且不报任何错。
现在读 `this`，测试里有一条「显式指定优先于密钥推断」就是为它写的。

**另有两处与本地版对齐的加固：**

- **服务端补了时钟回拨保护**。本地版早有 `guardClock`，服务端原先没有 ——
  理由是「服务端时钟可信」。但**可信不等于单调**：多实例的 NTP 校正、
  容器迁移都会让某个实例的 `now` 往后退，而这里判的正是「码有没有过期」。
  现在按「这条码自己的签发时刻」做水位，回拨超过 2 分钟即判该码不可用。
  容差比本地版的 60 秒宽，是因为服务端这个值要被「10 分钟有效」覆盖 ——
  把真人挡在门外比放过一次边界情况更糟。
- **邮箱形态校验的 `..` 规则两边补齐**。前端内核原先允许 `a..b@c.com`
  （本地部分连续点），服务端也不拦。按 RFC 5321 这是无效地址，
  现在两边同时拒收，测试里有一条跨端一致性断言。

### 4.8 1B 落地时顶出来的八件事（与原设计不同，都是实测的结果）

**① 同步记账**不能复用「已读」那套读写。**
设计里写「用 `ProgressStore.readMap` / `setRead` 存每条记录见过的云端时间戳」。
真做起来发现那是**布尔语义**（`if (val) m[id] = true`）：时间戳 `0` 被丢掉、
`-1`（冲突标记）读回来是 `true`、`9000` 也读成 `true`。
症状极其隐蔽 —— **表面上都「有值」**，于是「刚拉回来的又被推回去」、
冲突永远判不出来、游标永远是 0（每轮全量拉）。
现在这张表（`poem_sync_seen_v1`）有自己的读写，与「已读」不是一回事。

**② 「认领本机进度」= 打时间戳，但**不**记进 `seen`。**
两者看着都像「本机这份已就绪」，含义却相反：记进 `seen` 等于说
「已经和云端对齐了」，而它们恰恰是**还没有云端对应**的那一批 ——
用户先在本机背了一个月、之后才建账号，那批一篇都不能丢。
写错的症状是：新注册的人进度一条都同步不上去，且不报任何错。

**③ `touch()` 也**不许**顺手写 `seen`。**
同理：`seen` 记的是「云端最后给这一条的时间戳」，本机改动不改变那个事实。
写进去的后果是「看起来已经对齐」，这一条从此永远推不出去。

**④ 推成功之后要用「推上去的那枚时间戳」打标，不是「现在」。**
用 `now` 的后果：下一轮 `pending()` 判「本机时间戳 ≠ 见过的云端时间戳」，
于是同一条又被推一次，**每轮都推、永远推不完**。现在批量写一次盘
（逐条 `setItem` 在 N 条时会抖 N 次，且中途失败就只记了一半）。

**⑤ 冲突判定不能只看时间戳大小，还要看「云端知不知道本机这一版」。**
最初写「本机更新 + 时间戳对不上 = 冲突」，结果是**几乎每条本机改动都成了冲突**
（正常背书就是「本机更新」，而云端当然还没见过）。现在判据是
`seen[id] === 云端时间戳` —— 相等说明两边是**同一条线**上的先后，本机赢、推上去；
不等说明云端也动过而两份没有共同祖先，才请用户裁决。

**⑥ 冲突标记必须**最先**判。**
上一次已经判过「判不出来源」、用户还没选时，再来一轮不该把它又自动合并掉。
放在时间戳比较之后写的后果是：用户每次刷新页面，那个决定就被"重算"一次，
而他从来没被问过。

**⑦ 「先导出再决定」必须**真的给出文件**，且快照要**在发现冲突时就落**。**
最初只把「有没有快照」当条件返回，而快照本来只在用户点「保留账号」时才落 ——
于是这一支导出的是一张空纸。现在：一见冲突就落快照（后悔药提前备好），
「先导出再决定」把快照 + **待裁决的篇目清单**一起给出去，且一个字节都不改。

**⑧ 顺带修掉一个「只在真页面上才炸」的坑：引擎挂载时机。**
`js/sync-store.js` 最初在模块加载时抓一份 `window.ProgressStore`。
但页面里的脚本顺序不保证（老缓存里的旧页面尤其），
抓到 `null` 之后**永远**是 `null` —— 症状是 `Storage.set` 走不到同步记账，
**静默不同步**。现在每次现取（与 `js/storage.js` 的 `PS()` 同一条教训）。
这条还是 jsdom 的真页面测试顶出来的，数据层的纯 Node 测试看不见它。

### 4.9 2 期「补洞 + 2A」已落地（2026-09-17）：两根一直没接的线

> ✅ **2 期第一批已落地**：把 1A/1B 建好却**一直没接**的两根线接上，
> 并顺手把条款改到与代码一致。新增 `js/account-api.js`（**唯一接线处**）
> 与 `test/account-bind.test.js`（**纯 Node + 假 fetch，不联网**）。

#### 补的两根线（都是「服务端写好了、前端没人调」）

| # | 线 | 之前的状态 | 现在 |
|---|---|---|---|
| ① | `GET /api/me` | **没有任何页面调用过**（只有 `js/auth-api.js` 里定义着）。于是服务端判定的层级与角色没下发到界面，Pro/Max 的唯一合法挂载点空着 —— 决策清单第 8 条落不了地 | 个人中心与设置 · 通用在**有会话时**各问一次；答案带 `source:"server"` 写进 `poem_plan_v1`，`identity()` 据此让**服务端优先** |
| ② | `DELETE /api/account` | 接口与客户端方法都写好了，**但没有页面调它** —— `js/profile.js` 注销时走的是本机内核那个版本，**云端那一行还在**（合规问题，删除权） | 个人中心的注销走 `AccountApi.deleteAccount()`：**先服务端（先导出再删行）、后本机** |

#### 落地时定死的四条边界（都进了断言）

1. **失败不打断任何事** —— 断网 / 超时 / 503 / 401 / 5xx，一律只是「这一轮没问成」。
   所有网络调用包在 `AccountApi` 里，异常在那里被吞掉。
2. **不假装** —— `refreshMe()` 的 `reason` 只有四种取值，每种界面上有一句话对应：
   `ok` / `guest`（没登录，**正常状态**）/ `not-configured`（本站没开放）/ `unavailable`（连不上）。
   层级来源也如实标出来：「由服务器判定」还是「本机登记」——
   这两句在用户眼里的分量完全不同（本机那份改一行存储就能改）。
3. **不清用户数据** —— 拉不到 `/api/me` 时**不删**本机那份层级缓存。
   删了等于「后端抖一下，用户从 Pro 掉回 Free」，那是产品级事故
   （与 §1.3「后端挂了照样能背」同一条口径）。
   会话真过期（401）时才清，且**只清 `source:"server"` 那一份** ——
   管理员发的本机名单与它无关，退出登录不该把它抹掉。
4. **不做无谓请求** —— 没登录时**一个请求都不发**；`refreshMe()` 有**同会话只问一次**的闸
   （四页签点几下不会问四遍）。失败的那一次**也落闸** ——
   否则一个断网的用户每张页面都会白等 15 秒超时。

#### 三处「不这样就必错」的实现细节

**① 顺序：先服务端、后本机。**
`AuthCore.deleteAccount()` 会把内核会话清掉，而服务端那一步要会话 Cookie ——
反过来做的话，服务端会以 401 收场，而用户以为注销成功了。
`test/account-bind.test.js` 的第九节把「调服务端那一刻本机会话还在」直接断言下来。

**② 注销必须先导出、且导出**真的给到用户**。**
`/api/account` 先 `listProgress` 再做三件事（删进度 → 吊销会话 → 删账号），
导出那份**随响应回来**；页面把它做成一个下载按钮。
本期没有对象存储，所以返回的不是 `exportUrl` 而是一份数据 ——
**假装有个下载链接比不做更糟**。

**③ 连不上时**不阻断本机注销，但如实说云端还在**。**
`remote` 只有三种取值：`deleted` / `none` / `skipped`。
`skipped` 时页面**不跳走**，而是把那句话说清楚（删除权上的实情，不许含糊）。

#### 顺带修掉的一处「注释在说、代码没做」

`api/_lib/core.js` 的 `publicAccount()` **从来没下发过 `role`** ——
而客户端 `entitlement.js` 里早就写着「服务端下发的 role 优先」。
于是那条「服务端角色优先」一直只是注释：实际永远走本机兜底
（即「谁打开谁是 owner」，清空存储就能当管理员）。
现在 `publicAccount()` 下发 `role`（带白名单校验），
`identity()` 在 `source:"server"` 时以它为准，**两向都验**
（服务端说 user → 本机 owner 兜底让位；服务端说 owner → 本机 member 也升）。

#### 条款跟着代码改（按 §4.5 的纪律）

`/privacy/` 与 `/terms/` 的「删除方式」那条从**承诺式**改成**陈述式**：
写明「注销即删除服务器上的账号行与进度行，并把云端那一份导给你留存」，
**并如实补上一句「注销需联网；连不上时页面会说明云端那份还没删掉」**——
这句不是免责，是这一版代码的真实行为（`remote === "skipped"`）。
两页的字数上限同步收紧（隐私 2400 → 2391，靠删掉一句冗余表述，不是删信息）。

### 4.10 2B 期「短信口子」已落地（2026-09-17）：把注释变成真的能跑

> ✅ **2B 已落地**：在 8.1 之前，短信只是 `identity.channel` 里一个字符串。
> 现在「加 sms 通道」这件事**只差一个「谁去发」的实现** ——
> 归一化、摘要、频控、状态机全部就位，且**一分钱没花、一项配置没配**。

#### ① 短信不是「另一套流程」，是同一套流程的另一个 channel

`api/_lib/core.js` 的 `sendCode` / `verifyCode` **没有 channel 分支**在流程上：
码怎么生成、怎么摘要、失败几次作废、时钟回拨怎么护——两条通道**逐字共用**。
channel 只改三件事：**归一化规则、频控档、谁去投递**。

```
normIdentity(input) → { channel, value, mask, key }
  email → normalizeEmail / isEmailShape / emailHash
  sms   → normalizePhone / isPhoneShape / phoneHash（|phone| 命名空间）
```

摘要**按通道分命名空间**：同一个字符串在 email 与 phone 下摘要不同，
排除「某手机号串 = 某邮箱串」的交叉命中可能。表结构不变
（`accounts.email_hash` 那一列现在存的是「该身份标识的摘要」，列名是历史包袱）。

#### ② 频控更严 —— 因为短信是真金白银

邮箱成本近似零，短信 0.04 元/条。邮箱那套「一小时 5 封」放短信上
就是「一小时能烧 0.2 元/人」，被刷一晚几百上千。
所以短信独立一档：**60 秒 1 次、日 5 次、月 15 次**
（`config.rateSms` / `AuthCore.RATE_SMS`，两端同值）。

> ⚠️ 客户端内核的 `rateCheck` 必须能认 `phone` 档 ——
> 写了 `RATE_SMS` 而 `rateCheck` 不认它，短信就成了**实际不限速**，
> 而代码看起来「写了限制」。这是「写了但没接上」的同款坑（2A 那两个洞）。

#### ③ 没开通时**如实拒**，且不做任何副作用（2B 的核心口径）

```
POST { channel:"sms", value }  →  503 E_SMS_NOT_OPEN
```

1. **不假装**：没有真短信商时**绝不走 console 兜底当成功**。`transports.sms`
   是个空壳，它的 `send()` 直接 reject。一条收不到的短信 + 一个「已发送」提示 = 骗人。
2. **不做副作用**：拒在落库之前，**不建账号、不写码记录**。否则「试一下短信登录」
   在库里留一串孤儿账号。
3. **不偷偷降级**：界面收到 `E_SMS_NOT_OPEN` **不许**切回本机体验版
   （本机版同样发不出短信，切过去只是换个说法）。
   `js/auth-api.js` 给它一条**独立**文案，且不在回落名单里。

> `SMS_ENABLED=1` 只是「允许尝试」，不等于能发；`SMS_TRANSPORT` 指向已实现的商才真能发。
> 只开开关不接商，请求**仍然**是 503。

#### ④ 界面仍不渲染（条款不许跑在代码前面）

`login/index.html` 的短信按钮**仍是注释**。区别在于：注释里现在写清了
「开通时只需取消注释」——因为接口真的支持了。
但**按钮不渲染、也不写「即将上线」**：接口支持 ≠ 通道能用（还没签短信商）。

#### 验证

- `bash test/run.sh`：**4263 条断言全绿、0 失败**（较 2A 的 4185 增 78）
- `test/api.test.js` 新增第十八节：手机号归一化/掩码/摘要命名空间、
  **两端规则对拍**（前端与服务端对同一输入同判）、更严频控档、
  真 HTTP 下 503 / 400 的三条路径、老调用点兼容、**「只开开关不接商仍 503」**、
  码落入同一张 codes 表（通道不改落库形状）
- `test/auth.test.js` 补 2B 断言：归一化收敛、形状拒绝、独立短信档、返回带 channel
- `sw.js` 缓存版本 v122 → **v123**

### 4.11 2C 期「清单与自检」已落地（2026-09-17）：把 2D 那一步做成可执行的

> ✅ **2C 已落地**。2A 接了两根线、2B 把短信口子做成真能跑的代码。剩下的
> 「让它真的能用」是本项目唯一**没有业务代码可写**的一步（2D：配置与真开通）。
> 2C 的产出是：**那一步从此有了可执行的形式**，并且把 2A/2B 留下的
> 「同一件事两端各写一份」的漂移一次收干净。

#### ① 「没有代码可写」≠ 没有东西可做

2D 要用户在 Supabase / Resend 后台点几下、再往托管平台填几个变量。
放在一期工程里，这件事的常见下场是：**一篇文档 + 一张手抄的清单**。
而手抄的清单必然与代码分叉 —— 本项目里这种分叉已经出现过好几次
（`docs/auth-design.md` 里那些「已落地 / 未落地」的标注就是补丁）。

2C 把它拆成三件有形式的东西，全部**同源**：

| 产出 | 是什么 | 为什么不是「文档」 |
|---|---|---|
| `api/_lib/ops.js` 的 `ENTRY` | 每个环境变量：**是什么 / 缺了怎样 / 怎么补** | 自检与模板读的都是这一份 —— 「文档说缺 X、程序说缺 Y」不可能发生 |
| `scripts/doctor.js`（`npm run doctor`） | **不部署**就能问出「现在缺哪几个」 | 输出可直接贴进 Issue；退出码 = 体检结论（没到最低线退 1） |
| `.env.example` | 可直接粘贴的模板 | 由 `scripts/env-example.js` **生成**，不是手抄 |

```
$ npm run doctor
跬步 · 开通自检（服务端环境变量）
⚠️ 还没到「能真跑」的最低线（缺 SESSION_SECRET、SUPABASE_URL、SUPABASE_SERVICE_KEY）
发信通道：console（用户收不到信，只写服务端日志）
短信通道：未开通（如实回 503，不假装发短信）
-- 未设置的项 --
  [必须] SESSION_SECRET（会话）：缺它时 /api/* 一律回 503 E_NOT_CONFIGURED ——「未开放」是如实回答，不是坏掉
        怎么补：生成一串随机字符（openssl rand -hex 32），填进托管平台的环境变量
  …
```

**三档分得清**，这是自检最容易做错的地方：
**必须**（缺了就起不来：`SESSION_SECRET`、Supabase 那一对）／
**这一件需要**（缺了只是发不出真信：发信商密钥）／
**可选**（有它更好：站名、Cookie 名、冒烟开关）。
混成一张「缺 6 项」的表，用户会以为不配齐就用不了 —— 而事实是
**一个都不配也照样能完全离线使用**（这是 1A 立的第一条边界）。

**只报缺、不报值**：输出里连密钥的长度都不出现（长度是密钥信息的一半）。
这条是硬性的，因为**这段文字就是给人贴进 Issue 的**。
`test/ops.test.js` 里拿三个假密钥钉死这一条。

**`.env` 的真值不进仓库**：`.gitignore` 挡着 `.env` / `.env.local`，
但 `.env.example`（空模板）**要提交** —— 这两条互为反面，都进了断言。

#### ② 一次收干净：**同一件事两端各写一份**的四处漂移

2A/2B 反复踩的是同一类坑：**限制写在 A 处、读取在 B 处，谁也不报错**。
2C 把这条线拉出来逐处对拍（`test/api.test.js` 第十九节），改了四处：

| # | 原先 | 现在的症状（改之前） | 改法 |
|---|---|---|---|
| ① | 频控超限回哪个码：服务端认 `phone`、前端不认 | 同一个超限，本机版说一句话、服务端版说另一句 | 两端各有一个 `rateCode(bucket)`，**逐字同表**，由对拍守着 |
| ② | 频控四层的**文案**：服务端四层共用「发得太快了」 | 用户十分钟没点过按钮（是别人在同网段刷）也被说成「你发得太快」 | 服务端补 `RATE_MSG`，与前端 `ERR` 表逐字一致 |
| ③ | 频控**档位表**：`ip` 档只有服务端有 | 同一份签名两边行为不同（这类差异没人会去查） | 前端补 `RATE.ip`（30/时、100/日，与服务端同值） |
| ④ | **冷却时长**：服务端两个键（邮箱 / 短信），前端一个常量 | 「将来单独收紧短信」那天，两端各说各的秒数 | 前端补 `SMS_RESEND_COOLDOWN_MS`，与 `config.smsResendCooldownMs` 同值 |

> 本机版**没有真的 IP 可取** —— 补 `RATE.ip` 的意义不是「现在能拦住谁」，
> 而是**两端同一张表**：一条档位只在一端存在，就是下一个人踩坑的地方。
> 真正喂给它的 key 由调用方决定（浏览器里就是「本机」这一个桶）。

顺带把 `E_RATE_IP` 补进前端错误码表 —— 服务端 429 的码是**直接回给界面看的**，
前端 `messageOf` 认不出它就会掉进「操作没成功，请稍后再试」这句兜底。

#### ③ `/api/me` 如实自报**开通状态**（「不假装」那条的延伸）

§4.9 第 2 条要求界面如实标注「由服务器判定」。可**一台服务器自己是什么状态**，
用户此前看不到：发信靠 console 的实例、库在内存里的实例，
与一个配齐的实例，说的话不是同一件事。

于是 `/api/me` 多下发一个 `channel`：

```jsonc
{ "uid": "u_…", "plan": {"tier":"free"}, "role": "user", "mask": "a***@b.com",
  "channel": { "mail": "resend", "delivered": true, "db": "db", "sms": false } }
```

三个字段全是**事实**，且全部取自既有的判定函数（`cfg.mail()` / `cfg.hasDb()`），
**不在这里重算一份**（`config.mail()` 那段注释写着重算的下场：假绿且不报错）：

- `mail` / `delivered` —— console 就是「真实用户收不到」，如实说
- `db` —— `memory` 就是「重启即丢」，如实说
- `sms` —— 与 2B 的 503 同口径，没接商就是 `false`

客户端**收下但不落盘、不参与判权**（`AccountApi.channel()`）：
它是「这一轮问到的实情」，缓存一份必然与服务端真实状态漂移。

### 4.12 2D 期「配置与真开通」已落地（2026-09-17）：那一步从「照着一篇文档点鼠标」变成一条命令

> 2C 把「缺哪个变量」做成了可执行的（`npm run doctor`），但**「照着补齐」这件事本身**
> 还散在三处：文档里一句「去 Supabase 建项目」、`.env.example` 里一句
> 「Project Settings → API」、以及只有做过的人才知道的那些坑
> （service_role 不是 anon、SPF/DKIM/DMARC 三条 DNS、每 5 天探活为什么不能每 7 天）。

#### ① 为什么 2D 还能有代码可写

2D 原本写的是「**唯一没有业务代码可写**的一步」。这句话成立 —— 但它说的是
**业务代码**。2D 真正缺的不是代码，是**回执**：

| 缺什么 | 后果 |
|---|---|
| 步骤没有唯一的存放处 | 文档说「去 Supabase 建项目」、模板说「Project Settings → API」、探活说「填托管平台的 secrets」—— 三份各写各的，改一处必然漏两处 |
| 不在本机也走一遍就不知道对不对 | 只有「部署 → 打开登录页 → 等一封邮件」这一条验证路径，而那要走完 5 步之后 |
| 「最少配什么」没人明说 | 用户照 `.env.example` 从上往下填，填到一半以为必须填完 |

于是 2D 的产出是**把上面三件补上**，且仍然是「配几个变量」这一步的**可执行形式**。

#### ② `node scripts/doctor.js --steps`：五步、每步都有本机回执

| 步 | 做什么 | 在哪配 | 本机回执 |
|---|---|---|---|
| **A** | 生成会话密钥 | 托管平台的环境变量 | 自检里 `SESSION_SECRET` 从「未设置」变「已设置」 |
| **B** | 建 Supabase 项目 + 跑 schema + 拿两个值 | 托管平台环境变量 | 自检里「最低线已过」（`ok:true`） |
| **C** | 注册发信商 + 验域名 + SPF/DKIM/DMARC | 托管平台环境变量 | 自检里「发信通道」从 `console` 变成真通道名 |
| **D** | 探活 + 备份两个定时任务 | CNB 仓库的 `.cnb.yml` | 仓库里能看见这两条流水线；手动触发一次即回执 |
| **E** | 配完**当场验收** | 本机 `curl` | 下面那段四步命令，一步一个明确结论 |

**五步的次序不能颠倒**：A、B 是**必须**那两项（缺了接口整体 503 / 只用内存存储），
C 只影响「这一件」（发不出真信），D 是**可用性兜底**（不做的话第 8 天项目
会被 Supabase 暂停，而用户看到的不是「有点慢」而是「打不开」）。

#### ③ D 为什么落在 CNB 而不是 GitHub Actions

§1.2 A 写的是「GitHub Actions 探活」，那条判断的依据是
**「不引入任何新服务、不需要服务器」**——而本项目的真实情况是**反过来**的：

- CNB 是**本仓库（`npu-gpu-cpu/poem`）的主仓库**，`.cnb.yml` 在这儿
- GitHub（`ashleyzhang2028/poem`）是**同步出去的镜像**，代码由 CNB 单向推送
- 密钥（`SUPABASE_*`）放在 CNB 的**密钥仓库**里，一个地方注入、探活与备份共用

在 GitHub 上做，等于把密钥多复制一份到第二个平台，还要让镜像仓库反向承担
「保活主仓库的数据库」这件事 —— **成本比 CNB 上做高，收益一样**。
所以 D 的两条定时任务写在 `.cnb.yml`（`crontab:`，最小间隔 5 分钟，
时区 `Asia/Shanghai`），探活的判定口径不变（必须打到数据库、必须每 5 天）。

**探活的请求头（2026-09-17 修）**：`apikey` 头要填的是**密钥本身**，不是
`SUPABASE_URL`。原先写的是 `-H "apikey: $SUPABASE_URL"` —— 把一个 URL 当 key
发出去，Supabase 一律回 **401**。这条的杀伤力不在「探活红」，在**它看起来像
密钥仓库没配好**：症状是「密钥明明注入了，探活却天天 401」，于是下一个人会
反复去查密钥仓库，而真正要改的是这一行。PostgREST 认两个头，同一个
service_role key 两处都要带：

```
-H "apikey: $SUPABASE_SERVICE_KEY" -H "Authorization: Bearer $SUPABASE_SERVICE_KEY"
```

**两条排在 D 步最后才看得到的坑**：**①** 备份镜像的**大版本要跟服务端一致** ——
`supabase-backup` 用的是 **`postgres:17`**，不是 `postgres:16`；`pg_dump`
**不改**连比自己新的服务端，16 的客户端去连 Supabase 的 17.6 会在读到数据之前
就以 `aborting because of server version mismatch` 退出（`server version: 17.6;
pg_dump version: 16.15`）—— 报这句话**与连接串无关**，详见 §5.9，服务端升大版本时
`.cnb.yml` 里那一行要跟着升（反方向 —— 客户端比服务端新 —— 是允许的）；
**②** `SUPABASE_DB_URL` 本身怎么来。

**备份还要第三个值 `SUPABASE_DB_URL`**：它**不能在控制台直接复制** ——
去 Project Settings → Database → Connection string 取模板，再把
`[YOUR-PASSWORD]` 整体换成数据库密码（那串明文只在建项目时出现过一次，
忘了就 Reset database password）。密码里含 `@ : / # ?` 时必须百分号编码
（`@` → `%40`），否则 `pg_dump` 会把密码里那一段当成主机名，报
`could not translate host name` —— 看着像 DNS 坏了，其实是密码没转义。

#### ④ 验收：配完之后「怎么确认它真的成了」

B 的判据与 E 的第 ① 条指向**同一条命令** —— **它只回答事实，每一步都有一个明确结论**：

```
curl -sS -o /dev/null -w '%{http_code}\n' "$SUPABASE_URL/rest/v1/accounts?select=uid&limit=1" \
  -H "apikey: $SUPABASE_SERVICE_KEY" -H "Authorization: Bearer $SUPABASE_SERVICE_KEY"   # 期望 200
curl -sS "$SITE_URL/api/me" | head -c 200                                        # 期望 401 E_NO_SESSION（不是 503 E_NOT_CONFIGURED）
POST /api/send-code → {"codeId":…,"delivered":true,"transport":"<你配的那家>"}    # delivered 必须是 true
curl -sS -o /dev/null -w '%{http_code}\n' -X DELETE "$SITE_URL/api/account"     # 期望 401（不是 500）
```

**这四条判据都只认「如实」**：`/api/me` 回 401 才说明会话可签（回 503 就是
`SESSION_SECRET` 没生效）；`delivered:true` 才说明真发出去了（`console`
通道**永远**是 `false`，这条是 2C 定的，2D 不改）。B 的判据、E 的第 ① 条、以及 `--steps` 打出来的文字，
是**同一份字符串**（`test/ops.test.js` 里有断言守着 —— 三处各写一份，改一处必漏两处）。

#### ⑤ 这一步**不做**什么

- ⛔ **不改任何业务代码** —— 2D 配完之后 `git status` 是干净的（真值进平台，
  不进仓库：`.env` 被 `.gitignore` 挡着，探活用的密钥在密钥仓库里）
- ⛔ **不替用户注册账号** —— Supabase / 发信商都要本人邮箱与手机号，
  AI 做不了，也不该代持
- ⛔ **不发「已开通」这类话** —— 自检的输出只报「缺哪个」，不报「配得多好」
- ⛔ **不在探活里打印密钥** —— `-o /dev/null` 是有意的，响应体里可能有账号数据

### 4.14 2.2 期「服务端权威发放」（2026-09-17 回答 Issue #159）：名单从「本机登记」变成「服务端判定」

> ✅ **2.2 已落地**。2.1 把三处旧话按状态分叉之后，剩下的一件就是
> `docs/auth-design.md` §3.5 里那句一直欠着的话：
> 「真正的权威发放要等 1 期服务端（`POST /admin/grant`）」。
> 1 期早已做完，这一条还欠着 —— 2.2 就是把它补上。

#### ① 为什么这一条必须做，且必须**现在**做

`/admin/` 页上的名单从 0 期起就是「手工发邀请码的本机版」：管理员按掩码
写好名单 → 导出给对方 → 对方自己导入 → 掩码对上就生效。
它有一个**明说过的**局限：**对方改一行存储就能升级**。

服务端接通（2A）之后，这个局限就变成了一个**自相矛盾**：
`/api/me` 明明已经在下发服务端判定的 `plan`，`js/entitlement.js` 的
`identity()` 也写着「服务端那份优先」—— 但**服务端那一份从来没有被谁写过**。
于是「权威判定」这件事在代码里是一条**断链**：

| 断在哪 | 症状 |
|---|---|
| 没有任何接口能写 `accounts.plan` | 库里所有账号的 `plan` 永远是 `free`（`accountRow()` 就是这么建的） |
| 本机名单是唯一的发放途径 | 于是「层级由服务器判定」只对**手改过库**的人生效 |
| 而手改库这件事没人说得出判据 | 3 期的额度（按 uid 计数）就没有可依赖的层级来源 |

一句话：**2.2 是「服务端判定」这句话从注释变成事实的那一步。**

#### ② 接口：两条写、一条读（第 7~9 个函数，`api/admin/`）

```
POST   /api/admin/grant    req { emailMask, tier:"free"|"pro"|"max", until? }
  res  200 { matched, changed, uid?, tier, until, by, at, note }
       400 { code:"E_TIER"|"E_MASK"|"E_UNTIL" }
       401 { code:"E_NO_SESSION" }   403 { code:"E_FORBIDDEN", message }
       429 { code:"E_RATE_DEVICE", retryAfter }   503 { code:"E_NOT_CONFIGURED" }

DELETE /api/admin/grant    req { emailMask }        ← 收回：等价于发一个 free
POST   /api/admin/grants   req {}   res 200 { grants:[{emailMask,tier,until}], store }
```

**四条不许含糊的口径**（前三条都钉进了 `test/api.test.js` 第二十一节）：

1. **角色闸在服务端**。`accounts.role` 不是 `owner` / `admin` 一律 `403`。
   ⚠️ 这一节全部**直接打 HTTP**、一个界面都不经过 —— 因为要测的正是
   「把入口藏起来**不是**安全边界」这件事（`docs §3.4`）。
   客户端 `isOwner()` 在拿不到服务端角色时有「本机主人」兜底，服务端**没有**：
   两边的**兜底形态**故意不同，但**同一个明确角色**的答案必须一致（有对拍断言）。
2. **只认掩码，不认明文邮箱**。库里本来就不存明文（§2.4 第 1 条），
   接口也**不自己掩一次** —— 掩码规则若有两份实现，漂移的症状是
   「管理员明明发了，对方却拿不到」。形状不对一律 `400 E_MASK`。
3. **命中 0 条不是错误**，而是**一种如实的状态**：本方案里
   「对方先登录一次」才会在库里留下一行，管理员才可能拿到他的掩码。
   所以接口如实回 `{matched:0, changed:false}` + 一句成因。
   ⚠️ **绝不「查不到就替他建一条」**：掩码是**不可逆**的
   （`a***@qq.com` 对应哪个真实邮箱谁也不知道），造出来的是**永远登不上的幽灵行**。
4. **改了就要真的生效**。发放写的是 `accounts.plan` / `plan_until`，
   也就是 `planTier()` 唯一读的那两列 —— 于是发完之后 `/api/me` 下发的
   `plan.tier` 与 `features[]` 立刻跟着变，**不需要第二套判定**。
   收回等价于「发一个 free」：**没有第二张表**，也就不会出现
   「收回只做了一半」这种半生效状态。

#### ③ 两份名单的关系（这是本轮最容易被说混的一处）

| | 服务端名单（2.2 新增） | 本机名单（0 期就有） |
|---|---|---|
| 存在哪 | Supabase `accounts.plan` / `plan_until` | 浏览器存储 `poem_plan_grant_v1` |
| 谁判定 | **服务器**（`/api/me` 下发） | 本页自己算 |
| 改得动吗 | 对方改一行存储**改不动** | 对方改一行存储**就能改** |
| 怎么传给对方 | 不需要传（对方刷新即生效） | **要对方自己导入** |
| 是权威吗 | **是** | **不是**（界面上明写） |
| 是收费凭据吗 | **不是**（本站不收款，也不再做收费 —— 用户 2026-09-17 裁） | 不是 |

**两份不自动同步**：服务端发了一条，对方那台机器的本机名单不会跟着多一条。
这不是缺陷而是**边界**：「本机名单传不出去」这条局限在 2.2 之后**仍然成立**，
只是它不再是唯一的路。`/admin/` 页把两块**分成两张卡**、各有各的说明
（`test/account-pages.test.js` 的第六之二节守着「不许混成一块」）。

**发放失败时绝不自动回落本机名单**：那会让管理员以为服务端已经发好了 ——
而对方刷新后仍然是 Free。界面上如实分五种情况说话
（`ok` / `guest` / `not-configured` / `no-channel` / `unavailable`），
并明确提示「可以先用『只发到本机名单』兜底，但那一份不是权威」。

#### ④ 前端：发放走接线层，本页不自己 `fetch`

`js/auth-api.js` 加三条传输（`grant` / `revoke` / `grants`），
`js/account-api.js` 加三条接线（`adminGrant` / `adminGrants` / `adminRevoke`）——
与 2A 那两根线**同一条边界**：失败不打断、不假装、不清数据、不做无谓请求。

⚠️ `js/account-api.js` 里有一条**刻意不合并**的闸：发放要的通道**单独判**
（`grantChannel()`），**不并进** `refreshMe()` 用的那个 `usable()`。
理由很实：老缓存里的旧 `AuthApi` 没有这三个方法，若并进同一个闸，
症状会是**层级再也不更新** —— 那是拿一个不相关的新功能去废掉既有功能。
缺方法时如实回 `reason: "no-channel"`（刷新即可），且 `refreshMe()` 照常工作
（`test/account-bind.test.js` 第十七节第 ⑦ 条钉着这条）。

`403` 尤其**不许被说成「连不上」**：`reason` 仍是 `ok`，
原样把服务端那句「这一条只对管理员开放」带上去 —— 说成「连不上」用户会一直重试。

### 4.15 3 期「不花钱的那三件」设计方案（2026-09-18 回答 Issue #159）

**用户的问题**：3 期不花钱的**飞花令 / 题库复习 / 现场考试**这三部分怎么设计，
其中**飞花令与现场考试归 Max，题库归 Pro**。

> ⚠️ 2026-09-19 更正（Issue #163 末条）：**「现场考试」这个名字已收成「试题模拟」**，
> 且用户把原先挤在一个格子里的两件事裁成**两条能力**：
> 「一个是古诗词大会的**集子**的访问权限，一个是在线**试题模拟**的权限」
> → `exam.gathering`（《古诗词大会》集子，Max）与 `exam.paper`（在线试题模拟，Max）
> 在对比表上是**两行、两个钩叉**。下文出现的「现场考试」按当时的叫法读，
> 键名与层级不变（详见 §5.0.1 末尾那一节）。

**结论先放前面**：这一节只写**设计**，一行代码都不动。
不是因为「不值得做」，而是因为**它的门槛现在发不出去**：这三件全挂在 Pro / Max 上，
而 Pro / Max 现在只能靠管理员手工发放（2.2 之后这一条总算**发得动**了，但仍是手工）。

#### ① 先说清楚：这一版**改了层级口径**，与现有代码不一致

| | 现有（`js/entitlement.js` / `docs/auth-design.md` §3.5） | 本次用户口径 |
|---|---|---|
| 飞花令 | `feihualing` → **Pro 起** | **Max** |
| 考试与题库 | `exam.paper` → **Pro 起** | **拆两半**：题库 Pro、现场考试 Max（2026-09-19 又拆出 `exam.gathering`）|

也就是说这一版不是「新加三条能力」，而是**改两条既有能力的门槛，再按场景拆开**。
口径以用户 2026-09-18 这次为准（写在 Issue #159 里），
落地时要同步改三处：`js/entitlement.js` 的 `CAPS`、`test/entitlement.test.js`
第 68~69 行的断言、`/plans/` 那张对比表（它是**当场问内核**算出来的，所以会自动跟着变 ——
但 `docs/auth-design.md` §3.5 与 `/terms/`、`/privacy/` 的措辞要人改）。

**一条不许含糊的边界**：`/terms/` 里已经写明「Free 用户可用全部现有功能」
（`terms/index.html` 第二条）。这三件**新增**能力放 Pro / Max **不违背**那句 ——
但**不许顺手收紧任何现有能力**（课内 261 首、六部集子、排程、注音、导出 JSON、
登录后的语音朗读），那是「拿现有功能当人质」，0 期就划了红线。

#### ② 三件东西的共同形状：它们**不是三个功能，是同一个引擎的三张皮**

真正该先定下来的是一件小事：**这三件都只需要「诗词条目」的同一个子集** ——
`{ id, title, author, dynasty, text, translation }`。仓库里现成的 `data/index.js`
（`window.POEMS_ALL`，261 首课内，正文经 `masterTextOf` 取回）与六部集子
就是这批数据的全部来源，**不需要新数据、不需要新接口、不需要一个字的新诗**。

于是三件共用一条内核层（纯逻辑、零 DOM、零网络，与 `scheduler.js` / `review-models.js` 同款）：

```
js/flying-core.js   ← 飞花令（判令、取句、AI 对句的落点）
js/quiz-core.js     ← 题库（抽题、判分、错题回流）
js/exam-core.js     ← 现场考试（组卷、限时、交卷、评级；今名「试题模拟」）
```

三条纪律（都是本项目已经踩过坑的那三条）：

1. **内核纯逻辑**：能在 Node 里直接跑，不碰 DOM、不碰 `localStorage`、不发请求
2. **能不能用只走 `Entitlement.can()`**：页面里不许出现 `tier === "max"`
   （有源码扫描测试守着）
3. **没实现就如实说「这一层还没开」**：3 期界面一个字都不提前渲染
   （2A 起就定死的纪律，见 §5.0）

#### ③ 飞花令（Max）：一句诗里有没有那个字，是**判据**不是噱头

**玩法**（够简单、够传统、够小孩玩）：

```
系统抽字（如「月」「花」「春」）
  → 玩家从题库里说一句含这个字的诗（打字 / 选字两种输入）
  → 判「含不含」→ 判「是不是题库里的」（防自己编）
  → 判「说没说过」（本局不得重复，防「举头望明月」连说十遍）
  → 说过就轮到对手（AI / 另一个孩子）
```

**判据只有四条，条条可单测**：

| 判据 | 怎么说清「AI 说的也算数」 |
|---|---|
| 含令字 | `text.indexOf(ch) >= 0`，**逐字**比，不做繁简 / 异体转换（转换表是另一个坑，本期不碰） |
| 在题库内 | 按**归一化后的句子**匹配（去空白、去标点），命中记 `id` |
| 未重复 | 本局已用 `id` 集合；**同一首的不同句算不同**（「月落乌啼霜满天」与「江枫渔火对愁眠」是两句） |
| 轮次与胜负 | 轮到谁说不出（超时 / 认输）谁输；**AI 那边也必须走同一个判据**，不许它「知道有这句」就跳过校验 |

**AI 对句的落点（唯一花钱的地方，且可以不接）**：先做**纯检索版** ——
从题库里挑一句含令字的、没用过的，**直接从 `text` 里取句**，零成本、零延迟、可离线。
将来接 AI 时，它只负责**把一句话变成候选**，判据仍然走上面四条 ——
即「AI 出题、内核判题」，AI 说了不算。这一层现在**不接任何 AI 商**。

**为什么归 Max**：不烧钱，但它是三件里**最像「玩游戏」**的一件，
放最高一层不会让免费版显得残缺（free 一个诗库都不少）。

#### ④ 题库复习（Pro）：把「错过的」变回背诵题，**批改权仍在 `scheduler.js`**

这一件最容易被做成第二个背诵系统 —— 那样必定与每日计划打架。所以设计上钉死一条：

> **题库不产生新的复习排期，它只产生「今天该复习哪几首」的另一种来源。**

```
ProgressStore（唯一进度真相）
   └─ 每首的等级 / 次数 / 下次复习时间（既有）
        ↑
错题回流：答错 → 该首标「重新学过」→ 交给 scheduler 重排 → 回到每日计划
```

- **题目形状四种，全部由现有字段生成**：填空（挖正文里的字）、
  下文（给上句选下句）、作者朝代、译文连线；一题一个 `poemId`
- **判分只管对错，不管排期** —— 答对答错怎么影响下次出现，由 `scheduler.js` 说
- **错题按首去重**：同一首错三次也只回流一条（否则一次手滑能把今天的计划塞满）
- **题库复习与每日计划共用同一份进度**，不另起一套 `localStorage` 键
  （另起一套的下场是「清了缓存，错题全没了」）

#### ⑤ 现场考试（Max · 今名「试题模拟」）：入口与平时那三件**分开**，且**逐题不中断**

「现场」两个字要落成行为，落到三处：

| 试题模拟 | 平时复习 |
|---|---|
| 入口独立（`/exam/`），不在每日计划里 | 混在每日任务里 |
| **限时**（默认 20 分钟，到点自动交卷） | 不限时 |
| **交卷前不给对错**（不许边考边看） | 答完立刻说对错 |
| 交卷出**一张卷面**（得分 / 逐题对错 / 该回流的题） | 一条进度记录 |
| 归 **Max** | free / pro 照旧 |

- **组卷**：按学段 / 册次抽 N 题（默认 10 题），**先定「题量与时长」，再定「分数」** ——
  题量是设计参数，分数是判断题，先定题量不会返工
- **中途退出**：不评分、不产生错题回流（现场考试是「一次完整的动作」，
  半途而废不应污染背诵进度）；界面上如实写出来
- **成绩只作一次记录**：存本机（与进度同域），并写明**不是能力评估** ——
  别让家长把它当分数看（`/terms/` 那条「不替代课堂教学，不对成绩作承诺」同源）

#### ⑥ 顺序与「什么时候才开工」

```
现在可做、且不接任何 AI 的一件：三件内核的「形状 + 判据」
  └─ 前置：Pro / Max 名单里得先有人（2.2 之后发得动了，但仍是手工）
      ↓
飞花令（纯检索版，零成本、可离线）→ 题库复习 → 试题模拟
      ↓
真正花钱的那一层（AI 讲解 / 纠音 / AI 对句）等定价与资质，见 §5.0
```

**唯一现在就该做的代码改动是一条小账**：`/plans/` 与 `docs/auth-design.md` §3.5
里的层级口径要与本次口径对齐（飞花令 Pro→Max、考试拆两半）。
⚠️ 但它**同属 3 期**，与「不提前渲染 3 期界面」是同一条纪律：
口径改了，界面仍然一个字都不渲染 —— 改的是**内核表与文档**，不是给用户看的承诺。

#### ⑦ 这一节**不做**什么

- ⛔ **不接任何 AI 商**、不建额度表（额度大小取决于定价，定价取决于资质，§5.0 那条判断不变）
- ⛔ **不提前渲染 3 期界面**（不写「即将上线」「敬请期待」，有反向断言拦着）
- ⛔ **不收紧任何现有能力**（free 现有的一件都不收回，`/terms/` 那句已经写明）
- ⛔ **不在考试里做能力评估**（只是一次练习记录，不做「你孩子古诗词水平 XX 分」这类话）
- ⛔ **不引第三方题库**（261 首 + 六部集子就是全部素材，不新增内容源）

### 4.15 「跨设备同步开关」重做两轮：先改外观，再修「滑块根本没出现」（2026-09-18 回答 Issue #163）

用户原话（第一轮）：「跨设备同步选择框太丑了，改进。」
用户原话（第二轮，上一版上线之后）：
「跨设备同步 现在这个选择项你是认真的吗？奇丑无比，
你哪怕设计成 iPhone 设置里的选项开关一样也行啊。」

#### 第一轮：把浏览器默认的 checkbox 换掉

旧样子是**浏览器默认的 checkbox**：一颗 13px 的方框（白底 / 灰勾 / 圆角 2px）
+ 旁边一颗写着「关」「开」的文字。三处合起来都说不清：

1. 那颗方框与全站的纸面 / 描金细线 / 深青实底是**两套语言**
   （浏览器自带样式在 iOS 与安卓上还不一样）；
2. 「关」「开」两个字既像状态、又像一颗可点的按钮，而它其实是 JS 改写的文案；
3. 一行里横着「方框 + 关 + 一大段说明」，开关到底在哪儿要读两遍。

第一轮改成自绘的胶囊（40 × 24，滑块 18，起点 2），外观那一套留用到今天：
开着 = 深青实底 + 米白滑块 + 描金内边（与「年级」「复习算法」的选中同一句）；
关着 = 纸底 + 界行描边 + 淡墨滑块；不可用 = 更淡的底 + `cursor: not-allowed`。
一行 = `左标签 · 右开关`，说明文字挪到开关**下面**单独一行；那颗「关」「开」
文字标签删掉（状态由开关本体表达）。

#### 第二轮：外观对了，但那颗圆点一次都没出现过

> ⚠️ 这一节是整份文档里最值得看的一段「测试为什么没挡住」。

第一轮的结构是：**input 自己当胶囊**（`appearance: none` + 40×24 + 描边），
滑块是**另一个可以长在 DOM 任何位置**的 `<span class="switch-track">`，
两者靠 `position: absolute` 去叠。

而 `.switch` / `.settings-item` / `.settings-group` / `.settings-groups` /
`main.settings-page` / `.app` 一路上**全是 `position: static`** ——
于是滑块的包含块是**初始包含块**（文档），不是轨道：
`left: 2px; top: 2px` 把它钉在页面左上角（真机实测 `getBoundingClientRect()`
给出 `x = 2, y = -415`，在屏幕上方之外），`:checked` 那句 `translateX(16px)`
只是把它从页面 x=2 挪到 x=18。

**用户看到的**：一颗空药丸 —— 开着只有深青底、关着只有一圈描边，
那颗圆点从头到尾没出现过一次。

**而当时那五条守卫全绿。** 它们查的是**源码字符串**：
「有没有 `appearance: none`」「尺寸是不是 40/24」「`translateX` 是不是
按尺寸算出来的 16」—— 源码一条不错，画出来全错。这就是「合成值」那一类
假绿：把结论拆成几个各自成立的断言，而它们拼起来的那个东西没人验过。

#### 现在这一版（手机系统开关那一路）

```
<label class="switch">
  <span class="settings-label">跨设备同步</span>
  <input class="switch-input" type="checkbox" role="switch">   ← 0 尺寸，只管状态与焦点
  <span class="switch-toggle" aria-hidden="true"></span>       ← 可见的轨道；滑块是它的 ::after
</label>
```

- 滑块改成轨道的 **`::after`** —— 与轨道是同一个盒子里的父子（伪元素），
  「画不到一起去」在结构上不再可能；
- 轨道自己 `position: relative`，是滑块的包含块；
- 真实 `<input>` 留着（键盘 / 读屏 / 原生 toggle 都用它），画成 **0 尺寸**
  不占位；焦点环 `:focus-visible` 改画在**轨道**上（画在那颗 0 尺寸的
  input 上等于看不见）；关掉 `:focus` 只留 `:focus-visible`（鼠标点一下
  不该留下键盘才有的光晕）；
- 位移 180ms、轨道换色 220ms —— 与 `.seg` / `.chips` 的选中过渡同一档。

#### 守卫换了一整代：从「查源码」改成「量渲染」

| 层 | 判什么 | 为什么在这一层 |
|---|---|---|
| `test/ui-consistency.test.js` §13 | 尺寸只有一个来源、行程按尺寸算出来、三态各一句、结构（滑块是轨道的 ::after） | 纯源码可判的部分 |
| `test/pwa.test.js`（Chromium） | **滑块几何落在轨道内**、开着真的右移且右端不越界、滑块与轨道同一高度带、真实 input 0 尺寸、轨道点得到 | ⚠️ 这一层是必须的：jsdom **不支持** `getComputedStyle(el, '::after')`，会把**父元素**的样式原样返回（实测 `position` 读出 `relative`、`width` 读出 40px，全是轨道的值），拿它量滑块等于什么也没量 |

反面样本已核：把结构退回第一轮（独立 `.switch-track`），浏览器那一段立刻
6 条判红（含「点不到 `.switch-toggle`」），源码那一段也判红。

### 4.18 「那 5 条失败」收干净：两次落在同一处的合并产物（2026-09-17 回答 Issue #159）

**背景。** #171（同步开关改成自绘胶囊）与 #173（页脚去横线 + 全站链接无下划线 +
补齐开关样式）各自单独都全绿；两次**落在同一份 `css/style.css` 的同一个类名上**，
合进来之后全量测试红 5 条，且一挂就是两轮没人再看它们。

**真正的病根是两次改动各自只做了一半：**

| 来源 | 它加了什么 | 它**没**删什么 |
|---|---|---|
| #171 | `.switch` / `.settings-label` / 新口径的 `.switch-input`（自绘胶囊本体）与 `.switch-track`（滑块） | 旧的透明覆盖层那一套样式 |
| #173 | 旧口径的 `.switch-row` / `.switch-input` / `.switch-track` / `.switch-label` 一整套 | —— |

于是同一份表里出现了**两段同名规则**，而且语义还相反：
`.switch-track` 在前一段是**轨道**（40×24），在后一段是**滑块**（18×18）。
`.switch-label` 更是：样式表里给它写了规则，HTML 里那颗 span 早就删了。

**两条症状，一条真 bug、一条假警报：**

- **假警报（3 条）**：`test/ui-consistency.test.js` 的 `ruleOf()` 按设计是
  「累积」读同名规则的声明。读数读到了**先写的那一段**（`width: 40px` = 轨道），
  于是「滑块 18px」「滑块落在轨道内」这两条按 40 去算，算出 `40 − 2 − 40 − 4 = −6`。
  页面本身完全正常（浏览器用的是后写的那段）—— **测试红、页面对**，
  比漏判更难查，因为没人会去怀疑读数。
- **真 bug（2 条）**：`.switch-row` / `.switch-label` 的 DOM 断言还按旧写法写，
  而自绘版**故意删掉了**那颗写着「关 / 开」的 span。这一层还漏了一道真护栏：
  第 ⑨ 段那些「样式表里有没有这几条规则」的 `chk` 全都通过 —— 因为样式表里
  **确实有**那两条规则，只是**没有任何 HTML 用它们**。

**这一轮做了四件（都不改任何可见行为，只让守卫读得对）：**

1. `ruleOf()` 改成「累积 + **同名属性留最后一条**」—— 与浏览器的生效规则一致，
   「哪个值真生效」与页面终于说的是同一件事；
2. 样式表里删掉 #173 补进来的那一整段旧口径规则（`.switch-row` /
   `.switch-label` / 旧 `.switch-input` / 旧 `.switch-track`），
   并补一条**反向断言**：这两个类名不许再出现在样式表里；
3. 那 2 条 DOM 断言按自绘版翻成正向（`label.switch` 包着 input 与滑块、
   旧的文字标签已删），「透明覆盖层」那条改成「不许把 form 控件藏掉」
   （`display:none` / `visibility:hidden` / `opacity:0` 三种都判红）；
4. 顺手把两处**已经随裁决过期的断言**改口：`api.test.js` 里「note 说清为什么
   没计费」原先要「定价」二字，现在本站不收款，该说的是「免费、不限次」，
   但**实质不变**（不许写成「已计入额度」）；`account-pages.test.js` 里
   「没有收款能力（4 期才做）」改成「不收款、不是付费凭据」。

**一条教训。** 同一个类名在同一份样式表里出现两段，代码不会报错、
页面也照常渲染 —— **只有「按累积读」的断言会红，而红得还像测试自己写错了**。
所以第 2 条那条反向断言比修好这 5 条更重要：它防的是下一个人再走一遍。

### 4.19 ②篇目 PDF / 打印页（2026-09-17 回答 Issue #159 · Pro）

能力键 `export.paper`（Pro）。它是 §5.2 第 ② 批 —— 与 ① 同一类病：
`/plans/` 上写着它、代码里一行没有，那一行就是**假话**（§1 第 3 条）。

**它长在哪儿。** 入口在 `/settings/lists/`（我的清单）那一组的**下面**，
第二入口在诗词详情页工具条上（「这一篇打出来」）。不新开一页：
这一件事**没有自己的状态** —— 它用的就是「哪一份清单」。
所以与「古诗词大会」同一条路子：**就地叠层**，地址栏不动，返回键一层退一层。

#### 版面内核单独一份（`js/print-core.js`）

「这一份打出来是几页」是**用户在点打印之前就该看到的信息** ——
家长挑的是「够一张 A4 两面的量」，而不是打出来才发现多出一页。
把它写进页面里，就只能等浏览器排完版才知道；写成内核（纯逻辑、零 DOM），
点之前就说得出来，而且能被逐条断言。

| 参数 | 值 | 为什么是它 |
|---|---|---|
| 纸型 | A4 纵向（1 栏 52 行）/ A4 横向（2 栏 34 行）/ A5 半张 | 三种都是家里真有的纸 |
| 页眉页脚 | 占 2 行 | 不算内容，但**真的占位置** —— 不算进去页数就会偏少 |
| 卡片间距 | 1 行 | 一张卡片前后各留一点，读起来才不糊成一片 |
| 卡片高度 | 正文行 + 标题 1 + 出处 1 + 间距 1 | **算出来的**，不是估的 |

四条口径：

1. **标点照排** —— 原文怎么断，纸面上就怎么断。不按字数重排
   （「七言绝句排成两行」好看，但改了一次原文，而这份纸的用处之一正是拿去抄）。
   只有两种行会被丢掉：空行、只有标点的行。
2. **三个块开关真的改纸面** —— 拼音 / 译文 / 注释格线关掉，
   那几行就真的不出现在纸上（页数跟着变）。拼音**逐行配对**贴在正文上方；
   译文插在整篇之后（不逐句对照，那会把纸面撑成两倍厚）；
   格线是**真的空行**（一条 1px 的下划线写到第三行就写不下了）。
3. **卡片不跨栏** —— 跨栏的卡片会被撕成两半，读者要来回看。
   比一整栏还高的篇目**自己占掉一栏**，并如实报进 `oversize`。
4. **没有正文的篇目不占位置，且如实计数** —— 数进 `empty`，
   界面写「另有 N 篇没有正文、没有排进来」。悄悄少一篇比多打一张纸更难发现。

#### 页数只说「约」，不说「正好」

`PrintCore.summary()` 的措辞是「**约** N 张 A4 纵向（M 篇）」。
去掉那个「约」就是一句早晚会变假的话 —— `layout()` 算的是**版面预案**，
真正的字形宽度只有渲染时才知道（不同设备的中文字体差得很远）。
它管「打几页」，不管「好不好看」。

#### 打印走浏览器，不引 PDF 库

`window.print()`。浏览器的打印对话框里「另存为 PDF」本来就是同一件事，
且各平台都有；引一个 PDF 库就是几百 KB。界面上写的是
「打印 / 存 PDF」，**不写「导出 PDF」**（那会让人以为点了就落一个文件）。

`css/account.css` 的 `@media print` 只做两件事：**收外壳**（顶栏 / 页签 / 页脚 /
按钮 / 说明字，判在元素上而不是判在 `.app` 的某一条上）、**去颜色**（省墨）。
它有一条**反向**断言钉着：那一整块里**一条 `font-size` 都没有** ——
改字号就是重排，而纸面上的断行必须是原文的断行。
预览里那条「这里是一块」的辅助虚线也在纸上删掉：纸面上每篇之间多一道横线，
只会让人以为要撕下来。

#### 一轮里修掉的两处真问题（在写这一层时踩到的）

1. **换栏漏算纸张**。原先的写法是「先把 `column` 加一，再在末尾判
   `column ≥ columns` 才 `sheets++`」—— 那个判断在**放不下而跳过**的那条路上
   会漏掉。实测：三篇各占一栏被算成**一张纸**（应当 2 张）。
   症状是用户打出来才发现多一张，而这一层的存在理由正是「点之前就说得准」。
   现在只有一个换栏入口 `nextColumn()`，跨过最后一栏就是换一张纸。
2. **只有标点的行没被丢掉**。判据原先写成「去掉空白之后还含汉字或全角标点」，
   而一行「，」自己就是全角标点，照样通过 —— 它会占掉纸上一整行，
   而那一行上什么都没有。改成「这一行里有没有一个汉字或数字字母」。

### 4.20 Issue #197「完整登录流程」（2026-09-16 回答 Issue #197）

用户原话：

> 「我要求重新设计用户的整个登录流程。使用邮箱注册，注册邮件确认，登录，
> 忘记密码，重设密码，再加一个发送随机码快捷登录，要求用户邮箱必须记录到数据库，
> 用户名等也要。以及 profile 信息等等。」

设计全文在 `docs/auth-design.md` **§4.4**（流程全图、口令怎么存、两张令牌表、
四条「不假装」、三条「不泄露」）。这一节只写**架构上动了什么**与**口径推翻了什么**。

#### ① 两次口径翻转（先说清楚，因为都是「以前写过反话」）

| 项 | #197 之前 | #197 之后 | 为什么翻 |
|---|---|---|---|
| 邮箱明文 | **不落库**，只存 `email_hash` + `email_mask` | **落库**（`accounts.email`） | 用户裁「要求用户邮箱必须记录到数据库」。第二轮的「我还是要看到这些用户」是同一个诉求 —— 掩码 `a***@qq.com` **认不出人** |
| 登录凭证 | 「一律是邮箱随机码，**不做密码**」 | **两条路并存**（随机码 + 密码） | 用户要「注册 / 忘记密码 / 重设密码」——那就是密码这条路。而随机码那一条一个字没删（家长记不住密码，两条都得在） |

两条翻转都**写进了条款**（`/privacy/` 明写「邮箱会保存到服务器」「密码不存明文」），
并在 `test/legal.test.js` / `test/account-pages.test.js` 里各有一条正向断言
（不只是删掉旧断言 —— 删掉之后没有任何东西守着新口径）。
`docs/auth-design.md` §6.1 的标题也改成了「邮箱不在**本机**落明文」，
把服务端与客户端两半分开说。

#### ② 库里多了什么（一次真的迁移，四步）

`api/_lib/schema.sql` **§6**：

```
① alter accounts add column email / email_verified_at
                        / password_hash / password_salt      （四列都允许空）
② create table verifications (...)   + RLS
③ create table resets (...)          + RLS
④ create function kb_purge_expired(now_ms)   —— 三张令牌表一起清
```

三条设计取舍：

- **四列都允许空**（`not null default ''`）。老行不必回填就能继续登录；
  把它设成 `not null` 要么让迁移失败、要么得编一个假的默认值 ——
  而「编一个假的」正是本项目最恨的那件事。
- **两张令牌表不与 `codes` 合并**。6 位数字与 64 位 hex 是两种完全不同的
  凭据（空间、TTL、失败上限都不同）；合成一张的下场是
  「确认链接十分钟就过期了」（被码的 TTL 带上）这种查不出原因的怪事。
- **新表必须 `enable row level security`**。漏掉这一段不会报错，
  只是 anon key 能读别人的令牌摘要 ——
  `test/api.test.js` 有一条断言逐表核对。

#### ③ 为什么口令那四屏**不回落本机**

这是 #197 架构上最要紧的一条判断，与 1A 期「后端挂了照样能背」那一条**不冲突**：

| 功能 | 服务端不可用时 |
|---|---|
| 背诵 / 朗读 / 导出 / 六部集子 | **照旧全可用**（§1.3 那条边界没变） |
| 随机码登录 | **静默回落「本地体验版」** —— 它本来就是本机自证 |
| 注册 / 密码登录 / 确认 / 重设 | **如实说「暂时不可用」**，绝不回落 |

理由：口令摘要要有服务端 pepper、要落库；在浏览器里存一份等于把
「谁都改得动」的东西当凭据（`docs/auth-design.md` §1 第 3 条）。
偷偷回落会给出一个「注册成功了」但换台设备就登不上去的**假承诺** ——
而那正是这个项目反复在防的那一类错。

#### ④ 「不泄露邮箱是否存在」这条要**同时**做到三处

少一处就等于没做（攻击者挑最松的那一处问）：

1. `POST /api/login`：口令错与账号不存在回**同一个响应**，
   而且**耗时也要一样**（账号不存在时照样算一次 scrypt）
2. `POST /api/reset-request`：存在与不存在回**逐字相同**的 JSON
   （测试在生产形态那一档上直接比 `JSON.stringify`）
3. 界面文案**不出现**「没注册过 / 不存在」这类断言 ——
   允许的是**条件句**（「如果这个邮箱在本站注册过…」），
   判断留给收件箱，界面不替服务端回答

#### ⑤ 前端：一页四屏 + 两张独立落地页

| 落点 | 是什么 | 为什么不塞进登录页 |
|---|---|---|
| `/login/` | 两个页签（密码登录 / 快捷登录）+ 注册、忘记密码两屏支路 | 页签切动作**不跳页**；一页只有一件主动作（实心按钮），其余收成文字链 |
| `/verify/` | 确认邮箱（`?vid=&token=`） | 用户可能在**另一台设备**上点开邮件；挂在登录页上只会落到一个空白页 |
| `/reset/` | 重设密码（`?rid=&token=`） | 同上 |

「一页一件事」这条原则**没有松**，判据从「数几个邮箱输入框」改成
**结构上每个框都在自己的互斥 pane 里**（`test/account-pages.test.js` 第十一节）——
数字会随流程增减而变，结构不该变。

#### ⑥ 两条测试与三条反向验证

- `test/api.test.js` **第廿二节**（40+ 条，走真 HTTP）：六条接口的端到端 +
  口令摘要不落明文 + 邮箱大小写 + 确认令牌一次性 / 过期 / 方向只朝上 +

### 4.21 头像：用户名首字 + 可上传的图片（2026-09-19 · 回答 Issue #163）

**用户原话**：

> 「头像印记设置和传统用户头像流程不符，让人困惑，直接删除这个功能，
>  四个颜色背景选择全部删除。直接用用户名的第一个字母或者汉字显示在头像里。
>  允许用户上传图片作为头像，在上传前进行本地压缩，支持用户进行方形裁切，
>  放大缩小裁切，然后再上传裁切后的图片作为头像到 supabase 的文件或者图像存储。」

#### ① 上一版为什么被删（不是「做得不好」，是**方向错了**）

上一版（§4.13 那一轮）是「字符印」：从**固定 12 个字**里挑一个 + 从
**固定四色**里挑一个，理由写得很足（不收集、不存图、儿童照片不上云）。

那套理由在**合规**上没错，但它把「不收集」当成了**不做的理由** ——
而用户看到的是一件他到处没见过的事：别处的头像要么是自己的图、
要么是名字首字，**没人先从 12 个字里挑一个再挑一个颜色**。
自造的流程就是「困惑」本身。

→ 结论：**那条承诺属于 `/privacy/`，不属于头像这个功能**。
改条款（补一句「自己传的图会上传到服务器」）比绑住一个正常功能便宜得多。
用户裁决做图片头像之后，`docs/todo.md` 第 5 条那三个前置的②③
（告知 + 开关）由**这一版直接落进条款与默认行为**：
不传图就一个字节都不上传，传图时界面上写着「已同步到服务器」。

#### ② 两档，一个圆

| 档 | 什么时候 | 画什么 |
|---|---|---|
| **首字印**（默认） | 没传过图 | 用户名的第一个字母 / 汉字；纯英文昵称取首字母并**大写**；昵称为空才回落到「诗」 |
| **图片** | 传过图 | 那张图（铺满整圆，`object-fit: cover`） |

**「永不空」** 仍然是硬规矩：昵称为空、图片地址裂了、盘上全是脏值，
也要有一枚印可画 —— 最后一道兜底是「诗」（与 App 图标同源）。

#### ③ 盘上形状：地址进账号域，**字节进设备域**

```
poem_profile_v1      = { v:1, nickname, avatar: { img: "<https 地址>" | "" } }   ← 账号域
poem_family_v1       = { v:1, at, profiles:[{ id, nickname, avatar:{ img }, createdAt }] }
poem_avatar_local_v1 = { img: "data:image/jpeg;base64,…" }                      ← **设备域**
```

这一分是**非做不可的**，理由与 §3.1 同源：

- **地址**属身份（换台设备也该看到同一张脸）→ 账号域，跟着同步与导出走
- **字节**属可用性（断网时它必须还画得出来，`<img src>` 指着一个连不上的
  地址就是一枚裂图）→ 设备域，**不上云、不进导出**

于是 `Avatar.display()` 是**两档回落**：有效图片 → 本机那份图 → 昵称首字。
`src`（这台设备上真能画出来的那个地址）与 `remote`（盘上那个地址）
是**两件事**，界面不许混用。

⚠️ 一张 256×256 的图 base64 有几十 KB。塞进账号域的话，
每一条进度记录推一次就是几十 KB × 篇数 —— 免费档那 500MB 是这么吃光的。

#### ④ 压缩与裁切在**本地**做（一个字节都不出去，直到最后一次上传）

`js/avatar-image.js`：

| 步骤 | 做法 | 为什么 |
|---|---|---|
| 读文件 | `createImageBitmap()`，退回 `<img>` + blob URL | 前者解码在主线程之外；**两条都带超时**（iOS 上曾有图让 `createImageBitmap` 永远 pending） |
| 压缩 | 画进一张 256×256 的离屏 canvas | 顶栏画 42px、视网膜 2x 也只到 84 —— 256 已经是 3x，再大只是白传 |
| 编码 | `toBlob("image/jpeg", 0.86)`；**原图带透明则存 PNG** | 照片存 PNG 大 5~10 倍；而把 PNG 的透明转成 JPEG 是**毁图**（透明变黑边）。判据是**原图类型**，不逐像素扫 alpha（扫一张 4000×3000 要 12M 次读取） |
| 裁切 | 归一化的 `{ zoom, ox, oy }` → `cropRect()` | 归一化让「拖到哪」与画布大小无关：手机上拖一次、桌面上同一张图拖一次，结果得是同一个框 |

`cropRect()` / `zoomRange()` / `clampOffset()` 都是**纯函数**（不碰 canvas），
所以「方形裁切对不对」在 Node 里就能对拍，不必等浏览器。

交互三档输入归到同一组状态：**单指拖**（平移）、**双指捏合 / 滚轮 / 滑杆**（缩放）。
滑杆走**对数刻度**（放大 2 倍与 8 倍的手感一致）。

#### ⑤ 上传：`POST /api/avatar`，请求体是**裸字节**

```
POST /api/avatar      body = 图片字节，Content-Type: image/jpeg|image/png
  200 { url, bytes, note }      400 E_TYPE / E_TOO_BIG / E_NO_BODY
  401 E_NO_SESSION              429 E_RATE_DEVICE        503 E_NOT_CONFIGURED
DELETE /api/avatar    200 { deleted:true, url:"" }
```

三条刻意的取舍：

1. **裸字节，不是 JSON + base64**。base64 抬体积 33%，而 Vercel 的请求体上限
   是 4.5MB。为此 `handler.make()` 多了一个 `{ rawBody: true }` 选项 ——
   外壳默认会拿 `readBody()` 去 JSON.parse 请求体，图片一进去就是
   `400 E_BAD_BODY`（症状是「传头像永远失败」，还看着像前端坏了）。
2. **按 magic number 判类型，不看 `Content-Type`**。头部是客户端说的；
   一个写着 `image/jpeg` 的 HTML 存进 **public** 桶里就是一条存储型 XSS 的引信。
   只放行 JPEG（`FF D8 FF`）与 PNG（`89 50 4E 47…`）。
3. **路径由服务端拼**（`CONFIG.avatarPath(uid)` = `<uid 前两位>/<uid>/avatar.jpg`）。
   让客户端给路径的下场是「一个登录用户能覆盖另一个用户的头像」。
   文件名固定，**上传即覆盖**（`x-upsert: true`）—— 不删旧对象：删旧的要再发
   一个请求，它失败时用户头像不变、桶里却多一份垃圾。地址带回 `?v=<时间戳>` 破缓存。

`api/_lib/avatar-store.js` 与 `store.js` 同一条纪律：**两个实现**
（supabase / memory），接口一模一样，少一个不是编译错误而是某个约束静默失效。

#### ⑥ 配置：一个 public bucket，不用建表

```
SUPABASE_AVATAR_BUCKET = avatars    # 可配，缺省 avatars；控制台里建一个 public bucket
AVATAR_MAX_BYTES       = 1048576    # 单张 1MB（压完实际只有 10~20KB）
```

图片是**公开可读**的（`/object/public/...`）—— 头像本来就要画在每一页顶栏上，
走签名 URL 会让每一页多一次请求、且离线时全是裂图。路径里带 32 位随机 uid，
猜不到别人那一条。**这两项都写进 `.env.example` 与 `npm run doctor` 的清单。**

#### ⑦ 老数据零感知

上一版存的是 `avatar: { char: "梅", ink: "pine" }`。读的时候**只认 `img`**，
于是老用户那枚字印自然回到「昵称首字」（`nickname` 的第一个字）——
`char` / `ink` 不再读、不再写、不再校验（服务端名册白名单同样不认它们）。
老用户打开设置页看到的是「自己的名字首字」，而不是一个他认不出的东西。

#### ① 自选清单上限（本轮）

**为什么先做这一件**：它是能力表里**唯一一条「已宣称、却完全没落」的差异** ——
`/plans/` 上写着「自选清单 20 个（Pro）」，而代码里建几个都不拦，
于是那一行是**假话**。按项目自己的红线（§1 第 3 条「不假装配齐了」），
这一条要么落地、要么从表里删掉；用户要的是前者。

**限制写在数据层，不写在按钮上**：`js/collections.js` 的 `limit()` 是**全站唯一**
回答「能建几个集合」的地方，`create()` 与 `importText()` 都从它取数。
写在设置页里就只能拦按钮、拦不住直接调用 —— 与 `Entitlement.can()` 同一条纪律。

三档的取法：

| tier | 上限 | 依据 |
|---|---|---|
| free | **1 个** | 「免费不残缺」：用户第一次「加入背诵」自动建的那个永远放得下 |
| pro | **20 个** | `CAPS["collections.many"]` 的名字里写着的那个数 |
| max | **不限** | `CAPS["collections.unlimited"]` |

三处细节（都是「不这么写就出别的问题」）：

1. **按 tier 判，不按 `can()` 判**。那两条能力带 `login:true`，走 `can()` 时
   「登录过、但会话刚过期」会被判成 free —— 症状是「昨天能建 20 个，
   今天一刷新只剩 1 个」。这里只是产品分层的**软限**（真边界在服务端），
   按已发放的层级判更稳；门槛值仍取自 `CAPS` 的 `minTier`，不另抄一份。
2. **超限时如实回 `E_LIMIT`，不静默丢**。`importText()` 在满额时返回
   `{ collection:null, added:0, error:"E_LIMIT" }`，设置页据此说
   「自选清单已达上限（Free 1 个 / Pro 20 个 / Max 不限）」，**不**说
   「没认出清单里的篇目」—— 那是另一件事（错因说错 = 让用户白试一遍）。
3. **读不到权益内核时不设限**（返回 `Infinity`，不是按 free 卡 1 个）。
   页面脚本顺序不对 / 老缓存时把内核读成 null，若按 free 卡，症状就是
   「本来能建 20 个的人突然建不了第二个」，且由加载顺序引起、用户无法自查。
   与 `isOwner()` 无存储时的兜底同一条口径：**宁可不判，也不误拦**。

**验证**：`test/collections.test.js` 第九节单开一个 `entitlement + collections`
的 sandbox，逐档断言（free 建第 2 个被拦、Pro 正好 20 个、Max 连建 30 个全过、
拿不到内核时不设限、Pro 的 20 与能力表名字里的数字同源）。

#### ④ 子档案：一个家长，多个孩子各背各的（本轮）

用户 2026-09-17 的四句裁决就是这一件的规格：

> 「(b) 进度也分家：切到小明只看到小明的排期」「Free 档给 1 个昵称」
> 「要跟着分家」「一台设备上多个孩子各背各的」
> 以及稍后的「子档案 Max 180 个，我想象的是老师，负责 3-9 个班级的场景」

**它问的不是「多个昵称随便切」，是「同一台设备上几套各自独立的背诵进度」。**
孩子**不建独立账号**（§2.1：只允许成年人建号），所以一个子档案
= 一个展示名 + 一份**自己的**进度。

**分家的边界只有一条判据：这属不属于「孩子自己的东西」**

| 跟着子档案走 | 不跟 |
|---|---|
| 进度域（`poem_recite_progress_v1`） | 设备域：字号 / 对齐 / 连读档 / 注音开关 |
| 账号域（`poem_recite_settings_v1`：年级 / 学期 / 范围 / 每日数量） | 搜索页上次搜的词 |
| 已读域（六把 `poem_*_read_v1`） | 名册本身（它就是那份数组） |

⚠️ 最容易做错的是**粒度选错**：按「每个孩子一份完整存储」做会连带把设备偏好
也复制两份 —— 症状是「给小红调了字号，切回小明又变回去了」，正好踩中
§3.1 分域那条红线的反面。

**落地方式：改 `ProgressStore` 的读盘入口一处**

所有读盘（进度 / 设置 / 设备 / 搜索词 / 六把已读键）都经 `kk()` 一处换算，
于是「换成哪个孩子的键」只在一处决定。键的映射规则在**新文件 `js/family.js`**
（`keyFor(key, profileId)` 是全站唯一一处回答「这个档案的数据存在哪把键上」的地方）：

```
名册为空 / 没有当前孩子 → poem_recite_progress_v1              （分家前那份数据的家）
有当前孩子            → poem_recite_progress_v1::<childId>
```

⚠️ **「认领出来的第一个孩子」用的就是无后缀的老键，不是为了好看，是为了「零迁移」**：
`Family.ensure()` 认领时若名册为空，第一个档案直接指的就是老用户手上那一份，
所以升级后昵称、进度、年级、已读**全都在原地**，一个字节都不用搬。
代价只是键名规则多一条特例（有断言钉着不许散出去）。若改成「第一个也搬到 `::p1`」，
就得写「搬一半时断电」的恢复逻辑 —— 零迁移就是零风险。

⚠️ **哪些键分家由 `Family.isPerChild()` 一处说了算**，本文件不抄第二份清单：
进度域 / 账号域设置 → 分家；`poem_profile_v1`（名册自己）/ 设备域 / 搜索词 → 不分家；
六把集子已读键 → 分家（读没读过是孩子自己的事）。

**「当前是哪个孩子」放在账号域，不放在设备域**：一台平板上午小明读、
下午小红读，晚上家长拿手机看小明的进度；放在设备域的症状是
「手机上切到小红、平板上还显示小明」。

**上限按已发放层级判**（与 §5.2 ① 同一条口径，不按 `can()` 判 ——
那条能力带 `login:true`，「登录过、但会话刚过期」会被判成 free）：

| tier | 子档案上限 |
|---|---|
| free | **1 个**（「免费不残缺」：第一次自动认领的那一份永远放得下） |
| pro | **3 个** |
| max | **180 个**（老师带 3~9 个班级的场景） |

**四处必须钉住的边界**：

1. **越限如实说是上限**，不说「建不了」（错因说错 = 让用户白试一遍）
2. **新建的档案是空档**，界面明白说出来 —— 不说的话家长会以为孩子的进度丢了
3. **删除时后面的键要跟着前移**。第一个档案的家是无后缀老键，删掉它必须把
   第二个的数据搬过去；不搬的症状**不是报错**，是「删掉老大之后，老二的进度看着空了」
4. **最后一个不许删**（删了就没地方背书了）

**「没做的那一半」已经做了（2026-09-18）**：跨设备的子档案（名册与进度分家上云）
落在 **§5.5**。原来这一段写的是「明说不做」，理由是它要动线上库
（`progress` 主键 `(uid, poem_id)` → `(uid, child_id, poem_id)`）
且那条路线上还排着别的事；用户 2026-09-18 裁「先不做收费/资质，把功能做完」，
排期上再无前置，而 Supabase 项目当时**还是空的**（不是给线上数据搬家），
于是这一件开工并落地。这一段保留，是为了留下「当时为什么不做」的推理链。

### 5.2.1 收掉 `sync.multiDevice` 那道门：一条公开的假话（2026-09-18）

也就是说：**一个 free 用户可以打开设置页那颗开关并真的同步上去**，
而 `/plans/` 上对他宣称的却是「Pro 才有」。这与 2A 那两个洞、2.2 的断链、
③ 的 `export.all` 是**同一个形状** —— 限制写在 A 处（能力表）、读取在别处（没有读取点）。

#### ① 闸拦在两处，缺一处都不行

| 层 | 位置 | 作用 |
|---|---|---|
| **界面层** | `js/sync-store.js` 的 `gate()` → `setEnabled()` | 点开关那一刻如实说「Pro 起可用」 |
| **服务端** | `api/_lib/core.js` 的 `syncTierGate()` → `syncPull` / `syncPush` | **真正的边界**：直接的 HTTP 请求照样打得到，不够就 **403 `E_TIER`** |

为什么两处都要：

- **只有服务端没有界面层** → 用户点开开关、看着「开启中」、实际一条都传不上去，
  而且失败是**静默**的（同步层的 `guard()` 吞掉一切异常，那是 1B 立的第一条边界）
  →「怎么不同步了」根本查不出来
- **只有界面层没有服务端** → 那才是真的没拦（§3.4：藏入口不是安全边界）

#### ② 四条口径，条条有断言钉着

1. **拉与推都要判**，不是只判推。只判推的话，一个 free 用户照样能把云端
   **已有的**那份拉下来（那是别人的进度）。
2. **403 与 401 分开回**：前者是「你确实没这个权限」（去找管理员发层级），
   后者是「你还没登录」（去登录）—— 用户看到的下一步动作完全不同。
   合并成一句「失败」等于什么也没说。
3. **权限闸排在频控之前**：不够层级的人反复重试不该占掉别人的频控额度，
   而且他看到的必须是「你没这个权限」而不是「太频繁了」（后者会让他一直重试）。
4. **关掉永远不过闸**。一个 Pro 用户的层级过期之后，若「关」也被拦住，
   症状就是「同步还在传、用户关不掉」—— 那是最糟的形状，
   而关掉同步只是停上传，不需要任何权限。

#### ③ 「宁可不判，也不误拦」

`gate()` 拿不到权益内核（页面漏加载 `js/entitlement.js` / 老缓存）时**放行**，
不按 free 拦。与 `collections.limit()`、`family` 上限、`isOwner()` 同一条兜底口径：
这一层是**产品分层**，不是安全边界；脚本加载顺序引起的「本来有 Pro 的人
突然同步打不开」是用户无法自查的功能倒退。

#### ④ 三处状态文案跟着多了一档

`SyncStore.status()` 从四种变五种，新增 `"tier"`（开关开着、但层级不够）：

```
unavailable / tier / off / signin / ready
```

`tier` **排在 `off` 之后**：开关没开时不谈层级（没开就是没开，
说「要 Pro」会让人以为开了就能用）。设置页与个人中心各自如实说这一档，
**都不许把它说成「开启中」** —— 开关可能还留在「开」的位置上（层级过期、
或从别处传过来的存储），照抄那一位就是一句假话。

⚠️ 设置页那颗开关**不置灰**：点下去得到一句「Pro 起可用」，
比一个点不动的东西更容易看懂差在哪（与自选清单上限、导出按钮同一条纪律）。

#### 验证

- `bash test/run.sh`：**5824 条断言全绿、0 失败**
- `test/api.test.js` 第九节：free 推/拉都回 **403 `E_TIER`**、
  如实回 `minTier:"pro"`、文案里写明「本机进度不受影响」、
  **403 不说成「还没登录」**；第十二节（真 HTTP）先把账号抬到 pro 再验 Cookie 链路
- `test/sync.test.js` 新增「一之二、层级闸」一节：free 打不开且错因是 `E_TIER`
  （不是「打不开」）、Pro/Max 放行、**Pro 过期后仍然关得掉**、
  拿不到权益内核时不拦
- 一处**测试自身的坑**顺带记下：`SyncStore.use()` 是**整体替换** deps 的，
  只传 `{Entitlement}` 会把 `fetch` / `base` / `signedIn` 一起抹掉 ——
  症状是「闸看起来没生效」，而其实是同步层整体废了。harness 里加了 `setEnt()` 兜住。

### 5.3 全站课内诗词批量导出（③ · 2026-09-16 口径修正）

用户 2026-09-16 在 Issue #159 里把这一条**改了一次**，原话：

> 「为啥要有全站批量导出功能？这不是这个网站的核心资产吗？
>  顶多支持学校课本部分的全部导出。这个 pro 用户就行。」

这不是「补一句说明」，是**能力本身的口径变了**，所以三处一起改：

| | 改之前（§5.2 原计划） | 改之后（本轮） |
|---|---|---|
| 名字 | 全站批量导出 | **全站课内诗词批量导出 261 首** |
| 门槛 | **Max** | **Pro** |
| 内容 | 课内 261 + 六部集子 1592 篇 | **只有课内 261 首** |

**为什么不「留着老名字但内容缩水」**：`CAPS` 的名字与服务端 `featuresFor()`
下发的是**同一张表**（有逐字对拍断言）。名字里写着「全站」而实际只给课内，
那条断言与用户逐条看的 `/plans/` 对比表都会开始说谎 ——
正是 §1 第 3 条「不假装配齐了」要拦的那种假话。

#### ① 「不做整本导出」是一条**产品判断**，不是「还没做」

课内 261 首是**教材篇目**（谁都可以拿一本语文书抄下来）——给到用户手里没有代价。
六部集子是本站**整理并全文收录**的选本，一次性整本导出等于把站点的内容资产拷走。
这两件事在用户眼里完全不同，所以结论也不同：

- 课内 → **给**（`export.all`，Pro 起）
- 集子 → **不给**（**不是**「下一批」，是**不做**）

#### ② 拦在哪一层：范围表，不是按钮

`js/export-core.js` 的 `SCOPES` 是**唯一一处**回答「这份导出包含哪些篇目」的地方：

```js
custom: { name: "自选清单", books: null }              // 用户自己挑的那几篇
poems:  { name: "课内诗词", books: ["poems"] }         // 课内 261 首（本期的全部内容）
```

⚠️ 六部集子**刻意不在表里**。把入口藏起来不是边界（§3.4）——
按钮之外还能从控制台调到 `build()`，所以「能导什么」必须由表决定。
`test/export-core.test.js` 第一节逐个断言那五部**不在范围表里**，
把它们加回来必须先改那条断言与本节。

同一条纪律也落在**门槛**上：`js/settings.js` 在真导之前会再问一次
`Entitlement.can("export.all")`，不够就 `denyReason()` 如实说「Pro 起可用」。
按钮**照旧可见** —— 藏入口不是权限边界。

#### ③ 三条「导出本身别骗人」

1. **按教材册次排**（一年级上 → …… → 高三下，24 组），**不跟着数据文件的出场顺序走**。
   数据顺序是「列表页的顺序」，日后重排数据不该连带改掉用户手里的导出文件。
   同一册之内的次序由语料给，内核不替教材重排（重排就得再维护一份「册内次序」表）。
2. **正文一字不改**：不重排断句、不转标点。这份纸的用处之一正是**拿去抄** ——
   按字数重排好看，但那是改了一次原文。测试里有一条**逐字**判据：
   导出文件里每一行正文都要能在站点索引里一字不差地找到。
3. **没有正文的篇目如实计数**（`build().skipped`），**不写成一条只有题名的空条** ——
   读的人会以为「这篇就是这样」。悄悄少一篇比多导一篇更难发现。

#### ④ 导出的形态：纯文本，不是 PDF

`build()` 只产出**纯文本**（可直接存 `.txt`、可打印、可粘进任何文档）。
界面上写「导出 / 存 PDF」指的是**打印对话框里的「另存为 PDF」**那件事，
不假装点击之后会落一个 PDF 文件（同 §4.18 打印页那条口径）。

**验证**：`test/export-core.test.js`（324 条）—— 范围表里没有那五部、
261 首一篇不少、Pro 起 free 不可、24 个册次顺序正确、
正文逐字可查、空篇目如实计数、未知范围回空不抛、页面不自己拼门槛。

### 5.5 跨设备分档案：云端那一半（2026-09-18 落地）

§5.4 那张表里第 4 条裁的是「**先只做 ①**（一台设备上多个孩子各背各的）」，
②（跨设备）当时**明说不做** —— 理由是它要动线上库，而那条路线上还排着别的事。
这一节记的是 ② 落地的那一轮，连同**当时判断为什么可以现在做**。

#### 一句实话：它要动数据库，而且是一条主线

用户 2026-09-18 裁「我先不做收费/资质那部分，直接把功能做完」，
于是排期上再无前置；数据库本身也**还是空的**（Supabase 项目尚未建），
因此这是一次**同步进行的建库**，而不是「给线上已有数据搬家」。
这一点很重要：它把风险最大的一档（认领老数据 + 搬一半断电的恢复逻辑）
直接消掉了 —— 见下面第 2 条。

#### 一、动的是哪一条主线（三个地方，一处都不能漏）

```
postgres:  progress 表  primary key (uid, poem_id)
                      → primary key (uid, child_id, poem_id)
           kb_upsert_progress()  的 on conflict 跟着换（否则真库上运行时报错）
服务端:    syncPull / syncPush / familyGet / familyPut 带 child
           sanitizePayload 按 poem_id 分岔（名册那一行不是一篇「诗」）
客户端:    js/sync-store.js 的记账表（seen + 游标）按孩子分家
           名册（family:v1）上云，落在**账号那一档**
```

#### 二、`child_id = ''` 的含义：**它就是「第一个孩子那一份」**

这是整件事里最容易做错的一处。库里加列时给 `default ''`，
于是**所有现存行**都落在空串那一档；而 `js/family.js` 的无后缀老键
（`poem_recite_progress_v1`、在 `keyFor` 之前那一份）也正好是同一个含义。
两者**逐字同源**，于是：

- **老客户端**（不认识 `child` 这个字段）请求里不带它 → 落空串那一档，
  行为与分家之前**一字不差**
- **新客户端**永远带上真实的孩子 id → 与空串那一档互不干扰

⚠️ 反过来说：**不许**给老数据认领一个 `::p1` 之类的新 id。
那会让老用户的进度在升级后「看着空了」（数据还在，只是没人再指得到它），
而且要写「搬一半时断电」的恢复逻辑 —— 与 §5.2 ④ 那条「零迁移」是同一条判断。

#### 三、名册也上云，但它**不是一篇诗**

名册（`family:v1`）与进度共用 `progress` 表，理由是不新开表
（与 2.2 的 `game-quota:` 同源：多一张表就多一套 memory / supabase 两个实现
要同步维护，而「两个实现键集合不一致 → 静默失效」是反复踩过的坑）。
但**载荷完全是另一种形状**：

| | 进度那一行 | 名册那一行 |
|---|---|---|
| `poem_id` | 篇目 id | `family:v1` |
| `child_id` | 某个孩子 | **空串**（账号级） |
| `payload` | 背诵档案 | `{v, at, profiles[]}` |
| 白名单 | `sanitizePayload` | **`sanitizeFamily`**（另一份） |

⚠️ 两处不许混：走同一条白名单的下场是名册的 `profiles` 被丢掉、
推上去变成一个 `{}`，另一台设备读到的名册是空的 —— 症状是
「在平板建的孩子，手机上根本看不见」。所以 `sanitizePayload(p, poemId)`
**按 `poem_id` 分岔**，而不是放宽那条白名单（放宽等于让一篇诗的档案能塞任意字段）。

名册的推送**单独一批**（`pushPending()` 里先推它，显式用空串那一档）：
先推它的理由是另一台设备拿到名册才知道「有几个孩子」，
在那之前拉到的任何孩子的进度都不知道该归给谁。

#### 四、客户端：记账表按孩子分家（`seen` 与游标）

`poem_sync_seen_v1` 这把键（每条记录「见过的最后一次云端时间戳」+ 游标）
**必须跟着孩子走**，拼法在 `seenKey()` 一处（`…::<childId>`）。

不分家的症状**极难查**：两个孩子的冲突混在一张表里，于是界面上弹的
「保留本机 / 保留账号」争的是**别人家孩子**的那一条 —— 用户看不懂在问什么，
我们也不会想到去怀疑记账表。

⚠️ 它**不在** `ProgressStore.KEYS` 里（那是同步层自己的簿记，不是六把域键之一），
所以走不了 `Family.keyFor` 的转发，只能在这一层里显式拼一次。
`test/family.test.js` 里那条「拼 `::` 只有一处」的断言因此改成了**白名单**
（`family.js` + `sync-store.js`，多一个文件就红）—— 它防的是「各处各拼一遍」，
不是「一个字都不许拼」。

#### 五、四处刻意钉住的边界

1. **在途切档**：拉请求发出时问的是孩子 A，回来时用户已经切到 B ——
   服务端把这一批判给了谁回在回包里（`r.child`），客户端**逐字比对**，
   对不上就整批丢掉。不这么做的话，A 的进度会被写进 B 的盘上，
   且只在慢网络下偶发。
2. **注销导出所有孩子**：`accountDelete` 逐个档案地取（名册里那个 `profiles[]`
   是唯一知道「这个账号有几个孩子」的地方）。只导当前那个的话，
   注销之后再没有第二次机会，少导出一个就是**永久丢失**。
3. **额度记在账号那一档**：`gameCharge` 的用量行显式写 `child_id = ''` ——
   额度是「这个账号这个月用了几次」的账，不是孩子背了多少首。
   跟着孩子走的话，换个孩子接着刷，额度跟着清零。
4. **`Family.restore()` 是唯一的第二个写入口**：名册是账号域里唯一一份数组，
   谁都能拼的话早晚有人拼出一份缺 `at`、或有两条同 id 的脏名册。
   它自带「空名册不许把本机清空」（`E_EMPTY`）与「`at` 必须落在名册里」两条。
   内核不给这个入口时，同步层**不假装落上了**（不记「已经同步过了」的印）——
   否则那台设备会永远停在一个空名册上，且不报错。

#### 六、`childId()` 的收窄：它不是身份，是一个键

它是客户端生成的随机串（`f-<base36>-<base36>`），服务端**只当它是个键**，
不当任何权限。但因为它会进 URL 与 PostgREST 的查询串，所以：

- 长度 ≤ 64、只允许 `[A-Za-z0-9_-]`、去空白
- 认不出的一律**落回空串**（不报错、也不「替他建一个」）——

### 5.7 D 步探活的两处真 bug（2026-09-17 · 回答 Issue #159）

用户在 Issue #159 报：密钥仓库 `poem-secrets/supabase.yml` 按文档配好了，
但 `supabase-keepalive` 天天红，回 **401**，问「到底该建私有仓库还是密钥仓库，
还是有别的 bug」。回答是：**仓库类型没错（密钥仓库是对的），红是代码里两处
真 bug**，与密钥仓库无关。这一节把两处都记下来。

#### ① 「apikey」填成了 URL —— 401 的直接原因

`.cnb.yml` 的探活脚本原先写的是：

```
-H "apikey: $SUPABASE_URL" \
-H "Authorization: Bearer $SUPABASE_SERVICE_KEY"
```

`apikey` 头要的是**密钥本身**，这里却把 `SUPABASE_URL`（一个 `https://…` 的
地址）当 key 发了出去 —— Supabase 一律回 **401**。

这条的杀伤力不在「探活红」本身，在**它看起来像密钥仓库没配好**：症状是
「密钥明明注入了，探活却天天 401」，于是下一轮排查会反复去查密钥仓库
（新建 / 改名 / 重新注入），而真正要改的只是这一行。

PostgREST 认两个头，同一个 service_role key 两处都要带：

```
-H "apikey: $SUPABASE_SERVICE_KEY" -H "Authorization: Bearer $SUPABASE_SERVICE_KEY"
```

⚠️ 服务端代码里本来就是对的（`api/_lib/store.js` 的 `supabaseStore` 写的是
`apikey: KEY`）—— 错的只有**流水线里那条抄出来的命令**，以及它被
`api/_lib/ops.js` 的 `VERIFY_DB` 抄去的第二份、文档里的第三份。
三处一起改，并由 `test/ops.test.js` 钉住「apikey 后面不是 URL」。

#### ② 备份要的第三个值 `SUPABASE_DB_URL` 没人说怎么来

`supabase-backup` 需要 `SUPABASE_DB_URL`，而这一步原先只有一个变量名：

```
: "${SUPABASE_DB_URL:?SUPABASE_DB_URL 未注入，请检查密钥仓库 supabase.yml}"
```

那个值**不能在控制台直接复制** —— 它只能去 Project Settings → Database →
Connection string 取模板，再把 `[YOUR-PASSWORD]` 整体换成数据库密码
（那串明文只在建项目时出现过一次，忘了就 Reset database password）。
密码里含 `@ : / # ?` 时必须**百分号编码**（`@` → `%40`）：不编码时
`pg_dump` 会把密码里那一段当成主机名，报
`could not translate host name "…@db.<ref>.supabase.co"` —— 看着像 DNS 坏了，
其实只是密码没转义。

这一步现在写进了 `ops.js` 的 D 步（`node scripts/doctor.js --steps` 看得见），
由 `test/ops.test.js` 断言「D 步写了 DB URL / 写了那个占位符 / 指明了去哪取 /
写了百分号编码」。

#### ②之二 那条 `could not translate host name` 就是「密码没转义」（2026-09-17 复查）

**Issue #159 里两条任务一绿一红**，红的那条报的正是：

```
pg_dump: error: could not translate host name "db.twmtmohcaifswxtjowru.supabase.co" to address: No address associated with hostname
```

⚠️ **注意报错里那个主机名是「干净」的** —— 没有 `…@` 前缀、没有密码尾巴，
就是 `db.<ref>.supabase.co`。这说明**密码那一段已经被正确地从 URL 里解析掉了**，
「密码没百分号编码」在**这一例里不是原因**：

- 密码里的 `@` 没编码时，报错长这样：`could not translate host name "…@db.<ref>.supabase.co"`
  （引号里那串**带 `@` 和密码尾巴**）—— 这才是「密码没转义」的指纹；
- 报错里的主机名干净、且确实是 `db.<ref>.supabase.co` 时，URL 已经解析成功，
  失败发生在**解析这个名字**这一步：容器里这个域名**没有可用地址**。

两者只差引号里那几个字符，却指向完全不同的排查方向。所以这一步把**判据**写死，
不再靠「看着像」：

| 报错里引号内的主机名 | 结论 | 下一步 |
|---|---|---|
| 带 `…@` 或密码尾巴 | 密码没百分号编码 | 改密钥仓库里的值（`@` → `%40`） |
| 干净的 `db.<ref>.supabase.co` | URL 已解析，是 DNS 解析不到 | 按下面顺序查 |
| `localhost` / 别的域名 | 值填错了（不是 Supabase 的串） | 回 Connection string 重取模板 |

名字确实解析不到时，**按代价从低到高**查三条（前两条是平台侧的事实，与业务无关）：

1. **新项目有个发布窗口**：刚建的项目 DNS 可能还没发布完（几分钟到几十分钟）。
   先重跑一次这条流水线 —— 失败名单里最省事的一种。
2. **直连主机名 `db.<ref>.supabase.co` 在新项目上只给 IPv6（AAAA）**。Supabase 的
   「Direct connection」在新项目上不再提供 A 记录（IPv4 要另开 IPv4 add-on），
   解析不到地址的表现之一就是 `No address associated with hostname`。
   两个**零成本**的替代串，都在同一页 **Project Settings → Database →
   Connection string** 上：
   - **Session pooler**：`…@aws-0-<region>.pooler.supabase.com:5432`，用户名是
     `postgres.<ref>`（**不是** `postgres`）。给 `pg_dump` 用这个最稳，它走 IPv4。
   - **Transaction pooler**（`:6543`）：**不要**给 `pg_dump` 用 —— 它不支持
     `pg_dump` 需要的会话级特性。
3. 兜底：只要 `SUPABASE_URL` + `SUPABASE_SERVICE_KEY` 是通的（探活那条就是证明），
   导出可以**不依赖 Postgres 直连** —— 用 PostgREST 逐表拉 JSON。数据量小的时候
   够用（`backup/` 的产物从来不进 Git，拉到本地保存即可）。

#### ②之三 备份脚本现在**先自检 URL 形状，再跑 `pg_dump`**

只写文档不够 —— 上面那个「看着像 DNS 坏了」的坑要让**流水线自己**说出来。
`.cnb.yml` 的 `supabase-backup` 在 `pg_dump` 之前加了两条自检：

- 整串必须以 `postgresql://` / `postgres://` 开头（挡掉「只填了个主机名」这种填法）；
- 剥掉 `scheme://user:pass@` 之后，**主机段里不许再出现 `@`**。出现就是密码没编码 ——
  这时直接打印「把密码里的特殊字符百分号编码：`@` → `%40` …」并退出，
  **不再往 `pg_dump` 里送**那句容易被误读成 DNS 故障的报错。

> 这是「症状看起来像 A，其实是 B」那类坑的通用解法：**把 B 在更早的地方判掉**，
> 让报错本身指向真正要改的地方。与探活那条 `apikey` 头同源 ——
> 那次是「看起来像密钥仓库没配好」，这次是「看起来像 DNS 坏了」。

#### ③ 顺带修掉的一个真 bug：桌面首页的顶栏被挤成 369px

查上面两条时把 `bash test/run.sh` 跑了一遍，CI 的 PWA 那一层有 **3 条红**：

```
✗ {"顶栏":[56,425],"正文":[0,1920]}      桌面 1920px：顶栏与正文列左右同缘
✗ {"顶栏":[56,425],"正文":[0,1440]}      桌面 1440px：顶栏与正文列左右同缘
✗ {"顶栏":[56,425],"正文":[0,1280]}      桌面 1280px：顶栏与正文列左右同缘
```

顶栏宽 **369px**、停在页面正中偏左那一小截。两个原因叠在一起：

1. **`.topbar` 没认领 grid 那一行**。桌面那一档首页的 `.app` 是
   `grid-template-columns: minmax(0, 340px) minmax(0, 1fr)`，而 `.topbar`
   是 `.app` 的**第一个子元素** —— 不认领格子就会被自动放置塞进**第一列**
   （340px）里。CSS 里那句「顶栏与页脚各自是「一整行」」只是一句**声明**，
   没有任何规则实现它。
2. **`.topbar` 只写了 `max-width`、没写 `width: 100%`**。块级盒子只给
   `max-width` 时仍是「收缩到内容宽」的，那个 `max-width` 只是天花板。
   手机 / 平板那两档看不出来（`.app` 内容盒宽 692 / 724px，与顶栏的
   `max-width` 同值，收缩出来的结果碰巧与 100% 相等）；桌面那一档
   `.app` 变成 `100vw`（1808px 的内容盒）之后两者就分叉了。

改法与 `.dock-inner` 同一条写法：`width: 100%` 负责撑满那一格、
`max-width: var(--content-w)` 负责不许比内容区更宽、`margin: 0 auto` 居中；
再加上 `body[data-nav="home"] .topbar { grid-area: bar; }`。

### 5.9 `supabase-backup` 一直红：pg_dump 比服务端低一个大版本（2026-09-17 · 回答 Issue #159）

用户贴的失败日志（`supabase-backup`，定时任务 `crontab: 30 4 * * 1`）：

```
pg_dump: error: aborting because of server version mismatch
pg_dump: detail: server version: 17.6; pg_dump version: 16.15 (Debian 16.15-1.pgdg13+2)
Finished, code: 1
```

#### ① 这条**不是**上一条的复发

上一节（§5.7 ②之二）修的是「密码没百分号编码 → `could not translate host name`」。
这一条报的是**版本**，而且 `aborting` 这个词是关键：

- 那两句「版本不匹配」的**提示式**措辞是错的。原先把 `server version mismatch`
  写成「**警告**，不是备份失败，下一轮别当成新 bug 去查」—— 事实相反：
  **pg_dump 比服务端低大版本时是直接 abort**，一条数据都不导，退出码 1。
  写下「别当成 bug」那句，恰好会让下一轮的人放过一条真红。已在 §4.12 与
  `api/_lib/ops.js` 的 D 步里改成「低 = 直接 abort，不是警告」。
- 规则本身：**pg_dump 允许比服务端新，不允许旧**（新客户端读得懂老服务端的目录；
  老客户端读不懂新服务端的目录）。所以镜像跟着**服务端**大版本走。

#### ② 为什么之前选了 `postgres:16`，以及它为什么必然红

`node:20` 镜像里**没有** `pg_dump`（脚本里那句 `command -v pg_dump` 就是为此加的），
于是当初换成了 `postgres:16` —— 这解决了「工具不存在」，但没解决「工具的版本」。
Supabase 服务端是 **17.6**，`postgres:16` 里的 `pg_dump` 是 **16.15**，于是每次
都 abort。**备份从上线起就没成功过一次**，而红的原因看起来像「密钥 / 网络」那一类。

`0.7s` 的 duration 也是个指纹：真要连库导数据不可能这么快 ——
它在**连接之前**就退了。

#### ③ 改法：镜像换 `postgres:17` + 把两条「不许发生的事」变成脚本里的门

1. `docker.image: postgres:16` → **`postgres:17`**（跟着服务端大版本；
   服务端升 18 时同步换）。pg_dump 是**客户端**工具，不需要与服务端同发行版 ——
   镜像只是取工具的地方，工具够新就行。
2. 开跑先 `pg_dump --version` 打出版本：这一行让「镜像对不对」在日志里可见，
   不用等那句 abort 去猜。
3. **0 字节不算备份**。原先 `> backup/kuibu-$STAMP.sql` 一重定向，文件就
   已经存在了 —— abort 之后留下一个 **0 字节的 `.sql`**，「备份存在但只有 0 字节」
   比彻底没有更危险（人会以为那天备份过了）。现在失败时 `rm -f` 掉半截文件，
   成功后用 `test "$SIZE" -gt 0` 把门。

  「镜像就是 `postgres:17`」「不再是 `postgres:16`」「先打 `pg_dump --version`」
  「空文件退非 0」「失败删半截文件」
- `bash test/run.sh` 全绿、0 失败（PWA 那一层需能起 Chrome 的镜像）

### 5.10 「邮件送不到真人收件箱」到底要改哪里（2026-09-17 · 回答 Issue #197）

用户在 Issue #197 里问的是一个**运维问题**，不是代码问题：

> 「发信商还没配好（走的是 console 通道，只往服务端日志写一行）……什么意思，
> 我需要在哪里设置？我在 resend.com 配置了 resend，你是说我还需要到
> vercel 配置还是 supabase 配置？」

这一节记的是「这个问题该怎么被回答」，以及为此在仓库里落下的两块。

#### ① 三层不是一回事（这才是问题的根）

| 层 | 在哪 | 管什么 | **不管**什么 |
|---|---|---|---|
| 发信商 | Resend 后台 | 这一家**允许**你用它的服务发信（key + 验域名） | 本站的服务端根本不知道有这枚 key |
| 数据库 | Supabase 后台 | 账号与进度**存哪** | 与发信无关（Supabase 自己的邮件是它自己的验证信） |
| **托管平台环境变量** | **Vercel → 项目 → Settings → Environment Variables** | 把 key **交给本站的服务端** | — |

**本站的服务端 = 同一个 Vercel 项目里的 `api/*`**（§4.1 那张表写着账号已经是
✅ 已配 —— 说的是**数据库那两个变量**，与发信那一个不是一码事）。
于是「我在 Resend 配好了」的下一句应当是「这枚 key 插到了哪台机器上」，
答案就是 Vercel 那个项目的环境变量。

**不选 Supabase 的理由**也是这一条：Supabase 的 Environment Variables 只在
它自己的 Edge Functions / Auth 里生效，而我们的 `api/*` 跑在 Vercel 上，
读的是 `process.env`（`api/_lib/config.js`）—— 填在 Supabase 里没人读。

#### ② 代码侧落下的两块（都在**用户能看见**的地方）

这一步是**运维**做的，但「没做」这件事必须在用户面前**说得出来、且指向哪去做**。
Issue #197 之前只说「发信商还没配好」，用户唯一的线索是「resend 和 vercel 到底哪个」。

- **`js/login.js` 新增 `mailNotConfiguredNote()`**：这一句话原先在**三处各写各的**
  （注册完 / 重发确认邮件 / 忘记密码）。现在**只定义一处**，三处引用，
  并在里面**点名去哪儿配**（`npm run doctor -- --steps` 的第 C 步）。
  ⚠️ 一句话在三处漂移，用户就会看到三种解释 —— 这正是他会来问「到底哪个是真的」的原因。
- **`POST /api/reset-request` 的响应多一个 `mailConfigured`**：
  忘记密码那一屏原先**赌上了「发信商配好了」**——它回「重设链接已经发出去了」，
  而在 console 通道下那句话对**所有人**都是空的，用户等一封永远不来的信。
  ⚠️ 这个字段**不泄露「这个邮箱注册过没有」**：它说的是**这台服务器**的属性，
  与请求里那个邮箱无关，所以对**不存在的邮箱也必须带上它、且取值一样** ——
  否则「带这个字段 = 注册过」就成了新的枚举口（`test/api.test.js` 有断言把
  两侧的**键集合**与取值都钉住）。
  它与 `register` 的 `verifySent` 是**同一条纪律**（§4.6 第 1 条）：能不能发信
  是环境的事，与发的是哪一封邮件无关。

#### ③ 文档侧：一张表把三层分清，并写死步骤顺序

`README.md` 的「开通自检与配置清单」下多了一小节 **「发信商到底在哪配」**，

「重新部署」那一步单独拎出来说，因为它是「我明明配了」里最常见的一种：
**Vercel 的环境变量只在新部署里生效**。
