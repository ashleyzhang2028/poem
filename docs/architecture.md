## 0. 一句话结论

**用 Supabase，免费版不休眠，但它只当「账号目录」和「跨设备进度库」；
发信不走 Supabase，走自己的 `/api` 云函数（主 SendGrid、备 Resend）；
前端不上 Next.js，继续静态站；后端不超过 6 个 Serverless 函数。**

```
浏览器（静态 PWA，Vercel 托管，kuibu.app）
  │  js/auth-core.js            ← 已有，纯逻辑，零 DOM
  │  js/sync-store.js           ← 新增，ProgressStore 的远端实现
  ▼
api（同一个 Vercel 项目里的 /api/*，6 个函数）
  ├─ /api/send-code      → SendGrid 主 / Resend 备（不花钱）
  ├─ /api/verify-code    → 校验 → 签发会话（HttpOnly Cookie）
  ├─ /api/me             → {uid, plan, features[]}   ← Pro/Max 唯一合法挂载点
  ├─ /api/sync/pull      → 拉服务端进度（增量）
  ├─ /api/sync/push      → 推本机进度（增量、按条覆盖）
  └─ /api/account        → DELETE 注销（含数据导出）
  ▼
Supabase（免费版，Postgres + 一张 accounts 表 + 一张 progress 表）
  └─ 由 GitHub Actions 定时唤醒（见 §1）
```

**三条不可退让的边界（沿用 `docs/auth-design.md` §1）：**
1. **不注册也能用全部功能** —— 登录只增加「数据不丢 + 跨设备」，不拿任何现有功能当人质
2. **打开即用、可离线** —— 首屏不许因为有了后端而变慢；断网照常背
3. **不假装配齐了** —— 代码实现到哪一步，`/privacy/` 与 `/terms/` 就如实写到哪一步

## 1. supabase 免费版不休眠：可行，但必须认清代价

### 1.1 为什么它会休眠（官方口径）

Supabase 免费档（Free plan）的官方规则：

| 项 | 免费档 |
|---|---|
| 活跃项目数 | 2 个 |
| 数据库 | 500 MB |
| 月活用户（MAU） | 50,000 |
| 出口流量 | 5 GB / 月 |
| **空闲暂停** | **项目连续 7 天没有任何请求 → 自动暂停（paused）** |
| 唤醒方式 | 到控制台手工点，或发一个能打到数据库的请求让它自动恢复 |

暂停不是「睡一会儿」，是**整个项目停机**：数据库不可连、Auth 不可用、
REST API 全部返回错误。对用户的表现是「打不开了」，而不是「有点慢」。

> ⚠️ 这条是本方案里**唯一一个会直接砸在用户身上**的平台限制。
> 用户背了一个月，第 8 天打开发现进度拉不下来 —— 这是产品级事故，必须在架构里消掉。

### 1.2 让它不休眠的四种办法（按推荐度排序）

#### 办法 A：GitHub Actions 定时探活（**推荐，零成本，唯一真解**）

原理：暂停的判定是「7 天内没有任何请求」。那么**每 5 天发一个真请求**即可。

本项目现成的条件：代码已经在 GitHub（`ashleyzhang2028/poem`），
`.github/workflows/` 加一个 cron 就完事，**不引入任何新服务、不需要服务器**。

```yaml
# .github/workflows/keepalive.yml
name: supabase-keepalive
on:
  schedule:
    - cron: '0 3 */5 * *'      # 每 5 天一次，留 2 天缓冲
  workflow_dispatch:           # 也留一个手动按钮
jobs:
  ping:
    runs-on: ubuntu-latest
    steps:
      - name: ping supabase
        run: |
          curl -sS -o /dev/null -w '%{http_code}\n' \
            "${{ secrets.SUPABASE_URL }}/rest/v1/accounts?select=uid&limit=1" \
            -H "apikey: ${{ secrets.SUPABASE_ANON_KEY }}" \
            -H "Authorization: Bearer ${{ secrets.SUPABASE_SERVICE_KEY }}"
```

**四个必须做对的地方，否则探活本身会失效：**

1. **必须打到数据库**，不能只 ping 域名或健康检查页 —— Supabase 的状态页
   与根路径不触发数据库活动，只有 PostgREST / Auth 的真实查询算「活动」。
2. **必须每 5 天，不能每 7 天** —— GitHub 的 `schedule` 在高负载时可能延迟数小时，
   偶尔会跳过（官方文档明确：「可能延迟、在高负载时可能被丢弃」）。
   每 5 天一次，即使偶尔跳过一次也仍在 7 天窗口内。
3. **GitHub Actions 对 60 天无提交的仓库会停掉定时任务** —— 本项目天天在改，不成问题；
   但要在 workflow 里留 `workflow_dispatch` 手动口，万一停了能一键补上。
4. **探活失败必须能被发现** —— curl 的非 2xx 要让它红，否则「探活挂了 3 个月」
   会以「某天用户突然登不上」的形式暴露出来。上面的 `-w '%{http_code}\n'`
   配合 `-f` 或后续断言即可。

**这条办法的真实成本：** 每 5 天一次请求，一个月 6 次。
免费档流量 5 GB/月，这个量级可以忽略。

#### 办法 B：把邀请来的「每日真实访问」当探活（**不推荐作为唯一手段**）

有真实用户访问就是真请求，理论上不需要额外探活。**但不能靠它**：
- 跬步现在「打开即用、未登录不用后端」，绝大多数访问**根本不碰 supabase**
- 一旦连续 7 天没人发起登录/同步请求（比如一个寒假），项目就暂停，
  而**第一个想登录的用户恰好撞上暂停**——最坏的时机

所以 B 只能当 A 的补充，不能替代 A。

#### 办法 C：UptimeRobot / cron-job.org 之类的免费监控（**备选**）

可以，但它是**多一个第三方**：多一个能访问你数据库的账号、多一条要写进隐私条款的
数据处理者。既然 GitHub Actions 已经现成，没有理由再引一个。

#### 办法 D：升级 Pro（$25/月）（**现阶段不做**）

这是唯一「官方保证不休眠」的办法，也是唯一能拿到：
- 不暂停的 SLA
- 每日自动备份 + 7 天 PITR
- 可自选区域

**判断：现阶段不做。** 理由不是钱，是**顺序错了** ——
一个还没有一个付费用户的产品，先付每月 175 元保「后端不睡」，
而它的核心问题（没有主体资质、收不了钱）一点没解决。
探活方案在工程上等价，只在「忽然被 DDoS / 数据库爆掉」这类场景有差别，
而那时你早就该升级了。

### 1.3 但请记住：探活只是「可用性兜底」，不是「可靠性方案」

即使不休眠，免费档还有几条**探活解决不了**的限制：

| 限制 | 影响 | 应对 |
|---|---|---|
| **没有自动备份**（免费档无 PITR） | 误删数据 = 数据永久消失 | 每周一次 `pg_dump`（同样用 GitHub Actions）导出到仓库 artifact |
| 数据固定在美国 / 新加坡等共享区域，**不能自选** | 机房位置不可控 | 与合规无关（本站不以「国内项目」为前提，见 §4.2）；只按「最小化上传」设计 |
| 出口流量 5 GB/月 | 大文件不能走它 | 进度数据是 KB 级，不会触到 |
| 无 99.9% SLA | 平台故障只能等 | **进度数据必须本机也是完整副本**（见 §3.2 的「本机优先」） |

**最后这条最重要，它决定了整个同步架构的形状：**
> **supabase 里的进度永远不是唯一副本。本机 localStorage 始终是完整、可用的那一份。**
> 后端挂了、暂停了、欠费了，用户照样能背，只是不同步而已。

### 2.2 为什么后端只有 6 个函数，而不是一个「正常后端」

因为这个应用的后端需求**真的只有这么多**：

| 需求 | 函数 | 为什么不能更少 |
|---|---|---|
| 发验证码 | `send-code` | 只有它需要密钥、需要频控、需要真的发信 |
| 验证码换会话 | `verify-code` | 只有它能签会话，明文码不许出现在客户端 |
| 知道自己是谁 | `me` | 权益的唯一来源；客户端不得参与判定 |
| 拉进度 | `sync/pull` | 换设备恢复 |
| 推进度 | `sync/push` | 多设备一致 |
| 注销 | `account` | 合规硬要求（个保法删除权） |

**不需要的东西，明确列出，免得以后有人「顺手加」：**
- ❌ 不需要 GraphQL / ORM（6 个函数、4 张表，SQL 直接写更清楚）
- ❌ 不需要 Redis / 队列（频控用 `codes` 表的时间窗查询足够）
- ❌ 不需要微服务 / 容器（Serverless 冷启动对这 6 个函数的调用频率完全够用）
- ❌ 不需要 CDN 之外的缓存层（静态资源已经在 Vercel 边缘）

### 2.3 前端为什么**不**上 Next.js

这是本轮最该说清的一条，因为它是你最初的问题之一。

**Next.js 能带来的东西，这个项目一个都不需要：**

| Next.js 的能力 | 跬步需要吗 | 为什么 |
|---|---|---|
| SSR / ISR（服务端渲染） | ❌ | 内容全在客户端、本地生成，**没有任何一页的内容依赖服务端** |
| 路由框架 | ❌ | 13 个静态页面已经跑通，URL 约定（目录化、无 `.html`）是刻意的 |
| API Routes | ⚠️ 部分需要 | 但 Vercel 的 `/api/*` **原生就支持**，不需要 Next.js |
| React 组件化 | ❌ | 现在 25 个模块全是 IIFE + `window`，逻辑层 0 行 DOM（见下） |
| 图片优化 / 字体优化 | ❌ | 字体已**手工子集化**自托管（11 MB，比 Next.js 的自动优化更可控） |
| 打包器 / tree-shaking | ⚠️ 想要 | 但可以用 **不带框架的 Vite/Rollup 单独解决**，成本远低于上 Next.js |

**上 Next.js 的代价（真实存在，不是理论风险）：**

1. **26 个测试文件、12730 行测试几乎全部返工** —— 它们是 jsdom（加载真实 HTML）+
   源码扫描 + puppeteer。改成 React 后 HTML 是运行时生成的，
   「页面加载 js/storage.js」这类断言的对象不复存在
2. **`sw.js` 的缓存策略要重做** —— 现在是「静态资源缓存优先 + 导航在线优先」，
   写得很清楚（`README.md` 的 Service Worker 约定）。Next.js 的资源指纹变了，
   那套约定要重新推一遍
3. **首屏会变慢** —— 现在是「一个 HTML + 4 个字体 + 按需数据」，秒开。
   Next.js 客户端组件 + hydration 至少要加一个 runtime chunk，
   而**离线优先是跬步最硬的产品特性**，不能拿它换架构先进性
4. **PWA 离线承诺要重新验证** —— app shell 预缓存的清单会变（`PRECACHE` 现在是手写的，
   这恰恰是它的优点：改了什么、缓存什么，一眼看得见）

**判断：不迁移。** 如果你想要打包器，正确做法是
**只把 `js/` 那 25 个模块换成 ES modules + Rollup，页面保持静态 HTML 不动** ——
这是 0 期顺带能做的事（见 §3.1），成本约 2 人日，收益是 tree-shaking + 依赖显式化，
且**不需要动任何一页 HTML 的结构**。

### 2.4 账号与权益

| 项 | 决定 |
|---|---|
| 主键 | `uid`（`u_` + 8 位，永不复用，注销也不回收） |
| 登录标识 | `email_hash`（SHA-256 + 服务端 pepper），**不存明文邮箱** |
| 登录方式 | 邮箱随机码（6 位 / 10 分钟 / 单次） |
| 会话 | **HttpOnly + Secure + SameSite=Lax 的签名 Cookie**，30 天 |
| 权益来源 | **只有 `/api/me`**，客户端一切 `plan` 字段都是显示用的缓存 |
| 短信 | 只留口子（`channel` 枚举已就位），不实现 |
| 儿童 | 只允许成年人建号，孩子只是展示昵称；不做家庭子档案（1 期不做） |

> ⚠️ **这一条与 `docs/auth-design.md` §3.4 有冲突，以本文为准**：
> 原文档写「本期不做服务端鉴权」，现在 1 期就有服务端了，
> 因此**权益判定必须在服务端**。原文档那句「不作为付费/权益凭据」
> 适用范围收窄为「0 期（纯本机）」。

### 2.5 发信通道

| | **SendGrid** | **Resend** |
|---|---|---|
| 免费档 | 100 封/天（永久免费档） | 100 封/天、3000 封/月 |
| 国内到达率 | 较好（多年的 IP 信誉积累） | 普遍较差，易进垃圾箱 |
| 数据落地 | 可选 | **账号数据固定在美国**（官方明确） |
| SDK 体验 | 老派但稳 | 更现代 |

**决定（你已接受）：主 SendGrid，备 Resend。**
两者写在同一个 `transport` 接口后面，加起来不到 200 行，
通过环境变量 `MAIL_TRANSPORT=sendgrid|resend` 切换 ——
**换发信商不用改任何业务代码**，这正是 `docs/auth-design.md` §11 那句「只换 transport」的意思。

**发信必须做对的三件事（不做就等于没发）：**
1. **域名要配 SPF + DKIM + DMARC** —— 只验证域名不够，缺这三条会被 QQ/163 拒收
2. **发件人用子域**（如 `noreply@mail.kuibu.app`）—— 隔离信誉，
   万一被标记不影响主域的其他用途
3. **响应里永远不透露「这个邮箱是否存在」** ——
   无论新老用户都回同一句「若该邮箱可用，验证码已发送」，
   否则接口就成了「这个邮箱有没有注册过」的查询工具

## 3. 0 期：ProgressStore 分域（前端重构，零后端）

> **目标：让「哪些数据跨设备一致、哪些是设备本地」变成一个可枚举的清单。**
> 这一期的产出是**那张分类表**，不是那层接口。它本身不给用户任何新功能。

> ✅ **状态：0 期已落地（2026-09-15）**。
> `js/progress-store.js`（348 行，含中文注释；逻辑约 190 行）+
> `js/storage.js` 改成薄转发层 + `js/reader-core.js` / `js/settings.js` / `js/app.js`
> 三处改走设备域。新增 `test/progress-store.test.js`（130 条断言，排在 `test/run.sh`
> 第 0 层）。全量 32 层测试零回归。`sw.js` 缓存版本提 `v118 → v119`。
> 落地过程中的**三处与原设计的偏差**记在 §3.4，都是实测顶出来的，不是拍脑袋改的。

### 3.1 做什么

**① 抽出 `js/progress-store.js`（预计 < 200 行）**

`js/storage.js` **保留**为薄转发层：`Storage.get / getSettings / saveSettings /
exportJSON / importJSON` 一个签名都不改，实现转调 `ProgressStore`。
这样 `app.js` / `scheduler.js` / `progress.js` / `settings.js` 里那 500 行调用点
一处不动，改动面被压在引擎层。

接口见 `docs/auth-design.md` 引述的阶段 0 设计（Issue #132 上一条评论有全文）：
`get/set/setMany/all/remove/pruneUnknown/replaceAll` + 已读域 + 设置域
（`settings()/patch()/reset()`）+ `migrate()/profile()/cache()` + `exportJSON/importJSON` + `on()`。

**② 按字段拆家（这是本期真正的价值）**

用户已于 2026-09-15 裁决（`docs/auth-design.md` §12.2）：

| 归属 | 字段 | 落到哪个键 |
|---|---|---|

### 3.4 落地时顶出来的三件事（与原设计不同，都是实测的结果）

**① `helper` 必须**双写**，不能只写新键。**
设计里写的是「`helper` 搬到 `poem_device_prefs_v1`」。真做起来发现：六部集子页与
设置页**至今仍从 `poem_recite_settings_v1` 读它**（`reader-core.js` 的 `helperOn()`），
只写新键就会出现「首页说已开启、集子页是纯文本」——一份数据、两处说法。
现在的口径是：**新键是正主、老键里那份是镜像，写的时候两把一起写**
（`saveSettings` 与 `setHelper` 都双写），读的时候新键优先。
集子页那段的读写也已改走 `ProgressStore.helper()` / `setHelper()`，与引擎同源。

**② 导出备份里**必须**补上 `helper`。**
老版本导入备份时只认 `settings.helper`，导出时若把它从 `settings` 里摘掉，
用户在另一台设备上导入后会发现「阅读辅助变回默认」。
所以导出是**宽进严出**：导出时按位补齐（`settings` 里带一份 `helper`），
导入时按域过滤（`settings.helper` 与 `device.helper` 都收，写回设备域）。

**③ 引擎必须只认 `pick()` 出来的默认值，**不许**从旧盘上「继承」它自己写下的默认值。**
`saveSettings` 会把 `helper` 的镜像写进老键（见 ①），于是**旧键里一定有它** ——
如果 `helper()` 的回落顺序是「新键 → 老键 → 默认」，那么「老键里那份默认值」
就会被读成「用户选择」，而新键一旦有值就以新键为准……这条读法本身没错，
但 `settings()` 返回的对象里**不能再带 `helper`**：它属设备域，两处都返回就等于
又回到「一份数据两处说法」。现在 `settings()` 只返回账号域白名单 + `username`。

**顺带修掉的一个真 bug（不是设计里的）：** `js/app.js` 启动时
`settings = Storage.getSettings()` 拿到的对象里已经没有 `helper` 了，
`helperEnabled()` 于是判成「开着」——**在关掉了阅读辅助的机器上照样注音，
而设置页显示的是「关闭」**。现在启动与 `PoemApp.reloadSettings()` 之后都调一次
`adoptHelperFromDevice()`，从设备域现读一次写进本地快照。
这条被 `test/auto-read.test.js` 的「阅读辅助关闭 → 打开诗词是纯文本」当场抓住 ——
那一条在改之前是**绿的**，改完变红，说明它真的守着这件事。

### 4.2 数据上云：1 期的唯一实质合规风险（2026-09-15 重裁）

> **用户裁决（Issue #132，2026-09-15）**：「我没说这是一个国内的项目啊，为什么总是说要出境？
> 选择方案 B，不需要出境同意流程及界面。」

**先说清一件事：这不是一个「国内项目」。** 本站部署在 Vercel、语料库自带、
不接任何国内云也不接任何国内 CDN；「国内用户为主」是一个**受众事实**，
不是一条**架构约束**。前几轮把 Supabase 的共享区域一律读成「个人信息出境」，
是在给一个不存在的约束做设计 —— 于是凭空长出了「出境单独同意」勾选框、
「出境同意」流程与被误伤的方案取舍。**这套措辞本节整体删除。**

**但风险本身没消失，只是换了名字。** 真正要处理的是这件事：

- 1 期之前（含 0 期）数据只在本机，`/privacy/` 的「不上传、不云同步」成立
- 1 期一旦把账号与进度送上服务端，就**产生了数据上传**：从「无服务器」变成
  「有数据处理者」，`/privacy/` 必须如实改口，用户必须知情、可关、可删、可带走
- 跬步面向儿童，这是**最敏感的一类**用户 —— 口径要比一般产品更谨慎

**这不是出境问题，是「要不要上传」的问题。** 处理动作与服务器在哪个机房无关，
所以**不做「出境同意」这个独立流程，也不为它建任何界面**。

#### 裁定：**方案 B（进度上云）+ 据实告知，不做出境同意**

用户已选 **B：连进度一起上云**（换设备自动同步，这才是登录真正的价值）。

配足的动作收敛为**三件据实做**的事（都不叫「出境同意」）：

| # | 做什么 | 为什么还要做 |
|---|---|---|
| 1 | **注册/首次登录时据实告知**：说清「进度会保存到服务器以便跨设备同步」，用户点「继续」即视为同意 | 上传就要求知情同意，与机房位置无关；**不做单独勾选框、不做第二张页** |
| 2 | 设置页有「**不使用云端同步**」开关（**默认本地**） | 用户有权拒绝上传；关掉即完全退回 0 期行为 |
| 3 | 「**注销即删除 + 数据导出**」自助可用 | 删除权与可携带权是基本要求，也是 B 方案自己的技术前置 |

**明确不做的**：

- ⛔ 注册页的「个人信息出境单独同意」勾选框（**删掉**，不建）
- ⛔ 任何名为「出境」「跨境」「数据跨境传输」的界面、文案、开关
- ⛔ 为「选择机房 / 区域」而做的设置项（免费档本来也不能自选区域）

| 数据 | 存哪 | 说明 |
|---|---|---|
| `email_hash` + `plan` + `uid` | Supabase | 账号存在的前提；**只有摘要，还原不出邮箱** |
| 会话 Cookie | 浏览器 | 不上云 |
| **学习进度（背诵记录）** | Supabase | ✅ 已裁：**上云**（方案 B），可被开关关闭 |

**`/privacy/` 与 `/terms/` 的改法**：把「不上传、不云同步」如实改成
「默认只存本机；开启云端同步后会上传到服务器，可随时关闭、注销即删除」，
**不提「出境」二字**。这一改动与 1 期代码同批落地（条款跟随代码）。

> 「最小化」的原则不变：账号只存摘要、进度是 KB 级、本机始终保留完整副本
> （见 §1.3 那条「supabase 里的进度永远不是唯一副本」）。

### 4.3 接口契约（6 个函数，定死）

```
POST /api/send-code
  req  { channel:"email"|"sms", value, purpose:"login"|"reset", deviceId }
       （兼容 1A 的 { email } 调用点：channel 缺省即 "email"）
  res  202 { codeId, expiresAt, cooldown, transport, delivered, channel, store }
       400 { code:"E_EMAIL_FORMAT|E_PHONE_FORMAT|E_CHANNEL" }
       429 { code:"E_RATE_*", retryAfter }
       503 { code:"E_NOT_CONFIGURED|E_SMS_NOT_OPEN" }
  ⚠️ 无论账号是否存在，响应完全一致（防用户枚举）
  ⚠️ channel:"sms" 走**同一套**状态机，只是归一化 / 频控档 / 投递不同；
     短信未开通时如实回 503 E_SMS_NOT_OPEN，**不假装发送**（docs/auth-design.md §8.2）

POST /api/verify-code
  req  { codeId, code, deviceId }
  res  200 { account:{uid,nickname,plan,features[]} }  + Set-Cookie: kbsid=...
       400 { code:"E_CODE_WRONG|E_CODE_EXPIRED|E_CODE_USED|E_CODE_VOID", remaining }
       423 { code:"E_LOCKED", retryAfter }

GET  /api/me
  res  200 { uid, nickname, plan:{tier,until}, features:[] }
       401 { code:"E_NO_SESSION" }

POST /api/sync/pull        （方案 B）
  req  { since }   res 200 { recs:[{id,payload,updatedAt}], serverTime }

POST /api/sync/push        （方案 B）
  req  { recs:[{id,payload,updatedAt}] }   res 200 { applied, conflicts[] }

DELETE /api/account
  req  { confirm:true, deviceId }
  res  200 { deleted:true, export:{...} }   ← 数据随响应回（本期无对象存储，不给下载链接）
```

**服务端必须守住的三条（review checklist）：**
1. **明文验证码不进任何日志**（含错误上报、监控、`console.log`）
2. **权益只从 `/api/me` 来** —— 客户端传上来的任何 `plan` 字段一律忽略
3. **所有写接口都要频控** —— 不只 `send-code`；`sync/push` 也要有配额，
   否则一个坏客户端能把你的免费档流量刷爆

### 4.4 同步的合并规则（沿用 `docs/auth-design.md` §9）

- 本机有 / 账号空 → **认领本机进度**（新注册不丢数据）
- 本机空 / 账号有 → 拉账号数据
- 两边都有同一篇 → 取「`reps` 多 / `nextReviewAt` 晚」的一方（**打卡必须单调**）
- 两边都有但无法判断来源 → **不自动合并**，弹「保留本机 / 保留账号 / 先导出再决定」
- 弹窗前必须显示两边「篇数 / 截至时间」；「保留账号」前**先静默落一份本机快照**
- **只读页面绝不触发弹窗，也不写盘**

### 4.7 1A 落地时顶出来的六件事（与原设计不同，都是实测的结果）

**① 「重新发送冷却」不是频控的一档，必须单独判。**
设计里把 60 秒冷却写在 `RATE.email` 的窗口里。真做起来发现两者是不同的东西：
频控是「一段时间内最多几次」，冷却是「两次之间至少隔多久」。
混在一起写，`[[3600000, 5]]` 的第一个窗口会**直接放过**连点两次的行为，
而文档 §4.6 第 4 条明确要求「60 秒内只发一封」。
现在冷却由 `limiter.cooldown()` 单独判，测试里有一条专钉它。

**② 错误码的判定顺序会影响用户看到的话。**
「错满 5 次」时我们顺手把码记录也标成「已消费」（等于作废）。若先判 `consumed_at`，
用户会看到「这个验证码已经用过了」—— 而他一次都没对。
现在 `attempts` 先判、`consumed_at` 后判，与前端内核 `js/auth-core.js` **逐条同序**。
（服务端与前端各有一套实现，顺序不一致就会出现「同一个码两种说法」。）

**③ 后端挂掉时的降级分两层，1A 只落了第一层。**
- **第一层（1A 已落）**：接口**不 500** —— 没配库时降级 `memoryStore`；
  没配 `SESSION_SECRET` 时回 **503 `E_NOT_CONFIGURED`**（而不是 500），
  传输层把它翻译成「本站还没开放云端账号，当前是本机体验版」并标记降级。
- **第二层（1B 已补）**：「同步失败不打断背诵」的端到端验证。
  1A 当时还没有同步层，写一条「同步挂了照样背」的测试等于测一个空对象 ——
  那种断言永远绿、什么都不验，比不写更糟，所以当时如实标注为 1B 的活。
  **1B 补上了**：`test/sync.test.js` 第十节用十种坏情况逐条验（见 §4.6 第 8 条）。

**④ 明文验证码这条纪律，最先破的位置是「本地开发的日志」。**
`console` 通道本来顺手把码打到日志里（本地调试方便）。但那违反 §4.3 第 1 条，
而且**破了之后生产也会照打** —— 同一条 log 语句，没有人会记得在部署前删掉。
现在 console 通道只记「本该发往 a***@b.com」，并明确提示「要看码请开 `ALLOW_CODE_ECHO=1`」。
测试里有一条断言直接把 `console.log` 抓下来，扫其中有没有 6 位数字串。

**⑤ `sw.js` 里一个注释都不许有，于是「为什么」只能写在测试那边。**
用户明确要求 `sw.js` 去掉全部注释并禁止再加（`test/theme.test.js` 有硬断言守着）。
`/api/*` 那条早退的**理由**因此写进了 `test/api.test.js` 的注释里 ——
这条看起来是「文档放错了地方」，其实是唯一能同时满足两条约束的位置。

**⑥ `CONFIG.mail()` 差点写成读模块级 `CONFIG`。**
写成 `CONFIG.mailTransport`（而不是 `this.mailTransport`）的后果很隐蔽：
`Object.assign({}, CONFIG, { sendgridKey })` 这类覆盖**完全不生效**，
症状是「明明给了密钥却仍落到 console」，而且不报任何错。
现在读 `this`，测试里有一条「显式指定优先于密钥推断」就是为它写的。

**另有两处与本地版对齐的加固：**

- **服务端补了时钟回拨保护**。本地版早有 `guardClock`，服务端原先没有 ——
  理由是「服务端时钟可信」。但**可信不等于单调**：多实例的 NTP 校正、
  容器迁移都会让某个实例的 `now` 往后退，而这里判的正是「码有没有过期」。
  现在按「这条码自己的签发时刻」做水位，回拨超过 2 分钟即判该码不可用。
  容差比本地版的 60 秒宽，是因为服务端这个值要被「10 分钟有效」覆盖 ——
  把真人挡在门外比放过一次边界情况更糟。
- **邮箱形态校验的 `..` 规则两边补齐**。前端内核原先允许 `a..b@c.com`
  （本地部分连续点），服务端也不拦。按 RFC 5321 这是无效地址，
  现在两边同时拒收，测试里有一条跨端一致性断言。

### 4.8 1B 落地时顶出来的八件事（与原设计不同，都是实测的结果）

**① 同步记账**不能复用「已读」那套读写。**
设计里写「用 `ProgressStore.readMap` / `setRead` 存每条记录见过的云端时间戳」。
真做起来发现那是**布尔语义**（`if (val) m[id] = true`）：时间戳 `0` 被丢掉、
`-1`（冲突标记）读回来是 `true`、`9000` 也读成 `true`。
症状极其隐蔽 —— **表面上都「有值」**，于是「刚拉回来的又被推回去」、
冲突永远判不出来、游标永远是 0（每轮全量拉）。
现在这张表（`poem_sync_seen_v1`）有自己的读写，与「已读」不是一回事。

**② 「认领本机进度」= 打时间戳，但**不**记进 `seen`。**
两者看着都像「本机这份已就绪」，含义却相反：记进 `seen` 等于说
「已经和云端对齐了」，而它们恰恰是**还没有云端对应**的那一批 ——
用户先在本机背了一个月、之后才建账号，那批一篇都不能丢。
写错的症状是：新注册的人进度一条都同步不上去，且不报任何错。

**③ `touch()` 也**不许**顺手写 `seen`。**
同理：`seen` 记的是「云端最后给这一条的时间戳」，本机改动不改变那个事实。
写进去的后果是「看起来已经对齐」，这一条从此永远推不出去。

**④ 推成功之后要用「推上去的那枚时间戳」打标，不是「现在」。**
用 `now` 的后果：下一轮 `pending()` 判「本机时间戳 ≠ 见过的云端时间戳」，
于是同一条又被推一次，**每轮都推、永远推不完**。现在批量写一次盘
（逐条 `setItem` 在 N 条时会抖 N 次，且中途失败就只记了一半）。

**⑤ 冲突判定不能只看时间戳大小，还要看「云端知不知道本机这一版」。**
最初写「本机更新 + 时间戳对不上 = 冲突」，结果是**几乎每条本机改动都成了冲突**
（正常背书就是「本机更新」，而云端当然还没见过）。现在判据是
`seen[id] === 云端时间戳` —— 相等说明两边是**同一条线**上的先后，本机赢、推上去；
不等说明云端也动过而两份没有共同祖先，才请用户裁决。

**⑥ 冲突标记必须**最先**判。**
上一次已经判过「判不出来源」、用户还没选时，再来一轮不该把它又自动合并掉。
放在时间戳比较之后写的后果是：用户每次刷新页面，那个决定就被"重算"一次，
而他从来没被问过。

**⑦ 「先导出再决定」必须**真的给出文件**，且快照要**在发现冲突时就落**。**
最初只把「有没有快照」当条件返回，而快照本来只在用户点「保留账号」时才落 ——
于是这一支导出的是一张空纸。现在：一见冲突就落快照（后悔药提前备好），
「先导出再决定」把快照 + **待裁决的篇目清单**一起给出去，且一个字节都不改。

**⑧ 顺带修掉一个「只在真页面上才炸」的坑：引擎挂载时机。**
`js/sync-store.js` 最初在模块加载时抓一份 `window.ProgressStore`。
但页面里的脚本顺序不保证（老缓存里的旧页面尤其），
抓到 `null` 之后**永远**是 `null` —— 症状是 `Storage.set` 走不到同步记账，
**静默不同步**。现在每次现取（与 `js/storage.js` 的 `PS()` 同一条教训）。
这条还是 jsdom 的真页面测试顶出来的，数据层的纯 Node 测试看不见它。

> ✅ **2 期第一批已落地**：把 1A/1B 建好却**一直没接**的两根线接上，
> 并顺手把条款改到与代码一致。新增 `js/account-api.js`（**唯一接线处**）
> 与 `test/account-bind.test.js`（**纯 Node + 假 fetch，不联网**）。

#### 补的两根线（都是「服务端写好了、前端没人调」）

| # | 线 | 之前的状态 | 现在 |
|---|---|---|---|
| ① | `GET /api/me` | **没有任何页面调用过**（只有 `js/auth-api.js` 里定义着）。于是服务端判定的层级与角色没下发到界面，Pro/Max 的唯一合法挂载点空着 —— 决策清单第 8 条落不了地 | 个人中心与设置 · 通用在**有会话时**各问一次；答案带 `source:"server"` 写进 `poem_plan_v1`，`identity()` 据此让**服务端优先** |
| ② | `DELETE /api/account` | 接口与客户端方法都写好了，**但没有页面调它** —— `js/profile.js` 注销时走的是本机内核那个版本，**云端那一行还在**（合规问题，删除权） | 个人中心的注销走 `AccountApi.deleteAccount()`：**先服务端（先导出再删行）、后本机** |

#### 落地时定死的四条边界（都进了断言）

1. **失败不打断任何事** —— 断网 / 超时 / 503 / 401 / 5xx，一律只是「这一轮没问成」。
   所有网络调用包在 `AccountApi` 里，异常在那里被吞掉。
2. **不假装** —— `refreshMe()` 的 `reason` 只有四种取值，每种界面上有一句话对应：
   `ok` / `guest`（没登录，**正常状态**）/ `not-configured`（本站没开放）/ `unavailable`（连不上）。
   层级来源也如实标出来：「由服务器判定」还是「本机登记」——
   这两句在用户眼里的分量完全不同（本机那份改一行存储就能改）。
3. **不清用户数据** —— 拉不到 `/api/me` 时**不删**本机那份层级缓存。
   删了等于「后端抖一下，用户从 Pro 掉回 Free」，那是产品级事故
   （与 §1.3「后端挂了照样能背」同一条口径）。
   会话真过期（401）时才清，且**只清 `source:"server"` 那一份** ——
   管理员发的本机名单与它无关，退出登录不该把它抹掉。
4. **不做无谓请求** —— 没登录时**一个请求都不发**；`refreshMe()` 有**同会话只问一次**的闸
   （四页签点几下不会问四遍）。失败的那一次**也落闸** ——
   否则一个断网的用户每张页面都会白等 15 秒超时。

#### 三处「不这样就必错」的实现细节

**① 顺序：先服务端、后本机。**
`AuthCore.deleteAccount()` 会把内核会话清掉，而服务端那一步要会话 Cookie ——
反过来做的话，服务端会以 401 收场，而用户以为注销成功了。
`test/account-bind.test.js` 的第九节把「调服务端那一刻本机会话还在」直接断言下来。

**② 注销必须先导出、且导出**真的给到用户**。**
`/api/account` 先 `listProgress` 再做三件事（删进度 → 吊销会话 → 删账号），
导出那份**随响应回来**；页面把它做成一个下载按钮。
本期没有对象存储，所以返回的不是 `exportUrl` 而是一份数据 ——
**假装有个下载链接比不做更糟**。

**③ 连不上时**不阻断本机注销，但如实说云端还在**。**
`remote` 只有三种取值：`deleted` / `none` / `skipped`。
`skipped` 时页面**不跳走**，而是把那句话说清楚（删除权上的实情，不许含糊）。

#### 顺带修掉的一处「注释在说、代码没做」

`api/_lib/core.js` 的 `publicAccount()` **从来没下发过 `role`** ——
而客户端 `entitlement.js` 里早就写着「服务端下发的 role 优先」。
于是那条「服务端角色优先」一直只是注释：实际永远走本机兜底
（即「谁打开谁是 owner」，清空存储就能当管理员）。
现在 `publicAccount()` 下发 `role`（带白名单校验），
`identity()` 在 `source:"server"` 时以它为准，**两向都验**
（服务端说 user → 本机 owner 兜底让位；服务端说 owner → 本机 member 也升）。

#### 条款跟着代码改（按 §4.5 的纪律）

`/privacy/` 与 `/terms/` 的「删除方式」那条从**承诺式**改成**陈述式**：
写明「注销即删除服务器上的账号行与进度行，并把云端那一份导给你留存」，
**并如实补上一句「注销需联网；连不上时页面会说明云端那份还没删掉」**——
这句不是免责，是这一版代码的真实行为（`remote === "skipped"`）。
两页的字数上限同步收紧（隐私 2400 → 2391，靠删掉一句冗余表述，不是删信息）。

### 4.10 2B 期「短信口子」已落地（2026-09-17）：把注释变成真的能跑

> ✅ **2B 已落地**：在 8.1 之前，短信只是 `identity.channel` 里一个字符串。
> 现在「加 sms 通道」这件事**只差一个「谁去发」的实现** ——
> 归一化、摘要、频控、状态机全部就位，且**一分钱没花、一项配置没配**。

#### ① 短信不是「另一套流程」，是同一套流程的另一个 channel

`api/_lib/core.js` 的 `sendCode` / `verifyCode` **没有 channel 分支**在流程上：
码怎么生成、怎么摘要、失败几次作废、时钟回拨怎么护——两条通道**逐字共用**。
channel 只改三件事：**归一化规则、频控档、谁去投递**。

```
normIdentity(input) → { channel, value, mask, key }
  email → normalizeEmail / isEmailShape / emailHash
  sms   → normalizePhone / isPhoneShape / phoneHash（|phone| 命名空间）
```

摘要**按通道分命名空间**：同一个字符串在 email 与 phone 下摘要不同，
排除「某手机号串 = 某邮箱串」的交叉命中可能。表结构不变
（`accounts.email_hash` 那一列现在存的是「该身份标识的摘要」，列名是历史包袱）。

#### ② 频控更严 —— 因为短信是真金白银

邮箱成本近似零，短信 0.04 元/条。邮箱那套「一小时 5 封」放短信上
就是「一小时能烧 0.2 元/人」，被刷一晚几百上千。
所以短信独立一档：**60 秒 1 次、日 5 次、月 15 次**
（`config.rateSms` / `AuthCore.RATE_SMS`，两端同值）。

> ⚠️ 客户端内核的 `rateCheck` 必须能认 `phone` 档 ——
> 写了 `RATE_SMS` 而 `rateCheck` 不认它，短信就成了**实际不限速**，
> 而代码看起来「写了限制」。这是「写了但没接上」的同款坑（2A 那两个洞）。

#### ③ 没开通时**如实拒**，且不做任何副作用（2B 的核心口径）

```
POST { channel:"sms", value }  →  503 E_SMS_NOT_OPEN
```

1. **不假装**：没有真短信商时**绝不走 console 兜底当成功**。`transports.sms`
   是个空壳，它的 `send()` 直接 reject。一条收不到的短信 + 一个「已发送」提示 = 骗人。
2. **不做副作用**：拒在落库之前，**不建账号、不写码记录**。否则「试一下短信登录」
   在库里留一串孤儿账号。
3. **不偷偷降级**：界面收到 `E_SMS_NOT_OPEN` **不许**切回本机体验版
   （本机版同样发不出短信，切过去只是换个说法）。
   `js/auth-api.js` 给它一条**独立**文案，且不在回落名单里。

> `SMS_ENABLED=1` 只是「允许尝试」，不等于能发；`SMS_TRANSPORT` 指向已实现的商才真能发。
> 只开开关不接商，请求**仍然**是 503。

#### ④ 界面仍不渲染（条款不许跑在代码前面）

`login/index.html` 的短信按钮**仍是注释**。区别在于：注释里现在写清了
「开通时只需取消注释」——因为接口真的支持了。
但**按钮不渲染、也不写「即将上线」**：接口支持 ≠ 通道能用（还没签短信商）。

#### 验证

- `bash test/run.sh`：**4263 条断言全绿、0 失败**（较 2A 的 4185 增 78）
- `test/api.test.js` 新增第十八节：手机号归一化/掩码/摘要命名空间、
  **两端规则对拍**（前端与服务端对同一输入同判）、更严频控档、

## 5. 排期与顺序（为什么必须这个顺序）

```
0 期   ProgressStore 分域 ────┐  ✅ 已完成
       1.5~2 人日             │  产出：账号域/设备域清单
                              │  ← 这是 1 期同步的唯一前置
                              ▼
1A 期  后端 + 账号 + 发信 ────┐  ✅ 已完成（实际 1 人日）
       8~12 人日              │  产出：/api/me（权益挂载点）
                              │
                              ▼
1B 期  跨设备同步 ────────────┐  ✅ 已完成（实际 1 人日）
       6 人日                 │  前置：方案 B（已定，2026-09-15）
                              │  不做「出境同意」流程与界面
                              ▼
2A 期  注销自助 + 补洞 ───────┐  ✅ 已完成（2026-09-17）
       （含接上 /api/me）      │  产出：两根线接上、条款改到与代码一致
                              ▼
2B 期  短信口子 ─────────────┐  ✅ 已完成（2026-09-17）
       0 依赖 / 不花钱         │  产出：channel 枚举真的能跑、更严频控档、
                              │        未开通时如实回 503（不假装发短信）
                              ▼
2D 期  配置与真开通（用户自办）—— 注册 Supabase + SendGrid/Resend 密钥 +
                              │    SESSION_SECRET + 域名 SPF/DKIM/DMARC
                              ▼
2 期   条款二改（剩余部分）
                              ▼
3 期   收费（前置是**主体资质**，不是技术）
```

**三个顺序不能颠倒的理由：**

1. **0 期必须在 1 期之前** —— 不先分好家，同步一上线就会出现
   「在手机上调的字号覆盖了电脑上的」「电脑上背三上、手机上排二下」
2. **1A 必须在 1B 之前** —— 没有会话与账号，同步没有 key 可挂
3. **收费必须在最后** —— 它的前置是营业执照/个体工商户 + 备案 + 微信支付商户号，
   **全是日历时间不是人日**。技术侧的准备（`plan` 字段、`features[]`、服务端判定）
   在 1A 就做完了，**等资质一到就能开闸**

### 5.1 一句话回答你最初的问题

> **「那样我们就可以继续实现 0 和 1 了」—— 是的，那件事已经在 2026-09-15 定完了：**
>
> **进度上云 = 方案 B**（用户裁定，Issue #132）。配套只做三件据实做的事：
> 登录时据实告知、云同步开关（默认本地）、注销即删除 + 数据导出。
> **不做「出境同意」流程，也没有对应界面。** 见 §4.2。
>
> **1 期开工前不再有任何待裁事项。** 可以直接进 1A（6 个接口 + 发信适配层）。
